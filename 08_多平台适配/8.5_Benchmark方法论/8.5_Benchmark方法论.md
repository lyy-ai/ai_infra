# 8.5 Benchmark 方法论

## 课程概述

Benchmark 不是“跑个分”那么简单。多平台适配场景下，只有建立统一的测试标准、指标体系、自动化报告，才能公平地对比不同硬件/软件栈的性能，并指导后续优化方向。本节介绍如何构建跨平台性能对比框架，输出可复现、可追踪的 benchmark 报告。

学完本节后，你应该能够：

- 设计统一的 benchmark 指标体系。
- 实现跨平台推理 benchmark 框架。
- 自动化生成对比报告（表格、图表、结论）。
- 识别 benchmark 中的常见陷阱（warmup、抖动、功耗未统计等）。

---

## 1. 为什么需要统一 Benchmark

### 1.1 多平台对比的难点

| 难点 | 说明 |
|------|------|
| 软件栈不同 | TensorRT / ONNX Runtime / CANN / 自研 runtime 接口各异 |
| 精度不一致 | FP16 / INT8 / FP8 不同，直接比吞吐不公平 |
| 输入分布不同 | batch size、seq_len、并发数影响巨大 |
| 指标口径不同 | 有的算 prefill+decode，有的只算 decode |
| 环境差异 | CPU、内存、PCIe、散热都会影响结果 |

### 1.2 Benchmark 目标

- **公平**：同一模型、同一精度、同一输入分布。
- **可复现**：记录软硬件版本、commit、配置。
- **可追溯**：每次优化前后都能对比。
- ** actionable**：报告能指出下一步优化方向。

## 2. 统一测试标准与指标体系

### 2.1 必须控制的变量

- 模型结构、参数量、权重文件一致。
- 精度：FP32 / FP16 / BF16 / INT8 / INT4 明确标注。
- 输入：固定 batch size、seq_len、生成 token 数、随机种子。
- 环境：关闭无关进程，固定 CPU/GPU 频率（若允许）。
- warmup：正式测试前至少跑 5~10 次预热。

### 2.2 核心指标

| 指标 | 含义 | 适用场景 |
|------|------|----------|
| TTFT | 首 token 时间 | 交互式应用 |
| TBT / ITOK | 每 token 时间 | 流式生成 |
| Throughput | tokens/s | 离线批处理 |
| Latency (E2E) | 端到端延迟 | 完整请求 |
| Memory | 峰值显存/内存 | 资源规划 |
| Power | 平均功耗 / Energy per token | 边缘/成本敏感 |
| Accuracy | 精度损失 | 量化方案对比 |

### 2.3 吞吐 vs 延迟

```text
吞吐 (tokens/s) = batch_size × seq_len / latency
延迟 (ms/token) 越低，交互体验越好
通常：增大 batch 提升吞吐，但会牺牲单请求延迟
```

## 3. 自动化对比报告生成

### 3.1 Benchmark 框架结构

```text
benchmark/
├── config/          # 每个平台/模型的测试配置
├── inputs/          # 固定输入数据
├── runners/         # 各平台推理入口
├── metrics/         # 指标计算
├── reporters/       # 报告生成（Markdown / HTML / CSV）
└── main.py          # 一键运行
```

### 3.2 报告内容

1. 环境信息（CPU、GPU/NPU、驱动、软件版本）。
2. 模型信息（结构、参数量、精度）。
3. 测试配置（batch、seq_len、warmup、iteration）。
4. 性能表格（各平台各指标对比）。
5. 图表（吞吐柱状图、延迟折线图）。
6. 结论与下一步优化建议。

### 3.3 报告生成脚本

- `benchmark_framework.py`：定义配置、运行器、指标计算基类。
- `generate_report.py`：读取多个平台结果，输出 Markdown 对比报告。

## 4. 常见 Benchmark 陷阱

| 陷阱 | 后果 | 避免方法 |
|------|------|----------|
| 未 warmup | 首几次结果偏慢，拉高平均 | 先跑 10 轮再计时 |
| 混合 prefill/decode | 吞吐数字失真 | 分开统计 |
| 仅测理想 batch | 与实际业务不符 | 测多个 batch size |
| 忽略功耗 | 边缘场景选错方案 | 同步记录功耗 |
| 单点测试 | 结果不可信 | 多次取平均 / 中位数 |

## 6. 本节小结

- Benchmark 的核心是控制变量、统一口径、自动化报告。
- 指标体系至少包括延迟、吞吐、显存/内存、功耗、精度。
- 自动化报告让优化效果可量化、可追溯。
- 避免 warmup、混合阶段、单点测试等常见陷阱。
