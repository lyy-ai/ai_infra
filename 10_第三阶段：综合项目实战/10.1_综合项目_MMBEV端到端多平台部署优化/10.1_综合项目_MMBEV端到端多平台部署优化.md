# 10.1 综合项目：自动驾驶 MMBEV 模型端到端多平台部署优化

## 项目背景

自动驾驶多模态 BEV（MMBEV）感知模型需要将多路摄像头、激光雷达特征融合到统一 BEV 空间，模型结构包含 Backbone、View Transform、BEV Encoder、Detection Head 等模块，参数量约 60M，单帧输入包含 6 路摄像头图像（1600×900）。

业务侧提出在 **Orin（车端）**、**A100（云端仿真）**、**Ascend（国产化备份）** 三个平台同时部署，遇到的问题：

- Orin 端到端推理延迟 100ms，远超自动驾驶感知链路 50ms 的实时性要求。
- 跨平台算子实现不一致，A100 上跑的模型在 Ascend 上部分算子不支持、精度偏差大。
- 部署链路靠手工跑脚本，一次全平台验证需要 2 天，效率低、易出错。

**项目目标**：构建一套端到端部署优化方案，覆盖算子开发 → 编译优化 → Runtime 部署 → 量化压缩 → 推理引擎 → 多平台验证的完整流程，使 Orin 延迟降到 50ms 以内并满足精度要求。

---

## 一、业务模型分析

### 1.1 模型结构与耗时拆解

对 PyTorch FP32 模型在 A100 上做 profiling（Nsight Systems + PyTorch Profiler），得到各模块耗时占比：

| 模块 | 耗时占比 | 计算特征 | 关键算子 |
|------|----------|----------|----------|
| Backbone | 35% | 卷积密集 | Conv2d, SiLU |
| View Transform / BEV Pooling | 25% | 不规则 gather/scatter | 自定义 pooling |
| BEV Encoder | 20% | 规则卷积 | Conv2d, LayerNorm |
| Detection Head | 15% | 轻量卷积 + NMS | Conv1d, NMS |
| 其他（预处理/后处理） | 5% | CPU 为主 | resize, normalize |

### 1.2 关键结论

1. **BEV Pooling 是最大优化点**：PyTorch 原生 scatter 实现在 GPU 上高度非连续访存，Orin 上占 40% 耗时。
2. **小 kernel 过多**：整个模型约 200 个 kernel launch，Orin 上 launch overhead 占比不可忽略 → CUDA Graph 有收益。
3. **内存分配频繁**：中间 tensor 反复 cudaMalloc，峰值显存 14GB → 需要内存池。
4. **精度敏感层集中在 Head**：BEV 网格回归与 NMS 前特征对量化敏感 → INT8 需分层保护。

## 二、HPC 算子开发

### 2.1 核心算子优化

| 算子 | 优化手段 | 平台 |
|------|----------|------|
| BEV Pooling | 自定义 CUDA kernel：warp 级 reduce、共享内存分块、合并 scatter | A100 / Orin |
| LayerNorm + SiLU | kernel 融合，3 次全局访存降为 1 次 | A100 / Orin |
| Conv2d | Tensor Core + implicit GEMM（cutlass） | A100 / Orin |
| BEV Pooling | TBE 自定义算子 | Ascend |
| LayerNorm | CANN 内置算子 + 图融合 | Ascend |

### 2.2 跨平台适配规范

- **接口对齐**：统一 `(input_tensor, params) -> output_tensor` 签名，shape/stride/dtype 显式传递。
- **黄金标准**：每个算子先写 CPU numpy reference，再写平台 kernel。
- **一致性验证**：三平台跑同一组固定输入（固定 seed），判定标准：

| 精度 | max abs diff | cosine similarity |
|------|--------------|-------------------|
| FP16 | < 1e-3 | > 0.9999 |
| INT8 | < 1e-2 | > 0.999 |

### 2.3 成果

| 算子 | 平台 | 优化前 | 优化后 |
|------|------|--------|--------|
| BEV Pooling | Orin | 40ms | 8ms |
| BEV Pooling | A100 | 12ms | 4ms |
| LN+SiLU fused | Orin | 5ms | 2ms |
| BEV Pooling | Ascend | 15ms | 6ms |

**单算子平均性能提升 65%。**

## 三、编译优化

### 3.1 Laser 编译流水线

基于 Laser 编译框架搭建一键编译流水线：

```text
PyTorch MMBEV
  → ONNX 导出（固定输入 shape 分桶：6 路 / 8 路）
  → 前端优化：常量折叠、死代码消除（op 数减少 23%）
  → 图优化：conv+bn+silu 融合、layout 转换（NCHW→NHWC for Orin）
  → 后端 lowering：
      A100/Orin → TensorRT engine
      Ascend    → CANN om
  → 产物 + checksum + 版本命名（model-v2.3-trt-int8-tp1）
```

### 3.2 兼容性问题与解决

| 问题 | 解决方案 |
|------|----------|
| BEV Pooling 在 TensorRT 不支持 | 注册自定义 plugin，复用 CUDA kernel |
| 动态摄像头路数 | 按 4/6/8 路分桶编译 3 个 engine |
| Ascend LayerNorm 精度偏差 | 强制该层 FP32 计算，误差从 5e-2 降到 1e-3 |
| 中间 shape 推导失败 | 显式标注 dim，补充 reshape hint |

### 3.3 自动化

编译纳入 CI：提交算子/图改动后自动编译三平台产物并跑精度验证，全平台验证时间从 2 天缩短到 2 小时。

## 四、Runtime 优化

基于 TVM Relax 构建推理 Runtime，重点三项优化：

### 4.1 内存池

- 按 tensor shape 分桶缓存 buffer，推理全程零 cudaMalloc。
- KV/BEV 中间特征统一 workspace 复用。
- **效果：峰值显存 14GB → 9.8GB（-30%）。**

### 4.2 CUDA Graph

- Backbone + View Transform + BEV Encoder 为主干静态子图（约 200 个 kernel），捕获为 CUDA Graph 重放。
- **效果：消除 launch overhead，Orin 上节省约 8ms。**

### 4.3 异步流水线

```text
Stream A: H2D 拷贝下一帧  ─┐
                          ├─→ overlap
Stream B: 当前帧 GPU 推理 ─┘
CPU 线程池: 预处理 + 后处理（与 GPU 并行）
```

**综合效果：模型端到端延迟降低 40%（50ms → 30ms 的 Runtime 层贡献）。**

## 五、量化部署

### 5.1 INT8 量化方案

| 模块 | 精度策略 | 原因 |
|------|----------|------|
| Backbone | INT8（per-channel weight） | 卷积冗余大 |
| View Transform | INT8（敏感层保留 FP16） | BEV 坐标精度敏感 |
| BEV Encoder | INT8 | 规则卷积 |
| Head | FP16 | 回归精度敏感 |
| Activation | per-tensor scale + 校准集 2000 帧 | 覆盖典型驾驶场景 |

### 5.2 精度验证

- Tensor 级：逐层 diff，所有层 max abs diff < 1e-2。
- 感知指标级：nuScenes val 集 NDS 从 0.823 → 0.819（**损失 0.4% < 1%**）。
- 可视化抽检：BEV feature map、检测框与 FP16 对齐。

### 5.3 性能收益

| 平台 | FP16 延迟 | INT8 延迟 | 加速比 |
|------|-----------|-----------|--------|
| Orin | 55ms | 30ms | 1.8x |
| A100 | 18ms | 10ms | 1.8x |
| Ascend | 20ms | 12ms | 1.7x |

**推理速度整体提升约 2 倍。**

## 六、推理引擎

### 6.1 专用推理引擎

开发 MMBEV 专用推理引擎，整合上述所有优化：

```text
输入层：6/8 路摄像头队列 + 时间同步
  ↓
预处理线程池（4 线程，resize/normalize/标定变换）
  ↓
推理层：TensorRT engine + 内存池 + CUDA Graph + 双流异步
  ↓
后处理：BEV 解码 + NMS（GPU）+ 结果发布
```

### 6.2 软硬协同

- 多路输入共享 workspace，单帧多路一次 batch 送入，**GPU 利用率 60% → 85%**。
- 预处理/推理/后处理三级 pipeline，隐藏 H2D/D2H 延迟。
- 支持 4/6/8 摄像头配置动态切换（对应 3 个 engine）。

## 本节小结

- 端到端项目的关键是**先分析再动手**：profiling 找到 BEV Pooling 这个最大瓶颈，后续优化才有针对性。
- 五个模块环环相扣：算子快 → 编译顺 → runtime 稳 → 量化狠 → 引擎整。
- 所有优化都要回到业务指标：延迟、吞吐、精度、稳定性。
