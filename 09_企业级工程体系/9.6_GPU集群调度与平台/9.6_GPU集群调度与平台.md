# 9.6 GPU 集群调度与平台

## 1. 背景与动机：AI Infra 的另一半是"平台"

前面章节解决的是"单个任务怎么跑得快"：推理框架（第 5 章）、训练并行（第 6 章）、量化（第 7 章）。但公司里没有任何任务是跑在一张孤立显卡上的——所有训练/推理任务都要跑在 **GPU 集群**上，而 GPU 是公司最贵的资产。

两个朴素的事实决定了这一章的价值：

- **算力成本 = 卡数 × 时间 × 单价**。调度效率差 20%，对一个千卡集群就是每年数百万级的浪费。
- **业界 GPU 平均利用率常不足 50%**。排队空转、碎片、任务间波峰波谷，都是钱。

所以调度与平台不是"运维话题"，而是 AI Infra 工程师的核心战场。沿用本仓库的不可能三角思维，集群调度做的是另一组三角取舍：**利用率 / 公平性 / 隔离性**——

- 把卡塞得越满（利用率高），任务间干扰越强（隔离性差）、小任务越容易被饿死（公平性差）；
- 独占式隔离最好（整卡直通），利用率最低；
- 平台工程的全部内容，就是在这个三角里找到公司当前阶段的最优点。

## 2. K8s GPU 调度基础

### 2.1 GPU 如何暴露给容器

```text
节点上的 NVIDIA driver + device plugin
        │  上报节点可分配资源：nvidia.com/gpu: 8
        ▼
K8s scheduler 按容器 resources.limits 中的 nvidia.com/gpu 数量调度
        │
        ▼
kubelet 通过 device plugin 把具体 GPU 设备（/dev/nvidiaX）挂进容器
```

- **device plugin**：每个节点上的守护进程，向 kubelet 上报本节点 GPU 数量与健康状态。
- **容器申请**：Pod spec 里写 `nvidia.com/gpu: 2`，调度器把它当作一种标量资源和 CPU/内存一样处理。

### 2.2 原生调度器的两个根本问题

1. **不理解 GPU 拓扑**。一台 8 卡机器内部不是均质的：NVLink 域内通信带宽远高于跨机 RDMA；GPU 与 NUMA 节点、网卡（RDMA NIC）之间存在亲和性。原生调度器只看到"8 个可分配 GPU"，随机分配可能把 8 卡任务拆成 4+4 跨机，训练吞吐直接腰斩。
2. **不支持 gang scheduling**。原生调度器逐 Pod 调度：一个需要 64 卡的训练任务是 64 个独立 Pod，先调度的 Pod 占住卡等同伴——如果集群剩余资源凑不齐 64 卡，已占的卡就**空转死等**，甚至多个大任务互相持锁形成死锁。

## 3. Gang Scheduling 与批调度器

### 3.1 All-or-Nothing

分布式训练任务的特点是 **gang**：所有 worker 必须同时就位（all-or-nothing），缺一张卡全部卡住。批调度器（**Volcano**、**Kueue**、以及 Yarn 时代的对应物）把"一组 Pod"作为一个调度单元：

- 资源够 → 整组一起调度；
- 资源不够 → 整组排队，一张卡都不占。

### 3.2 排队、配额与公平共享

批调度器把集群治理变成队列治理：

| 机制 | 作用 | 典型实现 |
|------|------|----------|
| 队列（Queue） | 按团队/业务划分资源池 | Volcano Queue、Kueue ClusterQueue |
| 配额（Quota） | 每个团队保障性资源 + 弹性上限 | hard quota + borrowing |
| 公平共享（Fair Sharing） | 空闲资源按权重借出，团队交还时优先 | DRF 及其变体 |
| 优先级与抢占 | 高优任务（在线推理、紧急训练）抢低优任务 | priority + preemption |

**配额 + 借用**是核心模式：团队 A 保底 100 卡，集群空闲时可以用到 300 卡，但团队 B 的任务来了要能被抢占归还。这把"保底公平"和"整体利用率"同时拿到手——代价是被抢占任务要有 checkpoint/恢复能力（呼应 6.10 弹性训练）。

## 4. GPU 切分与共享

一张 A100/H100 对很多任务来说太大：小模型推理、开发调试、Notebook 都用不满。切分方案按隔离性从强到弱：

| 方案 | 粒度 | 隔离性 | 灵活度 | 说明 |
|------|------|--------|--------|------|
| **MIG** | A100/H100 硬件级最多 7 个实例 | 最强（硬件隔离 SM/显存/带宽，故障隔离） | 最低（几何约束固定，需重启重配） | 推理多租户首选 |
| **时间片共享** | 整卡 × N 个任务 | 最弱（显存不隔离，一个 OOM 全挂） | 最高（任意数量） | 开发机、低优任务 |
| **MPS** | 整卡 × N 进程 | 中（显存可设上限，计算仍争抢） | 高 | 比时间片延迟好，故障域仍共享 |
| **vGPU** | 虚拟化层切分 | 较强 | 中 | 需要 vGPU 授权，多见于虚拟化环境 |

**MIG 的 tradeoff 是典型的隔离性 vs 灵活度**：硬件级隔离让 SLA 可承诺，但 7 个实例的几何约束（如 3g.40gb 实例切出去后，剩余空间放不下第二个 3g）会造成"卡内碎片"；时间片共享灵活度满分，但显存不隔离意味着任何一个租户的显存泄漏都能拖垮整卡。

配套的 `mig_partition_planner.py` 在 A100 80GB 的 MIG 几何约束下做推理任务装箱规划，量化对比整卡直通 / 时间片共享 / MIG 三种方案。

## 5. 碎片问题

### 5.1 碎片是怎么形成的

大模型训练任务普遍要求 **8 卡整机**（一个完整 NVLink 域）。设想一台 8 卡机器被 1 卡推理任务占了 1 张：剩下 7 张卡空闲，但任何 8 卡训练任务都进不来——这 7 张卡就是**碎片**。集群越大、任务规格越杂，碎片越严重。

### 5.2 对抗碎片的策略

- **拓扑感知调度**：调度器理解 NVLink 域 / NUMA / 网卡亲和，8 卡任务只落整机，小任务集中 bin-packing 到少数机器上，把完整机器留给大任务。
- **bin-packing vs 回填（backfill）**：严格按优先级排序会让大任务饿死（小任务源源不断插队）；经典解法是 backfill——为大任务预留资源窗口，同时允许"能在窗口关闭前跑完"的小任务插进来填缝。
- **规格治理**：限制用户可申请的卡数档位（1/2/4/8），拒绝 3 卡、5 卡这类碎片制造机。

配套的 `gpu_scheduling_sim.py` 模拟 64 卡集群，对比朴素 FIFO 与"拓扑感知 bin-packing + gang scheduling"的等待时间、碎片率与利用率。

## 6. 利用率工程：混部与弹性

### 6.1 在线与离线的天然互补

- **在线推理**：延迟敏感（TTFT/TPOT 有 SLO），负载随用户访问有明显**波峰波谷**，深夜大量闲置；
- **离线训练**：吞吐优先、可以排队、可以被打断（有 checkpoint 就行）。

**混部**就是让训练任务跑在推理集群的波谷里：推理高峰时训练任务被抢占让路，低谷时训练任务把卡填满。这要求训练任务具备**弹性**（呼应 6.10 弹性训练）：节点被抢占后能缩容继续跑、资源回来后能扩容加速。训练任务由此成为集群的"**填谷**"负载。

### 6.2 PD 分离与调度的协同

5.6 节的 PD 分离在集群视角下有新的意义：prefill（compute-bound）和 decode（memory-bound）节点池的资源画像不同，可以分别调度到不同代际/不同性价比的硬件上；调度器按流量比例动态调整 P/D 节点数量，而不是为一个混合角色的实例池做整体扩容。调度器知道的"任务类型"越多，bin-packing 就越聪明——这是推理引擎设计与集群调度互相渗透的典型例子。

## 7. 监控与成本：让每一分算力有账可查

平台侧的监控不同于 9.5 节的单机指标，核心是**归集与归因**：

- **showback / chargeback**：按团队/项目/任务归集算力账单（卡时 × 卡型单价），showback 只展示、chargeback 真实计入成本中心。账单是最好的利用率推动力——"看得见的浪费才会被治理"。
- **利用率看板**：分团队/分集群的分配率（quota 用了多少）与真实利用率（nvidia-smi 的 SM 利用率）双层指标。只分配不使用是平台要抓的第一类浪费。
- **空闲卡回收**：长队列等待 + 零利用率的"僵尸任务"（忘了关的 notebook、挂死的训练）自动检测、提醒、回收。

## 8. 不可能三角视角的小结

| 取舍 | 牺牲 | 换取 |
|------|------|------|
| Gang scheduling | 调度延迟（整组排队） | 训练任务不死锁、不占空卡 |
| 配额 + 公平共享 | 大团队峰值弹性受限 | 小团队不被饿死、集群整体利用率高 |
| 抢占式混部 | 训练任务被中断的开销 | 推理波谷的算力不浪费 |
| MIG 切分 | 粒度固定、卡内碎片 | 硬件级隔离、SLA 可承诺 |
| 时间片共享 | 隔离性差、故障域共享 | 灵活度与密度最高 |
| 拓扑亲和 bin-packing | 小任务可能多等一会 | 整机留给大任务、碎片率下降 |

没有银弹：平台设计的每一次评审，本质上都是把这张表重新填一遍。

## 9. 工程实践

### 9.1 本节配套脚本

```bash
cd /data/liyangyang/ai_infra/09_企业级工程体系/9.6_GPU集群调度与平台

# 64 卡集群调度模拟：朴素 FIFO vs 拓扑感知 bin-packing + gang scheduling

# A100 80GB MIG 装箱规划：整卡直通 / 时间片共享 / MIG 三方案对比
python mig_partition_planner.py
```

两个脚本只依赖 stdlib + numpy，是离散事件模拟器与装箱规划器性质的教学程序。

### 9.2 落地建议

1. **先度量再优化**：没有分团队利用率看板和账单归集之前，不要上复杂调度策略——通常第一波收益来自回收僵尸任务和限制规格档位。
2. **调度器选型跟规模走**：几百卡以内 Kueue 足够；千卡以上、多队列复杂治理再考虑 Volcano 或自研。
3. **推理上 MIG、训练保整机**：推理多租户用 MIG 拿隔离性；训练任务尽量整机独占，别让别人的时间片任务混进训练机。
4. **弹性训练是混部的前提**：没有 checkpoint + 缩容能力的训练任务不要放进混部池，否则抢占就是事故。

### 9.3 开源参照：llm-d——推理编排与集群调度的合流

2025 年后值得关注的趋势是**推理服务的编排层开始与 K8s 调度融合**，代表项目是 **llm-d**（github.com/llm-d/llm-d，CNCF sandbox，Red Hat/Google Cloud/IBM Research/CoreWeave/NVIDIA 联合发起）：

- 它不是推理引擎，而是跑在 vLLM/SGLang 之上的 **K8s 原生分布式推理编排栈**：前缀缓存感知的智能路由、prefill/decode 分离部署、KV cache 分层 offload 与全局索引、基于实时推理信号的 SLO 感知自动扩缩容。
- 从平台视角看，llm-d 把本章讨论的多个主题产品化了：拓扑感知放置（PD 实例摆放）、弹性扩缩容（SLO 驱动）、多租户流量治理。
- 学习建议：它的 "well-lit paths"（经过 benchmark 验证的部署配方 + Helm chart）是个人搭建生产级 serving 实验环境的捷径；架构文档是"05 章推理技术如何变成生产系统"的参考答案。详见 `13.1_推理与Serving引擎` 第 6 节。

## 10. 面试高频问题

**Q1：K8s 原生调度器调度 GPU 有什么问题？**

一句话：两个问题——不理解 GPU 拓扑（NVLink 域 / NUMA / 网卡亲和），不支持 gang scheduling。

展开：原生调度器把 GPU 当标量资源，可能把 8 卡训练任务拆成跨机 4+4，NVLink 带宽优势全失；逐 Pod 调度导致多卡任务的先到 Pod 占卡空等，甚至多任务互相持锁死锁。解法是 device plugin 之上加拓扑感知调度与 Volcano/Kueue 批调度。

**Q2：什么是 gang scheduling，为什么训练需要它？**

一句话：把一组 Pod 作为整体调度——资源够就全部就位，不够就整组排队，一张不占。

展开：分布式训练 all-or-nothing，缺一张卡所有 worker 都卡住；非 gang 调度下已分配的卡空转死等，是纯粹浪费，极端情况多个大任务互相等待形成死锁。

**Q3：MIG 和时间片共享怎么选？**

一句话：要隔离性选 MIG，要灵活度选时间片。

展开：MIG 硬件级隔离 SM/显存/带宽，SLA 可承诺，适合生产推理多租户，但 A100/H100 最多 7 实例且几何约束固定；时间片共享密度最高但显存不隔离，一个任务 OOM 全卡遭殃，适合开发环境。MPS 居中：延迟好于时间片，隔离弱于 MIG。

**Q4：GPU 集群碎片是什么，怎么治理？**

一句话：零散空闲卡凑不齐任务需要的拓扑域（如 8 卡 NVLink 整机），看得见用不上。

展开：治理手段包括拓扑感知调度（大任务只落整机）、bin-packing（小任务集中到少数机器）、backfill（大任务预留窗口 + 小任务填缝）、规格治理（限制 1/2/4/8 档位）。脚本 `gpu_scheduling_sim.py` 量化演示了拓扑感知策略对碎片率的改善。

**Q5：怎么把集群利用率从 40% 提到 70%？**

一句话：度量先行（账单 + 利用率看板 + 僵尸回收），然后在线离线混部 + 弹性训练填谷。

展开：第一波收益通常是治理浪费——回收挂死任务、限制超规格申请；第二波是结构性——推理波谷跑可抢占的弹性训练（需要 6.10 的 checkpoint/缩扩容能力），配合配额借用让空闲 quota 流动起来。

**Q6：PD 分离和集群调度有什么关系？**

一句话：PD 分离把推理实例拆成资源画像不同的两类节点池，调度器可以分别选型和独立扩缩容。

展开：prefill compute-bound、decode memory-bound，适合不同硬件；调度器按实时流量比例调整 P/D 池大小，比混合实例池的整池扩缩容更省。任务类型信息越丰富，调度决策越优。

## 11. 小结

1. 集群调度与平台是 AI Infra 的另一半：它直接决定公司算力成本，核心取舍是利用率 / 公平性 / 隔离性的三角。
2. K8s 原生调度器不懂 GPU 拓扑、不支持 gang；Volcano/Kueue 补上批调度、配额、公平共享与抢占。
3. GPU 切分是隔离性与灵活度的取舍谱系：MIG > vGPU > MPS > 时间片。
4. 碎片治理靠拓扑感知 + bin-packing + backfill + 规格治理；利用率提升靠混部 + 弹性训练填谷 + 账单归因。
5. 调度器与引擎协同是趋势：弹性训练（6.10）让任务可抢占，PD 分离（5.6）让节点池可分型——平台懂任务越多，算力浪费越少。
