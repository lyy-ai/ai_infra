# 9.1 CI/CD 与自动化

## 课程概述

企业级 AI Infra 不是靠个人手动跑脚本堆出来的，而是靠**流水线、自动化、版本管理**持续交付出来的。CI/CD 在 AI 场景下的核心目标不仅是“编译通过”，还要保证模型转换、量化、编译后的精度与性能不会退化。本节介绍如何为 AI Infra 搭建一套 CI/CD 流水线。

学完本节后，你应该能够：

- 设计 AI Infra 的 CI/CD 流水线。
- 实现模型编译、测试、发布的自动化。
- 用版本管理追踪模型、代码、依赖的一致性。
- 识别 CI/CD 中的常见瓶颈与风险。

---

## 1. AI Infra CI/CD 的特殊性

### 1.1 与传统软件 CI/CD 的差异

| 维度 | 传统软件 | AI Infra |
|------|----------|----------|
| 产物 | 二进制 | 模型 + engine + 配置文件 |
| 构建时长 | 分钟级 | 小时级（大模型编译） |
| 测试目标 | 功能正确 | 精度 + 性能 + 稳定性 |
| 依赖 | 代码 + 库 | 代码 + 模型权重 + 数据集 + 硬件驱动 |
| 版本对象 | commit | commit + model checkpoint + docker image |

### 1.2 CI/CD 关键阶段

```text
代码提交
  ↓
Lint / Unit Test（算子、工具函数）
  ↓
模型转换 / 编译（ONNX → TensorRT / CANN / 自研格式）
  ↓
精度验证（Tensor Diff）
  ↓
性能回归测试（Benchmark）
  ↓
集成测试（端到端推理）
  ↓
产物打包（model + engine + config）
  ↓
发布 / 灰度上线
```

## 2. 模型编译 CI/CD 流水线

### 2.1 流水线设计原则

- **阶段清晰**：每阶段只做一件事，失败时快速定位。
- **产物隔离**：不同 commit / 不同模型版本独立目录。
- **资源调度**：GPU/NPU 编译任务需排队，避免争抢。
- **失败重试**：编译/测试偶发失败时自动重试。

### 2.2 GitHub Actions / GitLab CI 示例结构

```yaml
# .github/workflows/ai_infra_ci.yml
stages:
  - lint
  - build
  - test
  - benchmark
  - release

build_engine:
  stage: build
  script:
    - docker run --gpus all -v $(pwd):/ws build_image
        python scripts/build_engine.py --model $MODEL --output artifacts/
  artifacts:
    paths:
      - artifacts/*.plan
      - artifacts/*.om
```

### 2.3 关键产物

- 原始模型（PyTorch / ONNX / Safetensors）
- 编译后的 engine（.plan / .om / .custom）
- 配置文件（precision、input shape、batch、max seq len）
- 校验文件（MD5 / SHA256）

## 3. 自动化测试与验证

### 3.1 测试金字塔

```text
        /\
       /  \
      / E2E \          端到端推理（慢、覆盖广）
     /--------\
    /  Perf/Acc \      性能 + 精度回归
   /--------------\
  /   Unit Tests    \    算子、工具函数
 /--------------------\
```

### 3.2 自动化测试类型

| 测试 | 目标 |
|------|------|
| 单元测试 | 算子、工具函数、配置解析 |
| 模型转换测试 | ONNX / TRT / CANN 转换是否成功 |
| 精度测试 | 与 reference 的 diff 是否在阈值内 |
| 性能测试 | 延迟、吞吐是否退化 |
| 稳定性测试 | 长时间运行是否 OOM / 崩溃 |

### 3.3 自动化精度验证

- 固定输入、固定种子。
- 比较 FP32 / FP16 / INT8 与 reference 的误差。
- 输出 Tensor Diff 报告。

## 4. 版本管理与发布流程

### 4.1 版本对象

- **代码版本**：Git commit / tag。
- **模型版本**：模型权重版本、tokenizer、配置文件。
- **编译产物版本**：engine 文件 + 构建参数 + 依赖镜像 digest。
- **数据版本**：评测数据集、calibration 数据。

### 4.2 推荐版本命名

```text
model-v2.1.0-trt-8.6.1-fp16-tp1-pp1
        │      │       │     │
        │      │       │     └── 并行配置
        │      │       └──────── 精度
        │      └───────────────── TensorRT 版本
        └────────────────────── 模型版本
```

### 4.3 发布流程

```text
1. 打 tag 触发 release pipeline
2. 重新跑完整 CI/CD
3. 生成 release notes（变更点、性能数据、精度报告）
4. 产物上传对象存储 / 模型仓库
5. 灰度发布：先 1% → 10% → 全量
```

## 6. 本节小结

- AI Infra 的 CI/CD 需要同时保证功能、精度、性能。
- 流水线应分阶段：build → test → benchmark → release。
- 版本管理要覆盖代码、模型、产物、数据四个维度。
- 自动化是规模化的前提，也是避免人为错误的防线。
