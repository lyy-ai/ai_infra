# 13.1 推理与 Serving 引擎

> 学习目标：摸清 LLM 推理开源引擎的格局、各项目的生态位与架构特点，知道"什么场景选什么框架"、"读源码从哪个文件开始"。

## 1. 为什么引擎格局值得单独学

推理引擎是 AI Infra 中**迭代最快、工程密度最高**的开源领域：PagedAttention、Continuous Batching、PD 分离、Speculative Decoding 这些技术都是先在引擎社区落地，再进入教科书。理解引擎格局 = 理解这个领域的技术风向。

选择引擎时的四个判断维度：

1. **生态位**：通用 serving / 极致性能 / 端侧 / 特定硬件。
2. **架构路线**：Python 原生（迭代快）vs C++ 后端（性能上限高）。
3. **社区健康度**：响应速度、发版频率、背后组织（社区型 vs 厂商型）。
4. **与你目标岗位的匹配度**：面试国内大厂推理岗，vLLM/SGLang 源码经验是硬通货。

## 2. 主要项目档案

| 项目 | 背景 | 定位与特点 | 仓库 |
|------|------|-----------|------|
| **vLLM** | UC Berkeley 起家，社区驱动 | 事实标准。PagedAttention 发源地，功能最全（PD 分离、EP、多模态、硬件后端最多），Python 优先 + CUDA kernel | github.com/vllm-project/vllm |
| **SGLang** | LMSYS（伯克利系） | RadixAttention 发源地，结构化输出强，MoE/长上下文优化激进，RL rollout 场景事实标准 | github.com/sgl-project/sglang |

| **LMDeploy** | 上海 AI Lab（InternLM） | 国内团队代表，TurboMind 后端（类 TRT 路线），量化支持好，中文社区友好 | github.com/InternLM/lmdeploy |
| **Mooncake** | 月之暗面 | PD 分离 + KVCache 中心化存储的生产级开源实现（见 12.1 论文解读） | github.com/kvcache-ai/Mooncake |
| **LMCache** | U Chicago 等 | KV cache 复用与分层 offload 引擎，可作为 vLLM 插件 | github.com/LMCache/LMCache |
| **llama.cpp** | 社区（Georgi Gerganov 发起） | 端侧/CPU 推理事实标准，GGUF 格式，纯 C/C++ 无依赖 | github.com/ggml-org/llama.cpp |
| **llm-d** | Red Hat / Google Cloud / IBM Research / CoreWeave / NVIDIA 联合发起，CNCF sandbox | **编排层新物种**：不替代 vLLM/SGLang，而是跑在其上的 K8s 原生分布式推理编排栈（前缀感知路由、PD 分离、分层 KV、SLO 自动扩缩容） | github.com/llm-d/llm-d |

## 3. vLLM 源码阅读地图（重点）

vLLM 是推理引擎岗位面试的默认基准，建议按以下路径读（v1 架构）：

```
vllm/
├── v1/engine/            # 引擎主循环：LLMEngine / Processor / OutputProcessor
│   └── core/             #   调度器 Scheduler（continuous batching 决策点）
│       └── kv_cache_manager.py  # KV block 分配（PagedAttention 核心）
├── v1/worker/            # GPU worker：模型执行、CUDA graph 捕获
├── v1/attention/         # attention 后端抽象（flashinfer/flashattn/triton）
├── v1/sample/            # 采样与 logit 处理
├── model_executor/       # 模型定义与权重加载
└── entrypoints/          # OpenAI 兼容 API server
```

**推荐读法**：先跑通 `examples/` 离线推理 → 从 `LLM.generate()` 入口跟一遍完整调用链 → 重点读 Scheduler（5.3 章的 continuous batching 在这里落地）→ 再读 kv_cache_manager（5.2 章的 PagedAttention 落地）。

## 4. SGLang 与 vLLM 的差异（面试高频）

| 维度 | vLLM | SGLang |
|------|------|--------|
| 起家技术 | PagedAttention（显存分页） | RadixAttention（前缀树复用） |
| 编程模型 | OpenAI API + 离线 batch | 前端 DSL（程序化 LLM 调用）+ API |
| 强项 | 通用性、硬件覆盖、生态最大 | 结构化输出、MoE、RL rollout 集成 |
| 典型用户 | 通用 serving 首选 | 长上下文/Agent/后训练场景 |

实际趋势：两者功能高度互卷（vLLM 也有 prefix cache，SGLang 也有分页 KV），选型更多是生态与团队熟悉度问题。

## 5. 厂商引擎的定位

- **TensorRT-LLM**：NVIDIA 硬件上追求极致性能（in-flight batching、FP8 深度优化、与 NIM 微服务集成）；代价是 CUDA 绑定深、二次开发门槛高。面试 NV 系公司或性能敏感岗位必提。
- **LMDeploy**：国内 InternLM 生态，TurboMind C++ 后端设计干净，读 C++ 推理引擎源码它比 TRT-LLM 友好得多。
- **llama.cpp**：端侧圣经。学习 GGUF 量化格式、CPU SIMD kernel、内存映射加载的好地方。

## 6. 编排层新物种：llm-d 详解

llm-d 值得单独一节——它不是又一个推理引擎，而是代表了一个**新的架构分层**的出现。

### 6.1 定位：模型服务器之上的编排层

vLLM/SGLang 解决"单实例怎么跑得快"，llm-d 解决"几百个实例组成的服务怎么跑得聪明"：

```text
llm-d（编排层：智能路由 / PD 分离 / KV 分层 / 自动扩缩容）
  ↑ 调用
vLLM / SGLang（模型服务器：单实例推理执行）
  ↑ 运行于
Kubernetes（基础设施层：容器编排与资源管理）
```

2026 年 3 月加入 CNCF sandbox，由 Red Hat、Google Cloud、IBM Research、CoreWeave、NVIDIA 联合发起——这个发起阵容说明业界已形成共识：**推理系统的竞争点正在从引擎内部移到引擎之间的编排**。

### 6.2 核心能力（四大主题 + 批处理）

1. **智能路由**：前缀缓存感知 + 负载感知的请求路由（5.5 章思想的生产化），以及预测延迟调度（用延迟预测模型而非启发式规则做调度）。
2. **高级 KV Cache 管理**：分层 offload 到 CPU/磁盘 + 全局 KV cache 状态索引——多轮对话场景的有效工作集被显著放大（5.12 章思想的生产化）。
3. **大模型 serving**：PD 分离 + 宽专家并行（wide EP）跑 DeepSeek-R1、GPT-OSS 级别的大 MoE（5.6/5.11 章的生产化）。
4. **运维与 SLO**：多租户流量控制、基于实时推理信号的 SLO 感知自动扩缩容。
5. **批处理**：OpenAI 兼容 Batch API 的离线大批量推理。

### 6.3 公开的性能数据（项目方发布）

- 前缀缓存感知路由 vs 轮询：输出吞吐 3 倍、TTFT 快 2 倍（Llama 3.1 70B，4× AMD MI300X，Tesla/Red Hat 验证）。
- 预测延迟调度：TTFT 和 ITL 降 40%（NVIDIA GPU，Google 验证）。
- PD 分离：吞吐最高提升 70%（GPT-OSS on B200，AWS 验证）；同基础设施下 10-30% 吞吐提升（OCI 验证）。
- 宽专家并行：16×16 B200 集群 50k tok/s 输出（约 3.1k tok/s 每 decode GPU）。
- 分层 KV offload：250 并发用户下吞吐提升 13.9 倍（4× H100，对比仅 GPU 缓存）。

### 6.4 为什么它重要（对学习者）

1. **它是 05 章 + 09 章知识的"参考答案"**：PD 分离、前缀缓存、KV 分层、SLO 调度这些本仓库逐章讲过的技术，llm-d 把它们组装成了一套 K8s 原生产品——读它的架构文档能看到"教科书知识如何变成生产系统"。
2. **部署形态是 Helm chart + 测试过的配方（well-lit paths）**：降低了个体复现生产级 serving 的门槛——租几台 GPU 机器加一个 K8s 集群就能搭出大厂同款架构。
3. **面试新考点**："单引擎优化 vs 编排层优化"的分工是 2025 后推理系统面试的分水岭问题。
4. **参与价值**：CNCF sandbox 早期项目，社区处于建设期（SIG 分组、双周会），比成熟项目更容易参与核心讨论。

### 6.5 局限与注意

- 强绑定 K8s：没有 K8s 环境的团队引入成本高（这也是它与纯引擎的本质差异）。
- 性能数字来自项目方与合作伙伴的特定配置验证，迁移到自己的负载需要重新 benchmark（它提供了 Prism 可复现 benchmark 平台）。
- 编排层的收益在"多实例 + 前缀重复 + 长上下文 + 大模型"场景最大；单实例小模型场景用不上。

### 6.6 配套工具：AIConfigurator——PD 分离配置的自动寻优

引入编排层之后紧跟着一个新问题：**配置空间爆炸**。PD 分离后要决定 prefill worker 数、decode worker 数、每个 worker 各自的 TP/PP 并行度，再叠加 TTFT/TPOT 双 SLO 约束——手工试错的组合数根本跑不完。

**AIConfigurator**（NVIDIA ai-dynamo 组织开源，论文 arXiv 2601.06288）就是解决这个问题的工具：

1. **建模方式**：不用解析公式估算，而是用目标机器与框架上**采集的真实性能数据**建模推理性能（比 5.8 节手工估算脚本高一个置信度层级）。
2. **使用方式**：CLI 给定模型、GPU 型号与数量（如 `--model Qwen/Qwen3-32B-FP8 --total-gpus 32 --system h200_sxm`），可选 SLO 目标（`--ttft 2000 --tpot 30`），它搜索数千种配置输出推荐。
3. **产出**：直接生成可用于 **Dynamo 或 llm-d** 部署的配置文件——它是编排层的"配置计算器"，与 llm-d 构成"规划 → 部署"的配套关系。
4. **对本仓库读者的意义**：5.8 节 `parallelism_planner.py` 教的是手工估算的第一性原理，AIC 是同一问题的工业级自动化版本；两者对照能理解"解析估算 vs 实测建模"的路线差异。

**维护状态注意**：AIC 已进入维护模式，新功能迁移至后继项目 **AISimulate**（github.com/ai-dynamo/aisimulate）——学习其方法论（性能建模 + 配置搜索）的价值不受迁移影响，跟进新发展看 AISimulate。

## 7. KV Cache 系统与推理仿真：Tair KVCache 与 HiSim

### 7.1 Tair KVCache：企业级全局 KV Cache 中间件

阿里云开源的 **Tair KVCache**（github.com/alibaba/tair-kvcache）是"全局 KV 管理"这个新兴品类的企业级样本，与 Mooncake/LMCache 形成三种路线对照（详见 5.12 章 2.3 节）：

- **KVCache Manager**（已开源的核心组件）：集中式部署，统一管理全集群 KV Cache 元数据——多种匹配逻辑（前缀/滑窗/KV 匹配）、两阶段写入（先取写地址、写完通知）保可靠性、异构存储后端抽象（HF3FS/Mooncake/NFS 统一接口）、容量治理（配额/水位/逐出/异步删除）。
- **Optimizer**：回放真实 KV 访问 trace，仿真命中率与容量消耗，指导容量规划——容量决策从"拍脑袋"变成"先仿真后扩容"。
- **引擎适配**：客户端已支持 vLLM、SGLang、RTP-LLM、TRT-LLM。

学习价值：读它的组件划分（接入层/缓存逻辑/存储管理/索引管理/容量管理/仿真优化），是理解"一个生产级缓存中间件长什么样"的完整教案。

### 7.2 HiSim：免 GPU 的 LLM 推理仿真器

Tair KVCache 仓库中的 **HiSim**（hisim/ 子目录）是另一个方向的工具：**基于 CPU 的高保真 LLM 推理仿真系统**——

1. **做什么**：回放真实推理负载 trace，在**没有 GPU** 的情况下预测 TTFT、TPOT、吞吐等关键指标。
2. **精度**：官方报告在 SGLang v0.5.6.post2 + Qwen3 Dense 系列 + H20 的组合下预测误差低于 5%。
3. **与 AIConfigurator 的对照**：两者目标相同（低成本预测 serving 性能、辅助配置决策），机制不同——AIC 用实测性能数据建模 + 配置空间搜索，HiSim 用 trace 回放做事件级仿真。前者回答"最优配置是什么"，后者回答"这个配置跑我的真实负载会怎样"。

### 7.3 品类观察

KV Cache 正在从"引擎内部实现细节"演变为"独立的基础设施品类"：Mooncake（架构级）、LMCache（引擎插件级）、Tair KVCache（中间件级）三条路线并存，配套的仿真/规划工具（HiSim/AIConfigurator/AISimulate）也在成形——这是 2025-2026 推理 infra 最活跃的开源赛道之一。

## 9. 面试视角

- **Q：vLLM 和 SGLang 选哪个？** A：通用 serving 选 vLLM（生态最大、硬件支持最全）；长上下文/前缀重复高/RL rollout 场景 SGLang 更优；追求极限性能且全 NVIDIA 栈考虑 TRT-LLM。
- **Q：llm-d 和 vLLM 是什么关系？** A：不是竞品——vLLM 是模型服务器（单实例执行），llm-d 是其上的 K8s 原生编排层（跨实例的智能路由、PD 分离、KV 分层、SLO 扩缩容）。
- **Q：vLLM 的 V1 架构核心组件？** A：Processor → Scheduler（continuous batching）→ KVCacheManager（block 分配）→ Worker（模型执行 + CUDA Graph）→ OutputProcessor。
- **Q：你怎么跟进推理引擎的新特性？** A：盯 vLLM/SGLang 的 release note 和 RFC issue，重要特性先看对应论文再读实现 PR；编排层跟踪 llm-d 的 well-lit paths 与 SIG 动态。
