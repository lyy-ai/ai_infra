# 6.10 弹性训练与容错

## 课程概述

前面 6.1-6.9 节讨论的都是"理想世界里"的分布式训练：机器不死、网络不断、速度一致。万卡集群的真实世界恰恰相反——故障是日常，不故障才是意外。一个万卡任务跑两个月，经历数百次中断是常态。容错做得好与坏，直接决定有效训练时间占比（goodput）是 90% 还是 50%，也就是同样一批卡，训练成本差近一倍。

学完本节后，你应该能够：

- 从 MTBF 视角解释为什么万卡集群"每天多次中断"是数学必然。
- 列举故障类型谱：ECC/XID、NVLink、网卡光模块、节点宕机、straggler、NCCL hang。
- 设计 checkpoint 策略：同步 vs 异步、频率与故障损失的权衡、in-memory 副本。
- 说明 torch elastic 的弹性伸缩机制及其与调度器的联动。
- 描述故障检测、慢节点摘除与热备替换的工程闭环。

## 1. 背景与动机：万卡集群的故障现实

### 1.1 MTBF 视角：规模本身制造故障

单张 GPU 的年化故障率虽然只有几个百分点，看起来很低，但集群的期望故障间隔是：

$$
\text{MTBF}_{cluster} = \frac{8760 \text{ 小时}}{N \times \lambda}
$$

其中 $\lambda$ 是等效到每张卡的年化中断率。注意中断不只来自 GPU 本身：NVLink、网卡光模块、存储、软件 hang 任何一层出问题都会中断训练。仅算 GPU（$\lambda \approx 3\%$）时万卡 MTBF 约 29 小时；把全故障层算进去，等效年化中断率可达约 20%（参考公开数据：Llama-3 用 16k 卡训练 54 天经历数百次中断，约每天 8 次），万卡集群 MTBF 降到**数小时量级，平均每天多次中断**。规模本身就是故障的放大器，这是数学，不是运维水平问题。

### 1.2 故障类型谱

| 故障类型 | 表现 | 检测难度 | 备注 |
| -------- | ---- | -------- | ---- |
| GPU ECC/XID 错误 | 显存位翻转、XID 报错，卡直接掉线 | 低（有明确日志） | 最常见的硬件故障 |
| NVLink 故障 | 节点内通信报错或降速 | 中 | 可能只降速不报错，变成慢节点 |
| 网卡/光模块 | RDMA 丢包、带宽下降 | 中 | 光模块是易损件 |
| 节点宕机 | 整机无响应 | 低 | 电源、主板、OS  panic |
| 慢节点 straggler | 不报错，但每步都拖慢全局同步 | 高 | DP/PP 的同步语义放大其危害 |
| 软件 hang（NCCL 死锁） | 集合通信永不返回，全体卡死 | 最高 | 最难排查，日志往往没有有效信息 |

straggler 和 hang 是最阴险的两类：同步式数据并行里，**一步的速度由最慢的一张卡决定**；hang 则让所有卡空转烧钱，直到 watchdog 超时。

### 1.3 为什么容错是经济问题

训练总成本的真实公式：

$$
\text{总成本} = \frac{\text{算力成本}}{\text{goodput（有效训练时间占比）}}
$$

goodput 的损失来自三块：故障后重启的初始化、丢失的未 checkpoint 进度、checkpoint 本身的开销。万卡任务不做容错，goodput 掉到 50% 以下是常态——等于买两万张卡只用一万张。容错不是锦上添花，是万卡训练的第一优先级工程。

## 2. 核心原理

### 2.1 Checkpoint 策略：用存储换进度

**同步 checkpoint 的问题**

671B 级别模型，参数（BF16 约 1.3 TB）+ FP32 主权重 + Adam 的 m/v 状态 + 梯度，优化器状态总量可达**数 TB**（约 10 TB 量级）。同步 checkpoint 让全体 GPU 停下来等落盘：即便聚合存储带宽做到约 0.5-1 TB/s，每次也要阻塞数十秒级。每 15 分钟存一次，光 checkpoint 就吃掉数个百分点 goodput。

**异步 checkpoint**

两阶段：先把显存中的状态快照到 CPU 内存（pinned memory，秒级，阻塞很短），训练立刻恢复；后台线程再把 CPU 快照写到持久化存储。`torch.distributed.checkpoint` 的 async save 即此模式。把"阻塞训练的时间"从"存储带宽决定"压缩到"内存拷贝带宽决定"，阻塞时间降一个数量级以上。

**checkpoint 频率的 tradeoff**

故障发生时，丢失的进度 = 上次 checkpoint 之后已训练的时间，期望损失约为间隔的一半。存得越频繁，单次故障损失越小，但 checkpoint 开销越大。最优间隔由 MTBF、单次 checkpoint 开销、重启时间共同决定——配套脚本会扫描这个权衡。

**in-memory 副本**

更进一步：checkpoint 不落盘，而是备份到**同伴节点的内存**里（每个 rank 的状态同时写一份到邻居）。节点故障后直接从同伴内存拉取恢复，**秒级恢复**，跳过存储 IO 和重新初始化的分钟级开销。代价是要占用额外内存做副本，并处理节点对同时故障的小概率事件（可与低频落盘组合）。

### 2.2 弹性训练：让 world size 变成变量

**torch elastic（torchrun）** 的核心机制：

- **elastic agent**：每个节点上一个 agent 进程，负责拉起/监控本节点的 worker，worker 死亡时按策略重启或上报。
- **rendezvous（汇合点）**：所有节点通过 rendezvous 后端（etcd、c10d 等）协商出当前 world size 和 rank 分配。节点加入/退出时重新 rendezvous，**动态调整 world size**，训练不必整体停掉。
- 节点减少时用剩余节点继续训练（结合弹性数据并行重分片），节点恢复后下一批重新加入。

**与调度器的联动**：K8s/Slurm 负责资源层——检测节点故障、把故障节点摘除、调度热备机补位；torch elastic 负责训练层——重新 rendezvous、从最近 checkpoint 恢复。两层配合才能形成"故障-摘除-补位-恢复"的自动闭环。

### 2.3 故障检测与定位

**心跳与 NCCL timeout 的局限**：NCCL 的 watchdog timeout 只能告诉你"有人死了"（集合通信没完成），**不告诉你是谁**——hang 住的是受害者还是肇事者，从 timeout 日志本身看不出来。

**hang 排查工具链**：

- 各 rank 的堆栈快照（py-spy、torch 的 flight recorder/TRACE）找出卡在哪个集合通信；
- 对比各 rank 进入通信的顺序，定位"大家都到了、只有谁没来"；
- NCCL 的 `TORCH_NCCL_TRACE_BUFFER` 等机制记录通信事件环形缓冲，事后回放。

**慢节点检测**：straggler 不死，只是慢。有效手段是对 allreduce 延迟做**分位数监控**（p50/p99 按节点统计），持续偏离中位数的节点判定为慢节点，先标记观察，确认后**自动摘除**并用**热备机**替换——万卡集群常备一定比例的 spare 节点，故障节点自动下线、备机自动补位、从 in-memory 副本或 checkpoint 恢复。

## 3. 计算/通信/显存 tradeoff 分析

容错同样落在不可能三角上，只是这里的"计算"换成了"有效训练时间"：

| 手段 | 有效时间（收益） | 代价 | 三角解读 |
| ---- | ---------------- | ---- | -------- |
| 提高 checkpoint 频率 | 单次故障损失减小 | checkpoint 开销增大 | 存储 IO 换进度 |
| 异步 checkpoint | 阻塞从数十秒降到秒级 | CPU 内存占用、实现复杂 | 内存换时间 |
| in-memory 副本 | 恢复从分钟级到秒级 | 同伴节点内存被占 | 显存/内存换时间 |
| 弹性缩容继续训练 | 不等备机，少停机 | 缩容后吞吐下降、重分片开销 | 算力换可用性 |
| 热备机 | 秒级补位 | 常备空闲卡（约百分之几） | 算力冗余换时间 |
| 严格健康预检 | 减少带故障开训 | 开训前多花分钟级时间 | 开局慢换全局稳 |

核心规律：**容错的所有手段都是拿冗余（存储、内存、备用算力）换有效训练时间**。

## 4. 对比表格

### 4.1 Checkpoint 方案对比

| 方案 | 阻塞时间 | 恢复速度 | 资源代价 | 适用 |
| ---- | -------- | -------- | -------- | ---- |
| 同步落盘 | 数十秒级（TB 级状态） | 分钟级（读盘+初始化） | 低 | 小规模/低成本场景 |
| 异步落盘 | 秒级（仅内存快照阻塞） | 分钟级 | CPU 内存 | 主流大模型训练 |
| in-memory 副本 | 秒级 | 秒级 | 同伴节点内存 | 万卡高频故障环境 |
| 组合（异步+定期落盘） | 秒级 | 秒级/分钟级兜底 | 中 | 工业界标准做法 |

### 4.2 故障检测手段对比

| 手段 | 能发现什么 | 局限 |
| ---- | ---------- | ---- |
| 心跳/进程监控 | 节点宕机、进程崩溃 | 发现不了 hang 和慢节点 |
| NCCL watchdog timeout | 集合通信卡死 | 只说"有人死了"，定位难 |
| flight recorder/TRACE | hang 现场回放 | 事后分析，非实时 |
| allreduce 分位延迟监控 | straggler 慢节点 | 需要基线与阈值调优 |
| nccl-tests 预检 | 带故障的硬件 | 只能开训前用 |

## 5. 工程实践

### 5.1 健康检查前置

开训前对全部节点跑 nccl-tests（allreduce/alltoall 带宽与延迟基线）、GPU burn-in、ECC 状态检查，把"带病上岗"的节点在浪费机时之前剔除。万卡任务开训成本极高，预检的分钟级投入回报率极高。

### 5.2 分层监控

训练过程中三层监控并行：

1. **硬件层**：XID/ECC 计数、温度、NVLink 状态、网卡误码率；
2. **通信层**：集合通信延迟分位数、重传率；
3. **训练层**：step time 分布、loss 曲线异常、吞吐 MFU。

任何一层异常都要能自动触发"标记-隔离-替换-恢复"流程，而不是等人半夜看告警。

### 5.3 公开实践要点

- **Meta**（LLaMA 系列训练报告）：万卡级训练中硬件故障是中断的主要来源，自动化摘除 + 快速重启把人工干预压到极低比例。
- **字节**（MegaScale 等公开工作）：强调全链路可观测性与自动容错闭环，checkpoint 与恢复流程高度自动化。
- **DeepSeek-V3 报告**：训练框架内置高效 checkpoint 与容错设计，配合 DualPipe 等调度，把长周期训练的可用性做到很高水平；其经验之一是训练框架与集群调度深度协同，而不是各自为战。

### 5.4 动手实验

代码文件：`6.10_弹性训练与容错/checkpoint_cost_model.py`

```bash
cd /data/liyangyang/ai_infra/06_分布式训练
/data/qwen35_env/bin/python 6.10_弹性训练与容错/checkpoint_cost_model.py
```

脚本给定集群规模、单卡年故障率、模型+优化器状态大小、存储带宽、checkpoint 间隔，计算：

- 集群期望故障间隔（MTBF）；
- 每次故障平均损失的训练进度；
- 同步 vs 异步 checkpoint 下的 goodput；
- 扫描不同 checkpoint 间隔，分别找出同步/异步方案的最优间隔。

### 实验建议

- 把集群规模从 1k 调到 10k 再到 32k，观察 MTBF 和 goodput 如何变化（规模越大，checkpoint 必须越频繁，异步化收益越大）。
- 把存储带宽减半，看同步方案的最优 goodput 掉到多少。
- 修改重启时间参数，理解为什么 in-memory 副本（秒级恢复）在万卡场景回报巨大。

## 6. 常见误区

### 6.1 "单卡故障率很低，集群应该很稳"

MTBF 与卡数成反比。万卡集群即便单卡年化故障率只有 3%，期望也是每天多次中断。规模本身就是故障源。

### 6.2 "NCCL timeout 报错就能定位故障卡"

timeout 只表明集合通信没完成。卡死的可能是受害者（等一个已经死了的对端）。定位要靠各 rank 堆栈快照与通信事件回放。

### 6.3 "checkpoint 越频繁越好"

checkpoint 有真实开销，频率翻倍开销翻倍。最优间隔由 MTBF、单次开销、重启时间共同决定，存在解析上的最优点（见配套脚本扫描结果）。

### 6.4 "弹性训练就是自动重启"

自动重启只是最后一环。完整的弹性包括 rendezvous 动态调整 world size、弹性数据重分片、与调度器的摘除/补位联动、从最近 checkpoint 恢复进度。

## 7. 面试高频问题

**Q1：为什么万卡集群故障是常态？给个量级。**

一句话：MTBF = 8760 / (N x 等效年化中断率)；仅 GPU 一层（年化约 3%）万卡 MTBF 约 29 小时，计入网络/存储/软件全故障层后等效年化中断率约 20%，MTBF 降到数小时，每天多次中断。

展开：单点可靠性再高，乘以一万都会被放大成日常事件。参考公开数据，Llama-3 用 16k 卡训练 54 天经历数百次中断，约每天 8 次，其中约一半与 GPU 相关，其余来自网络与软件层。所以万卡训练的第一优先级不是峰值算力而是容错——goodput 从 50% 提到 90% 等于省下半个集群的钱。

**Q2：同步和异步 checkpoint 的区别？**

一句话：同步 checkpoint 全体 GPU 阻塞等落盘（TB 级状态、数十秒级），异步先快照到 CPU 内存再后台写盘，阻塞降到秒级。

展开：671B 模型优化器状态可达约 10 TB，存储带宽有限时同步阻塞不可接受；torch.distributed.checkpoint 的 async save 把阻塞时间从存储带宽解耦到内存拷贝带宽。进一步还有 in-memory 副本：状态备份到同伴节点内存，秒级恢复。

**Q3：checkpoint 频率怎么定？**

一句话：存在最优间隔——太稀疏单次故障损失大（期望损失约为间隔一半），太频繁 checkpoint 开销吃掉 goodput。

展开：用 goodput 模型（间隔 I、开销 C、MTBF M、重启 R）：goodput 约等于 (I - I/M x (I/2 + R)) / (I + C)，对 I 求极值即得。工程上结合异步 checkpoint 把 C 压小后，最优间隔显著变密，万卡场景常见数分钟到半小时级（见配套脚本扫描结果）。

**Q4：straggler 慢节点怎么发现和处置？**

一句话：对 allreduce 延迟做按节点分位数监控（p50/p99），持续偏离中位数的节点判定为 straggler，自动摘除并用热备机替换。

展开：straggler 不报错所以心跳发现不了；同步数据并行下每步速度由最慢卡决定，一个慢节点拖垮全集群。检测靠通信延迟统计而非存活探测；处置闭环是标记-隔离-备机补位-从 checkpoint/in-memory 副本恢复。

**Q5：NCCL hang 为什么难排查？怎么排？**

一句话：hang 时全体卡在集合通信里空等，watchdog 只能告诉你超时，无法区分肇事者与受害者。

展开：排查工具链是各 rank 堆栈快照（py-spy）+ NCCL flight recorder/TRACE 事件回放，对比各 rank 到达通信的序列找出缺席者；根因常见于硬件（NVLink/网卡半死）或不同 rank 通信顺序不一致的代码 bug。

**Q6：torch elastic 是怎么实现节点增删不中断训练的？**

一句话：每个节点的 elastic agent 监控 worker，通过 rendezvous 后端重新协商 world size 与 rank，节点退出后剩余节点重新汇合继续训练。

展开：K8s/Slurm 在资源层摘除故障节点、调度热备机；torch elastic 在训练层重新 rendezvous、重分片数据、从最近 checkpoint 恢复。缩容继续训练用吞吐换可用性，备机到位后再扩容恢复。

## 8. 本节小结

1. 万卡集群的故障是数学必然：MTBF 与卡数成反比，万卡意味着每天多次中断。故障类型谱从 ECC/XID、NVLink、网卡光模块、节点宕机，到最难缠的 straggler 与 NCCL hang。
2. 容错是经济问题：训练总成本 = 算力成本 / goodput，不容错的万卡任务 goodput 可掉到 50% 以下。
3. Checkpoint 三板斧：异步 checkpoint（内存快照 + 后台落盘）把阻塞降到秒级；in-memory 副本把恢复降到秒级；频率存在理论最优点，由 MTBF、开销、重启时间共同决定。
4. 弹性训练靠 torch elastic 的 agent + rendezvous 动态调整 world size，与 K8s/Slurm 联动形成"故障-摘除-补位-恢复"闭环。
5. 检测分层：心跳管死活、allreduce 分位延迟管慢节点、flight recorder 管 hang 定位；nccl-tests 预检把带病节点挡在开训前。
