# 6.9 MoE 训练与专家并行

## 课程概述

混合专家模型（Mixture-of-Experts, MoE）用"稀疏激活"打破了稠密模型的显存-算力锁定：总参数可以做得极大，但每个 token 只激活其中一小部分。以 DeepSeek-V3 为例：总参数 671B，每 token 激活约 37B，路由专家 256 个 + 共享专家 1 个，每 token 经 top-8 路由到 8 个专家。

但 MoE 把难题从"显存放不下"转移到了"通信扛不住"：专家总参数巨大，必须切到不同卡上（专家并行，Expert Parallelism, EP），而 token 要靠 all-to-all 通信找到它的专家。all-to-all 是整个分布式通信原语中对网络拓扑最敏感的一个，因此 MoE 训练成为通信优化的终极战场。

学完本节后，你应该能够：

- 解释为什么 MoE 必须引入 EP，以及 EP 与 TP/PP/DP 的关系。
- 估算一次 MoE 层前向/反向的 all-to-all 通信量，并判断通信占比。
- 说明负载均衡的三类手段：auxiliary loss、aux-loss-free bias、capacity factor。
- 解释 DualPipe 如何把 all-to-all 藏进计算里。
- 为 MoE 模型设计 TP/EP/DP/PP 的组合拓扑。

---

## 1. 背景与动机：为什么 Dense 三板斧不够

### 1.1 MoE 的账

Dense 模型每 token 激活全部参数，参数量 = 计算量 = 显存占用，三者同比例增长。MoE 把 FFN 换成 N 个专家 + 路由器：

```text
Dense FFN:    y = FFN(x)                        # 激活全部参数
MoE 层:       y = sum_i g_i(x) * Expert_i(x)    # 只激活 top-k 个专家
```

DeepSeek-V3 的关键数字：

| 指标 | 数值 |
| ---- | ---- |
| 总参数 | 671B |
| 每 token 激活参数 | 约 37B |
| 路由专家数 | 256 |
| 共享专家数 | 1 |
| 每 token 路由 | top-8 |
| MoE 层数 | 58（前 3 层为 Dense） |

计算量按 37B 走，显存却要装 671B——这是典型的"显存与计算解耦"，也是本仓库反复强调的不可能三角里，MoE 选择牺牲的那一角换成了**通信**。

### 1.2 为什么必须 EP

回顾 Dense 模型的三板斧：

- **DP**：每张卡复制全部参数。671B 参数 + 优化器状态，单卡显然放不下，且复制 671B 毫无意义。
- **TP**：把每个专家内部切开。256 个专家每个都做 TP 会把专家切得很碎，TP 的 all-reduce 每层都要做，通信量爆炸（见 6.4 节）。
- **PP**：按层切。层数有限，切不出 256 份；且 PP 不解决单层内专家参数巨大的问题。

专家才是天然的切分粒度：**EP 把 256 个专家分到不同卡上，每卡只持有 256/EP 个专家**。token 在本地算完 attention 后，通过 all-to-all 被发送（dispatch）到持有目标专家的卡上，算完 FFN 再通过 all-to-all 送回来（combine）。

EP 的本质：用**数据移动**换**参数驻留**。参数不再动（每卡固定持有自己的专家），动的是 token（激活）。MoE 训练的核心矛盾由此从显存转为通信。

## 2. 核心原理

### 2.1 EP 的数据流

以 EP=8、256 个专家为例，每卡持有 32 个专家：

```text
每张卡（一个 EP rank）:
  1. 本地 token 经过 attention，得到 hidden states
  2. Router 计算每个 token 的 top-8 专家编号
  3. dispatch (all-to-all): 按目标专家所在 rank 打包发送 token
  4. 本地专家计算: 对收到的 token 做 FFN
  5. combine (all-to-all): 把结果按原路送回 token 所属的 rank
  6. 按路由权重加权求和，进入下一层
```

注意一个 token 要发 8 份（top-8），dispatch 时通常按"token × 选中专家"展开成消息。

### 2.2 all-to-all 通信分析

每个 MoE 层有 dispatch 和 combine **两次** all-to-all。单卡单层通信量近似：

$$
V \approx 2 \times T_{local} \times k \times H \times \text{bytes}
$$

其中 $T_{local}$ 是本卡 token 数，$k$ 是 top-k（DeepSeek-V3 为 8），$H$ 是 hidden size（7168），bytes 取 2（BF16）。在讨论量级时常把 k 折叠进"有效路由 token 数"，简记为 $2 \times T \times H \times \text{bytes}$。

all-to-all 为什么是第一杀手：

1. **不规则、全员参与**：每个 rank 向组内所有其他 rank 发送大小不等的消息，消息大小由路由结果动态决定，无法像 all-reduce 那样用规整的 ring/tree 算法摊平。
2. **对拓扑极敏感**：NVLink 域内（如 H100 NVLink4，单卡约 900 GB/s 双向带宽）和跨节点 RDMA（IB 400Gbps 网卡折算单卡约 50 GB/s）有**约 18 倍**的带宽差。EP 组一旦跨节点，同一份通信量的耗时立刻放大一个数量级以上。
3. **随 EP size 增长不下降**：EP 越大，每卡专家越少、显存越省，但通信域越大、落在慢速链路上的字节比例越高。EP size 是显存与通信的直接对赌。

用配套脚本量化（取每卡 8192 token、top-8、H=7168、BF16）：

| EP size | 通信域 | 有效带宽 | 单层 all-to-all 耗时 | 单层计算耗时（参考） | 通信占比 |
| ------- | ------ | -------- | -------------------- | -------------------- | -------- |
| 8 | 节点内 NVLink | 约 900 GB/s | 约 2 ms | 约 29 ms | 约 7% |
| 64 | 跨节点 IB | 约 50 GB/s | 约 38 ms | 约 29 ms | 约 130% |
| 256 | 跨节点 IB | 约 50 GB/s | 约 38 ms（同量级） | 约 29 ms | 约 130% |

结论：EP 组最好收敛在 NVLink 域内（EP<=8，即一机 8 卡）；一旦跨节点，all-to-all 就会反超计算，必须把通信和计算重叠起来才有救——这正是 DualPipe 和 DeepEP 存在的理由。

### 2.3 负载均衡：MoE 的训练特有难题

路由是学出来的，天然有马太效应：热门专家越热，梯度越多，变得更强。负载不均的直接后果是通信和计算都由最热的专家决定（木桶效应），以及 token drop。

**手段一：auxiliary loss（辅助负载均衡损失）**

Switch Transformer 的经典做法：给路由加一个辅助损失，惩罚负载偏离均匀分布，与主任务损失加权相加。

- 优点：简单有效，直接作用在路由概率上。
- 缺点：辅助 loss 与主任务目标并不一致，权重调大了**损害主任务精度**，调小了均衡不住。这是拿模型质量换系统效率。

**手段二：aux-loss-free（无辅助损失均衡）**

DeepSeek-V3 的做法：不加 loss，而是给每个专家的路由打分加一个**可动态调整的 bias 项**——只影响选谁，不影响权重值。每步统计各专家负载，过载专家 bias 调低、欠载调高。路由分数本身仍由主任务损失训练。

- 优点：不污染主任务目标，均衡效果稳定。
- 缺点：需要在线统计与调节逻辑，工程复杂度转移到训练框架里。

**手段三：capacity factor（容量因子）**

硬性限制每个专家每步最多处理 $C = \text{capacity factor} \times \frac{T \times k}{E}$ 个 token，超出的直接丢弃（token drop），该位置用残差连接兜底。

- capacity factor 通常取 1.0-2.0：越小通信和计算越省、越均匀，但 drop 越多。
- **token drop 有精度代价**：被丢的 token 这一层相当于没有 FFN，对训练后期和难样本影响明显。推理时通常设得更大甚至不丢。

### 2.4 训练框架与通信库

**Megatron-LM 的 EP**：在 3D 并行之外新增 EP 维度，EP 通信域从 DP 域中划分（同一 EP 组内的 rank 同时也是不同的 DP rank）。Attention 等非专家部分走原有 TP/DP，专家部分走 EP。Megatron 还提供 ETP（Expert Tensor Parallel，专家内部再做 TP）用于专家本身很大的场景。

**DeepEP**（DeepSeek 开源的 EP 通信库）：

- 提供专门的 dispatch/combine kernel，支持节点内 NVLink 与跨节点 RDMA 两种路径。
- 关键思想是**与计算 SM 隔离重叠**：用专门的 SM 处理通信、绕过 SM 争用，让 all-to-all 和专家计算真正并行，而不是串行排队。

**历史脉络**：GShard/Switch Transformer 奠定 top-k 路由与 aux loss 范式；Tutel（微软）较早把 all-to-all 优化做成系统库；DeepSeek-V3 把 aux-loss-free + DualPipe + DeepEP 组合成工业界标杆方案。

### 2.5 DualPipe：把 all-to-all 藏进计算里

普通 1F1B（见 6.5 节）的气泡来自流水线填充/排空；MoE 训练还多一类开销：每个 MoE 层的 all-to-all 如果与计算串行，GPU 要么算要么通信，总有一方闲着。

DualPipe（DeepSeek-V3 提出）的做法：

- **双向流水线**：从流水线两端同时喂 micro-batch，前向与反向的 micro-batch 在调度上精细交错，双向流水进一步压缩了首尾气泡。
- **计算-通信精细重叠**：把每个 micro-batch 的计算拆成 attention、dispatch all-to-all、专家 FFN、combine all-to-all 等阶段，编排成"一块 GPU 算 attention 时，另一块的 all-to-all 正在跑"，通信被完全藏进计算的空隙里。

效果对比（定性）：

| 方案 | 流水线气泡 | all-to-all 暴露时间 |
| ---- | ---------- | ------------------- |
| 1F1B | (P-1)/(M+P-1) | 全部暴露，串行等待 |
| DualPipe | 双向填充，气泡进一步减小 | 大部分被计算遮盖 |

代价是实现复杂度极高：调度器要同时管理双向 micro-batch 流和通信 kernel 的 SM 配额，这也是 DualPipe 至今主要在 DeepSeek 体系内落地的原因。

## 3. 计算/通信/显存 tradeoff 分析

MoE 训练的每个旋钮都在三角上挪动：

| 旋钮 | 显存 | 通信 | 计算/精度 |
| ---- | ---- | ---- | --------- |
| EP size 增大 | 每卡专家减少，显存省 | all-to-all 域变大，跨节点字节增多 | 负载均衡更难 |
| top-k 增大 | 不变 | 通信量线性增大 | 模型能力增强，计算量增大 |
| capacity factor 减小 | 激活峰值降低 | 通信上界收紧 | token drop 增多，精度受损 |
| aux loss 权重增大 | 不变 | 负载更均衡、通信更均匀 | 主任务精度受损 |
| 通信计算重叠（DualPipe/DeepEP） | 调度 buffer 增加 | 暴露时间减少 | 实现复杂度上升 |
| ETP（专家内 TP） | 专家进一步切分 | 额外 all-reduce | 仅超大专家时划算 |

核心规律：**MoE 把显存压力换成了通信压力，再用调度与均衡算法把通信压力换成工程复杂度**。

## 4. 对比表格

### 4.1 MoE 层的并行方式对比

| 维度 | TP 切专家内部 | EP 按专家切 | ETP（EP+专家内TP） |
| ---- | ------------- | ----------- | ------------------ |
| 切分粒度 | 矩阵维度 | 整个专家 | 专家再切矩阵 |
| 通信原语 | all-reduce（每层频繁） | all-to-all（每层两次） | 两者都有 |
| 通信拓扑要求 | 高（但规整） | 极高（不规则） | 最高 |
| 适用场景 | 专家少而大 | 专家多而小（主流） | 超大专家 |
| 代表 | 早期 MoE | DeepSeek-V3、Mixtral 训练 | Megatron ETP |

### 4.2 负载均衡方案对比

| 方案 | 机制 | 对主任务影响 | 代表 |
| ---- | ---- | ------------ | ---- |
| auxiliary loss | 加辅助损失项 | 有损，权重要精调 | Switch Transformer |
| aux-loss-free bias | 调路由偏置不改权重 | 基本无损 | DeepSeek-V3 |
| capacity factor + drop | 硬上限丢弃 | drop 有损 | 各框架通用兜底 |

## 5. 工程实践

### 5.1 EP 与其他并行的组合拓扑

常见原则：**TP=1 或小 TP + 大 EP**。

- 专家本身（如 DeepSeek-V3 每专家约 2048  intermediate 维度）足够小，不需要再 TP 切碎；TP 引入的 all-reduce 与 all-to-all 叠加只会恶化通信。
- 通信域正交设计：EP 组从 DP 域内划分，TP 组限制在节点内，PP 跨节点（stage 间通信量小、对带宽不敏感）。DeepSeek-V3 训练的典型形态即 PP 跨节点、EP 尽量收敛在 NVLink 域内、DP 铺满其余维度。
- Attention 部分仍可用小 TP + SP，专家部分 TP=1，两部分在同一组卡上各自组织通信域。

### 5.2 动手实验

代码文件：`6.9_MoE训练与专家并行/ep_alltoall_estimator.py`

```bash
cd /data/liyangyang/ai_infra/06_分布式训练
/data/qwen35_env/bin/python 6.9_MoE训练与专家并行/ep_alltoall_estimator.py
```

脚本做两件事：

1. 估算 EP=8/64/256 下单层 MoE 的 all-to-all 通信量与耗时，区分 NVLink 域内（900 GB/s）与跨节点 IB（50 GB/s），与一层计算时间对比给出通信占比。
2. 模拟随机均匀路由下专家负载不均程度（max/mean）随 token 总数的变化，直观看到"token 越多越均衡"，理解为什么大 batch 对 MoE 友好。

### 实验建议

- 把每卡 token 数减半，观察通信占比变化（通信与计算同比例缩小，但占比不变——想想为什么）。
- 把带宽改成 25 GB/s（模拟拥塞的 IB），看 EP=64 时通信占比恶化到什么程度。
- 修改路由模拟为非均匀分布（如 Zipf），观察 max/mean 如何恶化，理解 aux-loss-free 的必要性。

## 6. 常见误区

### 6.1 "EP 越大越好，显存最省"

EP 越大通信域越大，跨节点字节占比越高。显存省下来的收益很快被 all-to-all 耗时吃掉。EP size 由 NVLink 域大小和负载均衡能力共同决定。

### 6.2 "auxiliary loss 是标准答案"

aux loss 直接损害主任务。DeepSeek-V3 之后，aux-loss-free 成为大模型 MoE 的主流方向，aux loss 更多作为小尺度实验的基线。

### 6.3 "all-to-all 和其他通信一样，重叠一下就行"

all-to-all 的消息大小由路由动态决定、全员参与、对拓扑敏感，是所有集合通信里最难优化的。DualPipe/DeepEP 级别的精细重叠是顶级工程，不是调个 flag。

### 6.4 "capacity factor 设 1.0 最省"

capacity factor=1.0 意味着任何负载波动都会 drop token。实践中取 1.0-2.0，训练前期可以激进、后期放松，推理时通常不 drop。

## 7. 面试高频问题

**Q1：MoE 为什么一定要 EP，能不能只用 TP/PP/DP？**

一句话：专家总参数太大单卡放不下，专家是天然切分粒度，TP 会把 256 个专家切碎导致 all-reduce 爆炸，DP 复制 671B 没有意义，PP 切不出足够的份数。

展开：MoE 的本质是显存与计算解耦——参数 671B、激活 37B。显存必须按 671B 切分，而切分的自然单位是专家本身。EP 让参数驻留、token 移动，代价是每层两次 all-to-all。TP 适用于"单层参数大但数量少"，MoE 恰好相反（专家多但每个不大），所以主流是 TP=1 + 大 EP。

**Q2：一次 MoE 层有多少通信量？怎么估？**

一句话：dispatch + combine 两次 all-to-all，单卡约 2 x tokens x top-k x hidden x 2 字节（BF16），讨论量级时简记 2 x T x H x bytes。

展开：以每卡 8192 token、top-8、H=7168 估算约 1.9 GB。节点内 NVLink（约 900 GB/s）只需约 2 ms，可忽略；跨节点 IB（约 50 GB/s）需要约 38 ms，反超单层计算时间（约 29 ms）。所以 EP 组是否跨节点是 MoE 训练性能的分水岭。

**Q3：all-to-all 为什么比 all-reduce 难优化？**

一句话：all-reduce 消息规整可用 ring/tree 摊平，all-to-all 消息大小由路由动态决定、全员互发、对拓扑极敏感。

展开：ring all-reduce 通信量与 rank 数无关（见 6.8 节），all-to-all 每个 rank 都要和组内所有 rank 交换不等长消息，拥塞由最热链路和最热专家共同决定，还会和负载不均叠加放大。

**Q4：负载均衡有哪些办法，DeepSeek-V3 怎么做的？**

一句话：三条路——auxiliary loss（Switch Transformer，损主任务）、aux-loss-free bias（DeepSeek-V3，只调路由偏置不加 loss）、capacity factor（硬上限 + token drop）。

展开：aux loss 是拿模型质量换系统效率；aux-loss-free 给路由分数加动态 bias，过载调低欠载调高，不影响梯度路径；capacity factor 取 1.0-2.0 兜底，超出即 drop，被 drop 的 token 该层走残差直连，有精度代价。

**Q5：DualPipe 比普通 1F1B 好在哪里？**

一句话：双向流水进一步压缩气泡，并且把每个 MoE 层的 all-to-all 与计算精细交错，通信几乎完全被计算遮盖。

展开：1F1B 只解决流水线填充/排空气泡，MoE 的 all-to-all 仍串行暴露。DualPipe 从两端同时灌 micro-batch，把 attention 计算与 dispatch/combine 通信在单卡时间线上交错排布，配合 DeepEP 的 SM 隔离实现真重叠。代价是调度复杂度极高。

**Q6：为什么 MoE 训练常用 TP=1 + 大 EP？**

一句话：单个专家很小不需要切，TP 的 all-reduce 与 all-to-all 叠加只会恶化通信。

展开：DeepSeek-V3 的专家 intermediate 维度约 2048，单专家参数小，EP 已解决显存问题。TP 会引入每层高频 all-reduce，且把专家切碎后与 EP 通信域交叉，通信拓扑复杂度失控。正确姿势是 EP 收敛在 NVLink 域内，PP 跨节点，DP 铺满，各通信域正交。

## 8. 本节小结

1. MoE 用稀疏激活解耦了显存与计算，代价是把压力转移给通信：EP 按专家切分参数，token 靠 all-to-all 路由。
2. 每个 MoE 层有 dispatch/combine 两次 all-to-all，通信量约 2 x T x H x bytes 量级；all-to-all 不规则、全员参与、对拓扑极敏感，是 MoE 训练的第一杀手。EP 跨节点（NVLink 900 GB/s 掉到 IB 50 GB/s）通信立即反超计算。
3. 负载均衡三条路：auxiliary loss 有损主任务、aux-loss-free bias 是 DeepSeek-V3 的主流方案、capacity factor + token drop 兜底但有精度代价。
4. 工程上靠 Megatron-LM 的 EP 维度、DeepEP 的通信 kernel 与 SM 隔离、DualPipe 的计算通信精细重叠三件套把 all-to-all 藏起来。
5. 组合拓扑的核心原则：小 TP（常为 1）+ 大 EP，EP 收敛在 NVLink 域内，各通信域正交设计。
