# 14.6 系统设计与开放题

> 共 15 题。系统设计题的评分标准是：先澄清需求 → 定量估算 → 架构分层 → 权衡取舍 → 落地方案。每题给出参考思路框架而非唯一答案。

---

### Q1：设计一个支持 10 万并发的 LLM 在线推理平台。

**参考框架**：
1. **澄清**：模型规模？输入输出长度分布？SLO（TTFT/TPOT）？——假设 70B 级、平均 2k 输入/500 输出、TTFT<2s、TPOT<50ms。
2. **估算**：单实例 goodput（需实测，假设每实例 50 并发）→ 需约 2000 实例；70B FP8 每实例 2 卡 → 4000 卡级集群。
3. **分层**：网关层（鉴权/限流/前缀亲和路由）→ 调度层（实例选择、SLO 感知）→ 引擎层（vLLM/SGLang）→ 基础设施（K8s + GPU 调度，可参考 llm-d 架构）。
4. **取舍**：PD 分离 vs 混部（看长上下文占比）；多副本 vs 大实例（故障域与利用率）。
5. **落地**：先单实例压测定 goodput → 小集群验证调度 → 灰度放量；全链路 TTFT/TPOT 按租户埋点。

**考察点**：定量估算能力、分层思维、SLO 意识。

### Q2：设计万卡训练集群的容错系统。

**参考框架**：
1. **故障模型**：等效 MTBF 小时级（每天多次中断）；故障谱——GPU ECC/XID、NVLink、网卡、节点宕机、慢节点、软件 hang（6.10 章）。
2. **检测**：心跳 + NCCL 超时（发现"死了"）+ 应用层 step time 分位监控（发现"慢了"）+ 训练前 nccl-tests 预检。
3. **恢复**：异步 checkpoint（分钟级间隔、内存快照后台落盘）+ 热备节点自动替换 + 通信组快速重建；参考 FlashRecovery 的"规模无关重启 + 单步内恢复"（12.2 论文）。
4. **指标**：goodput（有效训练时间占比）是北极星指标，目标 >90%。

**考察点**：对"故障是常态"的认知、checkpoint 成本建模、慢节点治理。

### Q3：给你一个业务：每天 1 亿条长文档问答（平均输入 50k，输出 200），设计推理方案。

**参考框架**：
1. **特征提取**：输入极长输出极短 → prefill 主导；文档被多次提问 → 前缀复用率高。
2. **核心技术选型**：prefix cache 是第一杠杆（命中即省 prefill）；PD 分离（prefill 重负载独立扩容）；KV 分层 offload（Mooncake 模式）；长上下文模型选型（MLA/线性架构降低 KV 体积）。
3. **估算**：离线/准在线负载可削峰填谷（夜间批处理）；按"每文档 prefill 一次 + 复用 N 次"算成本模型。
4. **验证**：A/B 看 prefix 命中率对成本的弹性。

**考察点**：从业务特征反推技术选型（而不是背技术清单）。

### Q4：设计一套 GPU 集群的利用率提升方案。

**参考框架**：
1. **先度量**：分团队/任务的分配率与真实利用率双层看板、卡时账单（showback）；找到浪费类型（僵尸任务、碎片、波谷空闲）。
2. **再治理**：碎片——拓扑感知 bin-packing + 规格治理；波谷——在线离线混部（训练填谷、可抢占）；僵尸——自动检测回收。
3. **配套能力**：弹性训练（6.10）是混部前提；gang scheduling（9.6）防死锁。
4. **目标**：业界平均利用率 <50%，合理目标 60-70%（留 SLO 余量）。

**考察点**：平台思维（度量先行）、混部的前提条件。

### Q5：设计端侧（车端）多模型共存的推理系统。

**参考框架**：
1. **约束**：硬实时（控制频率）、显存/算力封顶、功耗墙、功能安全。
2. **设计**：安全关键模型 pinned 常驻 + 大模型按需加载；内存准入控制（新任务申请显存时评估拒绝/降级）；静态 shape + TensorRT；降级策略预案（5.10 章 edge_colocated_scheduler.py 模拟的正是这个）。
3. **验证**：最差情况（全负载同时激活）的延迟预算表，而不是平均情况。

**考察点**：硬实时思维 vs 云端 SLO 思维的差异、降级设计。

### Q6：如何评估"要不要自研推理引擎"？

**参考框架**：
1. **先算账**：自研的成本（3-5 人年起步 + 持续跟进上游）vs 收益（性能超出 vLLM/SGLang 多少、业务定制多深）。
2. **默认答案**：绝大多数团队不该自研——基于 vLLM/SGLang 二次开发（插件、自定义算子、调度策略）覆盖 90% 需求。
3. **该自研的信号**：硬件是自研芯片（生态没有支持）、业务模型结构极端特殊（如自动驾驶的 BEV 小模型群）、规模大到 5% 性能 = 千万级成本。
4. **折中方案**：向开源贡献特性（上游化）而非维护私有 fork。

**考察点**：工程决策的成本意识。

### Q7：设计跨地域多机房的推理服务（容灾 + 就近接入）。

**参考框架**：
1. **分层**：全局流量调度（DNS/Anycast 就近接入）→ 区域内集群自治（完整服务能力）→ 模型分发（多机房镜像与版本一致性）。
2. **容灾**：单机房故障时流量切换（容量预留 N+1）；KV/prefix cache 不跨地域（状态局部性）。
3. **成本**：就近接入省的是网络延迟，跨地域调度的代价是命中率下降（prefix cache 局部性）——取舍点。
4. **SLO**：分地域独立考核 TTFT/TPOT。

**考察点**：状态（KV cache）对全局调度的约束——这是 LLM serving 区别于传统无状态服务的关键。

### Q8：老板问"为什么我们的 GPU 这么贵，能不能省"，你怎么系统性回答？

**参考框架**：
1. **拆解成本**：模型推理成本 = 卡时 ×（权重读取 + KV 管理 + 调度损耗）/ 有效 token；先给数字画像（利用率多少、goodput 多少、单位 token 成本）。
2. **优化菜单按 ROI 排序**：利用率（混部/调度，往往最大头）→ 量化（FP8/INT4）→ 引擎升级（CB/投机解码）→ 架构层（更小的激活参数、prefix 复用）→ 采购层（选型/租买）。
3. **反面**：不要跳过度量直接买更多卡。

**考察点**：把技术能力翻译成成本语言（管理层沟通）。

### Q9：设计一个支持"训练-推理一体化"的 RL 后训练平台。

**参考框架**：
1. **负载特征**：rollout（推理）与训练交替、权重频繁同步、环境交互（agentic）。
2. **架构选型**：verl 类 colocate（省机器）vs 训推分离（简单但利用率低）——给出判断条件（模型规模、rollout 占比）。
3. **关键组件**：rollout 引擎池（vLLM/SGLang）+ 训练后端（FSDP/Megatron）+ 权重同步通道（resharding + NCCL 广播）+ 环境服务池（agentic 场景）+ 样本缓冲区（异步化）。
4. **演进路径**：同步 → 流水线化 → 全异步（AReaL 思路），按团队成熟度逐级演进。

**考察点**：对 6.11 章知识的系统化运用、架构演进思维。

### Q10：如何设计大模型推理的灰度发布与回滚？

**参考框架**：
1. **版本对象**：引擎版本、模型权重、配置（量化档位/调度参数）三者独立版本化。
2. **灰度**：按实例 → 按流量比例 → 按租户分阶段；金丝雀实例带完整 SLO 监控。
3. **回滚**：权重与引擎解耦使回滚=切流量+换回镜像；CUDA Graph 预热是切换延迟的关键（先预热再接流）。
4. **验证门禁**：性能回归（9.2 章）+ 精度回归（固定评测集）双门禁。

**考察点**：发布工程、性能与精度双维度回归意识。

### Q11：让你把 DeepSeek-R1（671B）部署到公司内网，给你 64 张 H800，出方案。

**参考框架**：
1. **算账**：FP8 权重约 671GB；64×80GB=5.1TB 总显存，权重占 13%，余量给 KV cache 与激活——容量可行。
2. **并行策略**：EP=64（跨 8 机）+ DP attention；all-to-all 走 IB；或用官方推荐的大 EP 配置（DeepEP low-latency 模式）。
3. **结构**：prefill/decode 分离（如 16 卡 prefill + 48 卡 decode，按负载比例调），前缀 cache 开启。
4. **风险**：跨节点 EP 对 IB 网络质量敏感；先小规模（8/16 卡）验证再全量。

**考察点**：容量估算 + MoE 部署知识 + 分阶段验证的工程素养。

### Q12：设计一个 AI Infra 的性能回归防护体系（CI 层面）。

**参考框架**：
1. **三层**：单元级（kernel benchmark，μs 级，每次提交跑）→ 模型级（端到端延迟/吞吐，每日跑）→ 集群级（多卡扩展性，每周跑）。
2. **门禁**：基线 + 容差（考虑机器噪声，用多次中位数）；退化自动 git bisect 定位提交（9.2 章 regression_gate.py / git_bisect_helper.py）。
3. **稳定性**：固定机器池 + 独占模式跑 benchmark，避免噪声淹没信号。
4. **数据沉淀**：所有 benchmark 结果入库，可视化趋势（9.2/9.3 章）。

**考察点**：质量体系的层次与噪声处理。

### Q13：如何向一个不懂技术的负责人解释"PD 分离"的价值？

**参考框架**：
1. **类比**：餐厅把"备菜"（prefill）和"上菜"（decode）分成两个工种——一个师傅同时备菜又上菜时，来一个大单（长文档）所有桌子的上菜都卡住。
2. **量化语言**：分开后，同等硬件下可服务的客户数提升 X（引用 DistServe/llm-d 的数字口径），或同等客户数下响应更快。
3. **代价诚实说**：系统更复杂、多一份数据传输成本；短请求场景收益小。

**考察点**：技术翻译能力——AI Infra 工程师向上沟通的必备技能。

### Q14：设计端云协同的推理架构（隐私敏感场景）。

**参考框架**：
1. **分流原则**：隐私数据与简单请求端侧处理（小模型），复杂请求脱敏后上云（大模型）。
2. **端侧**：量化小模型（INT4/INT8）+ 固定延迟预算（见 5.10 章）。
3. **云侧**：承接复杂请求；注意端云延迟差（网络 RTT）对体验的影响，流式输出掩盖。
4. **一致性**：端云模型能力差异导致回答质量跳变——需要路由策略让用户无感（如置信度门控）。

**考察点**：隐私约束下的架构分层、体验一致性。

### Q15：开放讨论：推理系统的"下一个数量级提升"可能来自哪里？

**参考框架**（言之成理即可，考察视野）：
- 架构层：线性/混合注意力（KV 与长度解耦，Kimi Linear/SALA 路线）——若成熟，长上下文成本结构重写。
- 硬件层：FP4 普及 + NVL72 级 scale-up——单位算力成本再砍半。
- 系统层：编排层智能（llm-d 方向）——把现有硬件的利用率从 50% 拉到 80% 等于"白捡"半个数量级。
- 算法-系统协同：投机解码、稀疏化的进一步融合。
- 给出自己的排序并说理由——面试官看的是判断力而非标准答案。

**考察点**：技术视野、判断力的表达。
