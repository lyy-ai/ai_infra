# 14.1 CUDA 与算子题

> 共 30 题。公司画像缩写：**LLM**=大模型公司（DeepSeek/月之暗面/智谱/Qwen/字节Seed 等）、**芯片**=芯片厂（NVIDIA/昇腾/地平线等）、**云**=云厂商与平台团队、**车**=自动驾驶/具身智能。

---

### Q1：解释一下 warp divergence，什么时候会发生？

- 画像：全部；难度：基础
- 一句话：同一 warp 内 32 个线程走到不同分支时，硬件只能串行执行各分支路径（各分支都要执行一遍，不活跃的线程被屏蔽），导致利用率下降。
- 展开：发生在 if-else、循环次数不一致、按 threadIdx 取模分配任务等场景；SIMT 执行模型决定了一个 warp 同一时刻只有一条指令流；优化手段包括重排数据让同 warp 线程走同分支、用掩码代替分支、把分支粒度提到 block 级。
- 追问：warp divergence 一定有害吗？——不一定，如果分支很短或一边几乎不走，开销可忽略；关键看两条路径的长度差。

### Q2：什么是 bank conflict？怎么避免？

- 画像：全部；难度：基础
- 一句话：shared memory 按 32 个 bank 组织，同一 warp 的多个线程同时访问同一 bank 的不同地址时访问被串行化，带宽降为 1/N。
- 展开：广播（多线程读同一地址）不算冲突；经典场景是按列访问二维数组（stride=32 的倍数）；解决办法是 padding（每行加 1 个元素错开 bank）或调整访问模式。
- 追问：A100 上一个 bank 每周期能提供多少字节？——4 字节；32 bank 共 128 字节/周期/SM。

### Q3：如何保证 global memory 的合并访存（coalesced access）？

- 画像：全部；难度：基础
- 一句话：让同一 warp 的 32 个线程访问连续对齐的 32 个地址（128 字节对齐段），一次访存事务完成；否则被拆成多个事务，带宽利用率暴跌。
- 展开：AoS vs SoA 布局差异（struct of array 利于合并）；stride 访问的代价可以实测（本仓库 2.2 章 `coalesced_vs_stride.cu`）；非对齐访问在现代架构有部分缓解但仍要尽量避免。
- 追问：half2/float4 向量化加载和合并访存是什么关系？——向量化让每个线程一次取更多连续字节，与合并访存正交，通常叠加使用。

### Q4：手写一个 Softmax 的 CUDA kernel，你会考虑哪些点？

- 画像：全部；难度：进阶
- 一句话：核心是数值稳定（减最大值）+ 高效归约（warp shuffle + shared memory 多级归约）。
- 展开：三遍法（求 max → 求 exp 和 → 归一化）可以融合成两遍（online softmax：同时维护 running max 和 running sum）；一行一个 block，行内线程归约；大维度用 float4 向量化加载；小维度考虑一个 warp 处理多行。
- 追问：online softmax 的数学依据？——e^(x - m_new) = e^(x - m_old) × e^(m_old - m_new)，可以增量修正已累积的 sum。

### Q5：GEMM 优化的层次有哪些？从 naive 到 Tensor Core。

- 画像：芯片、LLM；难度：进阶
- 一句话：naive → shared memory tiling → 寄存器分块 → 向量化加载 → double buffering 流水线 → Tensor Core（WMMA/MMA）→ 软件流水线与 warp specialization。
- 展开：核心是提升算术强度（FLOPs/字节）：tiling 让数据复用发生在 shared memory 和寄存器；block 尺寸选择是 occupancy 与复用度的权衡；本仓库 CudaGemmProject 有四级实现与 A100 实测数据（tiled_vec4 达 cuBLAS FP32 的约 72%）。
- 追问：为什么 Tensor Core 版本的 shared memory 布局和 fp32 版不同？——MMA 指令对 fragment 的布局有特定要求（ldmatrix 需要特定的 swizzle 来避免 bank conflict）。

### Q6：解释一下 Roofline 模型，怎么用它判断优化方向？

- 画像：全部；难度：基础
- 一句话：性能上限 = min(峰值算力, 带宽 × 算术强度)；先算 kernel 的算术强度（FLOPs/访存字节），落在带宽区就优化访存，落在算力区就优化计算。
- 展开：LLM decode 的 GEMV 算术强度极低（约 2 FLOPs/字节）所以是 memory-bound，量化降精度本质是降字节数；prefill 的 GEMM 在 batch 大时 compute-bound。本仓库 2.8 章 `roofline_calc.py` 可动手算。
- 追问：H100 的拐点算术强度大约多少？——FP16 算力约 989 TFLOPS、带宽 3.35 TB/s，拐点约 295 FLOPs/字节。

### Q7：CUDA Stream 和 Event 的作用？多流并发的坑有哪些？

- 画像：LLM、车；难度：进阶
- 一句话：Stream 是异步任务队列，同流内串行、跨流可并发；Event 用于跨流同步和计时。
- 展开：多流可实现计算-通信/计算-拷贝重叠；坑包括：默认流（legacy stream）的隐式同步会杀掉并发、stream 间资源竞争、kernel 启动顺序与依赖没管理好导致竞态、事件计时必须等事件完成再读。
- 追问：怎么验证多流真的并发了？——nsys timeline 看 kernel 时间重叠，而不是只看总耗时。

### Q8：Occupancy 是什么？是不是越高越好？

- 画像：芯片、LLM；难度：基础
- 一句话：Occupancy = SM 上常驻活跃 warp 数 / 最大支持 warp 数，受寄存器、shared memory、block 尺寸限制；不是越高越好。
- 展开：memory-bound kernel 需要高 occupancy 来隐藏访存延迟；但 register-heavy 的计算 kernel（如大寄存器分块 GEMM）主动牺牲 occupancy 换数据复用；看 ncu 的 achieved occupancy 而非理论值。
- 追问：怎么提高 occupancy？——减每线程寄存器（__launch_bounds__）、减 shared memory 用量、调 block 尺寸。

### Q9：FlashAttention 为什么快？核心思想是什么？

- 画像：全部；难度：进阶（高频必考）
- 一句话：IO 感知——通过分块计算 + online softmax，不把 N×N 注意力矩阵写回 HBM，把 attention 从 memory-bound 拉到接近 compute-bound。
- 展开：标准实现写回 N×N 中间矩阵，访存量 O(N²)；FA 在 SRAM 里分块完成 QK^T→softmax→PV，访存量降为 O(N)；online softmax 让分块结果可增量合并；代价是反向传播要重算（recomputation），用计算换显存/带宽。
- 追问：FA2 比 FA1 改了什么？——减少非 GEMM 开销（更好的 warp 划分）、Q 在外层循环、序列维并行；FA3 则用 Hopper 的 TMA + warp specialization + FP8（见 2.10 章）。

### Q10：ncu 和 nsys 的分工？你分析性能瓶颈的流程？

- 画像：全部；难度：基础
- 一句话：nsys 看时间线（调度、通信、kernel 间隙），ncu 看单个 kernel 内部（SM 利用率、访存、stall 原因）。
- 展开：流程——nsys 先看宏观（GPU 空闲？启动开销？通信占比？）→ 找到热点 kernel → ncu 看 SOL 部分（SM/Memory 哪个更接近上限）→ 按 stall reason（long scoreboard = 等访存等）定位 → 迭代。
- 追问：kernel 时间很短但占比高，可能是哪类问题？——launch overhead 或 kernel 间隙，考虑 CUDA Graph 或算子融合。

### Q11：CUDA Graph 解决什么问题？什么场景不能用？

- 画像：LLM、车；难度：进阶
- 一句话：把一串 kernel 调用录制为图一次提交，消除 CPU 侧启动开销；decode 这种小 kernel 高频场景收益最大（vLLM 用它加速 decode）。
- 展开：启动开销约 3-10μs/个，decode 一步几十个 kernel 时 CPU 提交成为瓶颈；要求形状静态——batch size、序列布局变化就得重新捕获或 padding 到固定档位。
- 追问：vLLM 怎么处理动态 batch 与 CUDA Graph 的矛盾？——按 batch 档位捕获多个图，运行时向上取整 padding。

### Q12：shared memory 和寄存器的容量与带宽量级？A100 为例。

- 画像：芯片；难度：基础
- 一句话：A100 每 SM 有 192KB 可配置 shared memory/L1、64K 个 32-bit 寄存器（256KB），shared memory 带宽约 20+ TB/s 量级，远高于 HBM 的 1.6 TB/s。
- 展开：存储层次：寄存器（最快，线程私有）→ shared memory（block 共享）→ L2 → HBM；越靠近算力越快越小；GEMM 优化的本质就是把数据尽量压进上两层。
- 追问：shared memory 配大了会怎样？——挤占 L1 cache 且降低 occupancy（每 SM 能驻留的 block 变少）。

### Q13：atomicAdd 的代价？Reduce 为什么最后用 warp shuffle？

- 画像：全部；难度：基础
- 一句话：原子操作串行化冲突地址的访问，高冲突时吞吐骤降；warp shuffle 在同 warp 内寄存器级交换数据，不经过 shared memory，无 bank conflict 无同步。
- 展开：Reduce 的演进：全局原子加 → shared memory 树形归约 → warp shuffle 归约（warp 内）→ 多级组合；本仓库 2.3 章 `reduce.cu` 有完整实现。
- 追问：跨 block 归约怎么办？——两级 kernel 或 cooperative groups 的 grid sync 或最后一级用原子加。

### Q14：__syncthreads 的开销与坑？

- 画像：芯片、车；难度：基础
- 一句话：block 内屏障同步，所有线程到达后才能继续；坑是分支内调用导致死锁（部分线程永远到不了屏障）。
- 展开：同步开销与 block 内 warp 数相关；现代 CUDA 提供 named barrier 和 cooperative groups 更细粒度；Hopper 的 warp specialization 用 mbarrier 替代了大部分显式 __syncthreads。
- 追问：__syncwarp 和 __syncthreads 的区别？——前者 warp 内同步（Volta 后独立线程调度需要），后者 block 级。

### Q15：L1/L2 cache 在 GPU 上的角色和 CPU 有什么不同？

- 画像：芯片；难度：进阶
- 一句话：GPU 的 L1 与 shared memory 共享物理空间且主要服务合并后的访存，程序员可控性弱；优化重点在显式管理 shared memory 而不是依赖 cache 命中。
- 展开：GPU 的 cache 更多用于平滑不规则访存和跨 SM 的 L2 共享；A100 L2 40MB 且支持 persistence 窗口（cudaAccessPolicyWindow）；persistent kernel + L2 驻留是热点技术。
- 追问：为什么 GPU 优化强调 shared memory 而 CPU 强调 cache 友好？——GPU 给程序员显式控制权（数据局部性可预测），CPU 依赖硬件预测。

### Q16：FP16/BF16 混合精度训练中梯度溢出怎么处理？

- 画像：全部；难度：基础
- 一句话：用 loss scaling——损失乘大系数让梯度进入 FP16 可表示区间，更新前再除回来；溢出（inf/nan）则跳过该 step 并降低 scale。
- 展开：动态 loss scaling 策略（增长/回退）；BF16 指数位与 FP32 相同（8 位）所以范围大不需要 scaling，但尾数只有 7 位精度低；master weight 保留 FP32 副本。
- 追问：为什么权重更新要留 FP32 master copy？——小梯度 × 小学习率的增量在 FP16 里会被舍入为零。

### Q17：怎么算一个 kernel 的理论加速上限（Amdahl 视角）？

- 画像：LLM、车；难度：基础
- 一句话：只优化占比 p 的部分，加速上限 = 1/(1-p)；先 profile 找占比最大的瓶颈再动手。
- 展开：kernel 层面同理——如果访存占 70%，把计算优化到极致也只有约 1.4 倍；这就是为什么先看 nsys 占比再选优化点。
- 追问：工程上 Amdahl 的常见误用？——忽略了优化后瓶颈转移（计算快了以后访存变成新瓶颈，需要重新分析）。

### Q18：GEMM 里 K 维很大时怎么处理（split-K）？

- 画像：芯片、LLM；难度：进阶
- 一句话：把 K 维切给多个 block 并行算部分和，最后做归约（原子加或二级 kernel），用额外归约开销换并行度。
- 展开：M、N 小而 K 大时（如 decode 的 GEMV 形态）grid 太小喂不饱 GPU，split-K 提升 SM 占用；cuBLAS 会自动选择 split-K 策略。
- 追问：split-K 为什么不适合默认开启？——多一次归约的显存写读，K 不大时得不偿失。

### Q19：Warp specialization 是什么？为什么 Hopper 上流行？

- 画像：LLM、芯片；难度：深入
- 一句话：block 内 warp 分工——生产者 warp 专职搬数据（TMA）、消费者 warp 专职计算，形成流水，替代传统"所有 warp 搬运-计算交替"的模式。
- 展开：Hopper 的 TMA 异步拷贝 + mbarrier 让生产者与消费者解耦；FA3、CUTLASS 3.x 的 pingpong/cooperative 调度都用它；效果是计算和搬运几乎完全重叠（本仓库 2.10 章 `warp_specialization_sim.py` 有定量模拟）。
- 追问：为什么 Ampere 时代不流行？——没有 TMA 和异步屏障，生产者角色的搬运本身就要占用大量计算资源，分工收益不明显。

### Q20：Triton 和手写 CUDA 怎么选？

- 画像：LLM；难度：进阶（2024 后高频）
- 一句话：融合类、shape 多变的 LLM 算子用 Triton（开发快、autotune）；极致性能或需要硬件新特性（TMA/warp specialization 级控制）的算子手写 CUDA/CUTLASS。
- 展开：Triton 通常达手写 80-95% 性能；torch.compile 的 Inductor 默认生成 Triton；vLLM/SGLang 的 fused kernel 大量用 Triton；决策器见本仓库 2.9 章 `triton_vs_cuda_decision.py`。
- 追问：Triton 做不了什么？——寄存器级精细控制、跨 block 协作（cluster）、复杂的 warp 级编舞。

### Q21：怎么排查一个"训练变慢了 20%"的问题？

- 画像：全部；难度：进阶（行为题+技术题混合）
- 一句话：分层二分——先确认是全局变慢还是部分 rank 变慢（慢节点），再按计算/通信/数据加载/I-O 分段计时定位。
- 展开：对比 profile（nsys trace 前后对比）；检查 NCCL 带宽是否退化（nccl-tests）；检查是否有节点降频/ECC 错误；数据侧看 dataloader 等待；本仓库 6.10 章有完整故障谱。
- 追问：为什么强调先看 rank 维度？——同步训练中一个慢节点拖全体，平均指标会掩盖它；看 p99/p50 比看 mean 重要。

### Q22：CUDA 里 float4 向量化加载的前提条件？

- 画像：芯片；难度：基础
- 一句话：地址必须 16 字节对齐，且访问的元素个数是 4 的倍数（或处理边界）。
- 展开：不满足对齐会报 misaligned address 错误；通常配合 reinterpret_cast；向量化把 4 次访存合成 1 次，提升带宽利用率。
- 追问：向量化一定能提速吗？——memory-bound 且原本已合并的 kernel 提升有限；主要收益在减少指令数和事务数。

### Q23：Persistent kernel（常驻 kernel）是什么？用在哪？

- 画像：芯片、LLM；难度：深入
- 一句话：kernel 启动后不退出，常驻 SM 上循环消费任务队列，消除重复启动与初始化开销。
- 展开：用于 decode 阶段的融合算子、NVSHMEM 类通信-计算融合；需要配合 cooperative launch 保证所有 block 同时驻留；坑是占用 SM 影响其他任务。
- 追问：和 CUDA Graph 的区别？——Graph 减少 CPU 提交开销，kernel 还是一个一个跑；persistent 是单个 kernel 内部循环，连 kernel 边界都消除了。

### Q24：多卡间通信的原语有哪些？allreduce 的带宽怎么估算？

- 画像：LLM、云；难度：进阶
- 一句话：broadcast/reduce/allgather/reduce-scatter/allreduce/all-to-all；ring allreduce 的每卡通信量 = 2×(N-1)/N × 数据量，时间 ≈ 通信量 / 有效带宽（busbw）。
- 展开：ring 适合大数据量（带宽最优），tree/recursive doubling 适合小数据量（延迟最优）；NCCL 自动选算法；实测用 nccl-tests 的 busbw 指标。
- 追问：all-to-all 为什么对网络更苛刻？——每对节点都要直接通信，不规则且全员参与， bisection bandwidth 成为瓶颈（MoE 训练的痛点，见 6.9 章）。

### Q25：写 kernel 时怎么处理边界（非整除的维度）？

- 画像：全部；难度：基础
- 一句话：guard if（边界判断）+ 尾部单独处理；向量化加载时对尾段退回标量路径。
- 展开：Triton 的 tl.load 带 mask 参数天然处理；手写 CUDA 要在 load/store 两端都 guard；边界处理错误是最常见的 correctness bug。
- 追问：怎么测试边界正确性？——专门构造非整除 shape 的单元测试，对齐/非对齐 × 大/小维度组合覆盖。

### Q26：介绍一下 cuBLAS/cuDNN 和手写 kernel 的关系，什么时候还要手写？

- 画像：LLM；难度：基础
- 一句话：标准稠密算子用库（cuBLAS 已接近峰值）；手写/自研的机会在"库里没有的融合模式"。
- 展开：cuBLASLt 支持 epilogue 融合（bias+activation）；手写场景：特定 shape 的极致优化、融合多个算子省中间显存、新硬件特性库还没跟上。
- 追问：面试被问"你写的 GEMM 和 cuBLAS 差多少"怎么答？——给具体数字与差距根因（本仓库 CudaGemmProject：tiled_vec4 达 cuBLAS FP32 约 72%，差距在软件流水线与寄存器调度深度）。

### Q27：GPU 的 Tensor Core 工作原理？为什么要求特定 shape？

- 画像：芯片；难度：进阶
- 一句话：Tensor Core 是矩阵乘加硬件单元，一条指令完成一个小矩阵块的 D=A×B+C（如 m16n8k16），要求输入按特定 fragment 布局喂入。
- 展开：从 WMMA API 到 PTX 的 mma.sync 再到 Hopper 的 wgmma；对齐与 fragment 布局要求来自硬件数据通路；fp16/bf16/int8/fp8/fp4 各代支持不同。
- 追问：wgmma 和 mma.sync 的区别？——wgmma（Hopper）是 warpgroup 级、异步、可直接从 shared memory 读操作数，省去了 ldmatrix 到寄存器的搬运。

### Q28：如何实现一个低延迟的 KV cache gather kernel（paged attention 的核心访存）？

- 画像：LLM；难度：深入
- 一句话：按 block table 间接寻址 gather KV page，关键是让 gather 尽量合并（page 内连续）+ 预取下一页地址掩盖延迟。
- 展开：FlashDecoding 思路——按 KV 维再切分并行后归并；vLLM/FlashInfer 的实现可参考；难点在 page 大小选择与 occupancy 平衡。
- 追问：page 选大还是选小？——大 page 合并好但显存碎片浪费大；小 page 反之；vLLM 默认 16 token/page 是平衡点。

### Q29：GPU 降频（throttling）怎么发现和处理？

- 画像：云、LLM；难度：进阶
- 一句话：nvidia-smi 看 clocks 与 throttle reasons（温度/功耗/ECC），dcgm 做集群级监控；处理包括改善散热、调功耗墙、摘除异常卡。
- 展开：训练任务对降频敏感（同步训练最慢卡决定全体速度）；thermal throttling 常因机房热点；SW power cap 是主动限功耗。
- 追问：降频和"慢节点"的关系？——持续轻微降频的节点就是 straggler 的来源之一（见 6.10 章）。

### Q30：给你一个 kernel，ncu 显示 SM busy 90% 但吞吐不高，可能什么原因？

- 画像：芯片、LLM；难度：深入
- 一句话：SM 忙 ≠ 有效产出高——可能是 warp divergence、低 ILP、过多同步、或做了无用功（padding 计算、重复计算）。
- 展开：看 issue 的指令构成（ALU vs FMA vs LSU）；看 executed instructions 与 useful work 的比例；看 achieved occupancy 与 stall 分布；SM busy 高但 IPC 低说明在空转。
- 追问：怎么区分"真忙"和"假忙"？——对比 achieved IPC 与该指令类型的理论峰值，以及用 roofline 算理论耗时与实际耗时之比。
