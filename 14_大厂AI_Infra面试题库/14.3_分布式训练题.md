# 14.3 分布式训练题

> 共 25 题。公司画像缩写：**LLM**=大模型公司、**芯片**=芯片厂、**云**=云厂商与平台团队。对应仓库第 6 章与 12.2/12.3 论文。

---

### Q1：DDP 的梯度同步是怎么做的？为什么比朴素 DP 快？

- 画像：全部；难度：基础
- 一句话：反向传播过程中按 bucket（默认 25MB）分桶做梯度 allreduce，通信与反向计算重叠，不等全部梯度算完。
- 展开：朴素 DP 等所有梯度算完再同步，通信完全暴露；DDP 的 bucketing + 重叠让通信藏在反向里；bucket 顺序按反向完成顺序动态调整。
- 追问：什么时候 DDP 的通信藏不住？——计算/通信比低时（小模型、慢网络、大梯度量），如本仓库 DistributedTrainProject 实测的 PCIe 双卡负收益案例。

### Q2：ZeRO 三个阶段分别切什么？通信代价如何？

- 画像：全部；难度：基础（必考）
- 一句话：ZeRO-1 切优化器状态、ZeRO-2 加切梯度、ZeRO-3 连参数也切；通信量递增（ZeRO-3 每层前向反向都要 all-gather 参数）。
- 展开：显存收益：混合精度下优化器状态是大头（Adam 的 m/v + master weight ≈ 参数的 12 字节/参数 × N）；ZeRO-3 显存最省但通信最多；FSDP 是 ZeRO-3 的 PyTorch 原生实现。
- 追问：ZeRO-Offload 是什么？——把优化器状态和梯度放到 CPU 内存，计算仍在 GPU；省显存但引入 PCIe 传输开销。

### Q3：Tensor Parallel 切分点在哪？为什么 MLP 和 Attention 的切法不同？

- 画像：LLM；难度：进阶（必考）
- 一句话：线性层按列/行交替切（column-parallel 后接 row-parallel），中间不用通信；MLP 切 hidden 维，Attention 切 head 维，每层两个 allreduce。
- 展开：column→row 组合使中间激活不用同步（g、f 两个恒等/通信算子对）；TP 通信量在激活上，随 batch×seq 线性增长，所以 TP 通常限在 NVLink 域内（8 卡）。
- 追问：为什么 TP 一般不跨节点？——每层两次 allreduce、通信频率太高，跨节点带宽扛不住。

### Q4：Pipeline Parallel 的气泡怎么算？1F1B 怎么降气泡？

- 画像：LLM；难度：进阶
- 一句话：气泡率 ≈ (p-1)/(m+p-1)，p 为 stage 数、m 为 microbatch 数；1F1B 通过交错调度让激活显存不随 microbatch 数爆炸，同时保持相同气泡率。
- 展开：GPipe 简单但显存峰值高（存所有 microbatch 的激活）；1F1B 尽早启动反向、释放激活；microbatch 数越大气泡越小但显存越大（tradeoff 见 6.5 章 bubble 计算器）。
- 追问：PP 的通信量比 TP 小得多，为什么？——PP 只在 stage 边界传激活（点对点、每层一次），TP 每层两次全员 allreduce。

### Q5：3D 并行怎么组合？给一个 70B 模型 512 卡设计并行策略。

- 画像：LLM；难度：进阶
- 一句话：典型配方 TP=8（机内 NVLink）× PP=4-8（跨节点）× DP=剩余；即 TP 吃机内带宽、PP 跨节点、DP 补满。
- 展开：先定 TP（NVLink 域大小）→ PP 数让每 stage 显存装得下（权重+激活）→ DP = 总卡数/(TP×PP)；70B FP16 权重 140GB + 优化器状态，单 stage 8 卡 TP 后每卡约 17.5GB 权重，宽裕。
- 追问：数据并行度是不是越大越好？——受 global batch 上限与收敛约束，DP 过大要么 batch 爆炸要么梯度累积失效。

### Q6：MFU 是什么？怎么算？多少算好？

- 画像：LLM、云；难度：基础
- 一句话：MFU = 实际有效 FLOPs / (卡数 × 峰值 FLOPS × 时间)；训练 Transformer 的有效 FLOPs ≈ 6 × 参数量 × token 数（前向 2N + 反向 4N）。
- 展开：单卡 H100 密集 FP16 约 989 TFLOPS；开源框架 30-40% 常见，优化好的 50%+，MegaScale 万卡 55.2%（见 12.2 论文）；activation checkpointing 会把分子变大（重算）所以口径要统一。
- 追问：MFU 掉了 5 个点，可能什么原因？——通信占比上升（规模扩大/网络抖动）、慢节点、数据加载瓶颈、kernel 退化。

### Q7：训练 7B 模型需要多少显存？（手算题）

- 画像：全部；难度：基础（必考手算）
- 一句话：混合精度 Adam 下，参数(14GB FP16+28GB FP32 master) + 梯度(14GB) + 优化器状态(56GB 的 m/v) ≈ 112GB 起，再加激活。
- 展开：口诀——每参数 16-18 字节（2 FP16 参数 + 4 FP32 master + 4 梯度FP32 + 8 Adam m/v）；激活显存取决于 batch/seq/是否开 checkpointing；所以 7B 全量微调单卡 80GB 不够，需要 ZeRO/FSDP。
- 追问： activation checkpointing 省多少？——只存层边界激活，中间激活反向时重算，激活显存降约一个数量级，代价约 30% 额外计算。

### Q8：MoE 训练的 all-to-all 通信怎么分析？

- 画像：LLM；难度：深入（2024 后高频）
- 一句话：每个 MoE 层有 dispatch 和 combine 两次 all-to-all，通信量 ≈ 2 × tokens × hidden × 字节数；EP 跨节点时 IB 带宽（约 50GB/s/卡）vs 层计算时间决定通信是否暴露。
- 展开：本仓库 6.9 章 `ep_alltoall_estimator.py` 可定量算；NVLink 域内（900GB/s）通常能藏住，跨节点藏不住就要 DualPipe 类重叠设计；负载不均会放大有效通信时间（等最慢专家）。
- 追问：DeepSeek-V3 怎么解？——DualPipe 双向流水把 all-to-all 藏进计算 + 细粒度 EP + aux-loss-free 均衡（见 12.2 论文）。

### Q9：负载均衡在 MoE 训练里为什么难？方案有哪些？

- 画像：LLM；难度：进阶
- 一句话：路由是学出来的且动态漂移，token 分布天然不均；方案有 auxiliary loss（有效但伤主任务）、capacity factor + token drop（控上限但丢信息）、aux-loss-free bias 调整（DeepSeek-V3 路线）。
- 展开：aux loss 系数是敏感超参（大了伤效果、小了不均衡）；expert 负载不均直接变成设备负载不均（有人等最忙的卡）。
- 追问：capacity factor 怎么选？——训练常取 1.0-2.0，越小越省算力但 drop 越多；推理场景另有冗余专家等工程手段（见 5.11 章）。

### Q10：万卡训练的故障率怎么估？容错怎么做？

- 画像：LLM、云；难度：进阶
- 一句话：万卡集群各类硬件/软件故障叠加后等效 MTBF 只有小时级（每天多次中断），容错是必修课：健康预检 + 秒级检测 + 异步 checkpoint + 快速重启 + 慢节点治理。
- 展开：checkpoint 频率的取舍——同步写阻塞训练，异步快照到内存再后台写盘几乎无感；故障损失 = 上次 ckpt 后的进度 + 重启时间；本仓库 6.10 章 checkpoint_cost_model.py 可算最优间隔。
- 追问：FlashRecovery（12.2 论文）相比传统 ckpt 方案的改进？——秒级检测、与规模无关的重启、单步内无 checkpoint 恢复（RPO 压到一个 step）。

### Q11：混合精度训练的数值稳定性怎么保障？

- 画像：全部；难度：基础
- 一句话：master weight 保 FP32、梯度用 loss scaling（FP16）或直接 BF16、累加用高精度、敏感层（softmax/归一化）保 FP32。
- 展开：FP16 范围窄要 scaling；BF16 范围大免 scaling 但精度低；累加器位宽不足是隐蔽坑（FP8 训练里要定期提升到 FP32 累加，见 7.11 章）。
- 追问：loss scaling 系数怎么调？——动态调整：连续无溢出则倍增，溢出则减半并跳过本步。

### Q12：梯度累积（gradient accumulation）的数学与工程注意点？

- 画像：全部；难度：基础
- 一句话：多个 microbatch 梯度累加再一次更新，等效大 batch；工程上注意梯度要按累积步数归一化、且 ZeRO-3/FSDP 下梯度通信时机变化。
- 展开：等效 batch = micro_batch × accum_steps × DP；梯度裁剪要在归一化后的完整梯度上做；与学习率的关系（大 batch 需要调 lr schedule）。
- 追问：梯度累积能无限增大等效 batch 吗？——系统上可以，算法上大 batch 有收敛与泛化问题（需要相应调 lr 与 warmup）。

### Q13：数据加载成为瓶颈怎么发现和解决？

- 画像：全部；难度：基础
- 一句话：nsys 看 GPU 空泡 + dataloader wait 时间占比；解法：增大 num_workers、prefetch、pin_memory、数据预处理离线化、用更快的存储格式（webdataset/二进制 shard）。
- 展开：多模态/长序列场景数据侧更容易瓶颈（解码图片、变长 packing）；DDP 下每个 rank 的 dataloader 要独立 shuffle（不同 seed 偏移）。
- 追问：序列 packing 是什么，为什么提效？——把多条短序列拼到定长消除 padding 浪费，吞吐可提升数倍，但要处理跨序列注意力掩码。

### Q14：Ring AllReduce 的过程与通信量？

- 画像：LLM、芯片；难度：进阶
- 一句话：分成 reduce-scatter 和 all-gather 两阶段，每卡传 2×(N-1)/N 份数据；大数据量下带宽最优（与树形算法的小数据量延迟最优互补）。
- 展开：N 卡时每卡发送总量 = 2×(N-1)/N × D ≈ 2D（与 N 无关）——这是 ring 的可扩展性来源；本仓库 6.8 章 ring_allreduce_sim.py 有模拟。
- 追问：NCCL 什么时候不用 ring？——小消息用 tree/collnet 降延迟；具体算法由 NCCL 按消息大小与拓扑自动选。

### Q15：通信与计算重叠的具体做法有哪些？

- 画像：LLM；难度：进阶
- 一句话：DDP 梯度分桶重叠、ZeRO/FSDP 的预取（前向时提前 all-gather 下一层参数）、TP 内 allreduce 拆分流水、PP 的 microbatch 交错、MoE 的 DualPipe。
- 展开：重叠的前提是有独立流和足够的计算厚度；通信拆分粒度是关键超参；本仓库 6.8 章与各框架实现（Megatron 的 --overlap-grad-reduce 等）对照。
- 追问：为什么重叠对小模型无效？——计算太薄，通信时间本来就盖不住；小模型应该减少并行维度而不是优化重叠。

### Q16：FSDP 和 Megatron-LM 的设计哲学差异？

- 画像：LLM；难度：进阶
- 一句话：FSDP 是"数据并行的显存增强"（对模型代码侵入小，自动分片）；Megatron 是"显式并行语义"（TP/PP 手工定义，性能上限高但侵入深）。
- 展开：FSDP2 的 per-parameter sharding 改进了内存碎片与通信粒度；超大模型预训练主流仍是 Megatron 系（TP/PP/EP 控制力）；微调场景 FSDP 更顺手。
- 追问：RL 框架里为什么两者都要支持？——verl 的双后端：研究迭代用 FSDP（改模型方便），大规模生产用 Megatron（性能上限）。

### Q17：模型从 dense 扩容到 MoE（upcycle）怎么做的？

- 画像：LLM；难度：深入
- 一句话：把 dense FFN 复制成多个专家初始化，加路由器继续训练；稀疏激活让容量翻倍而单 token 计算不变。
- 展开：upcycle 比从零训 MoE 省大量算力（复用 dense 学到的表示）；路由器的初始化与 warmup 影响稳定性；SPES（12.2 论文）展示了去中心化场景下的 upcycle 路径。
- 追问：upcycle 后为什么还要训练很久？——路由器要从零学，专家要在路由分化下重新特化。

### Q18：长序列训练（128k+）的系统方案？

- 画像：LLM；难度：进阶
- 一句话：激活显存随序列平方/线性爆炸——用 context parallelism（序列维切分，ring attention 传 K/V）+ selective activation checkpointing + FlashAttention 组合。
- 展开：CP 把序列切到多卡，ring 传递 K/V block 与计算重叠；注意力是因果的需要 zigzag 切分平衡负载（见 5.12 章 ring_attention_sim.py 的思路在训练侧同样适用）。
- 追问：CP 和 SP（sequence parallelism）区别？——SP 切的是 LayerNorm/Dropout 等 TP 未覆盖部分的激活（Megatron 概念），CP 切的是完整序列维含注意力。

### Q19：训练大规模模型时 checkpoint 系统怎么设计？

- 画像：LLM、云；难度：进阶
- 一句话：分片写（每 rank 写自己那片）、异步化（先快照到内存再后台落盘）、分层存储（本地 SSD→远端对象存储）、校验与可恢复性测试。
- 展开：671B 模型优化器状态可达数 TB，同步写阻塞以分钟计；torch.distributed.checkpoint 支持 async；要定期做"恢复演练"验证 ckpt 真能加载。
- 追问：checkpoint 频率怎么定？——最优间隔 ≈ √(2×写时间×MTBF) 类模型（本仓库 checkpoint_cost_model.py），核心是 goodput 最大化。

### Q20：慢节点（straggler）怎么检测和治理？

- 画像：LLM、云；难度：进阶
- 一句话：同步训练最慢节点决定全体速度——按 rank 监控每 step 耗时与通信等待，p99 离群的节点做硬件诊断（降频/ECC/网络）并自动摘除。
- 展开：NCCL timeout 只能发现"死了"不能发现"慢了"；需要应用层打点（每 rank step time 上报）；治理手段：重启训练进程、隔离节点、热备替换。
- 追问：为什么万卡下慢节点是常态？——几千个部件总有几个处于亚健康（降频、温度、光模块衰减），概率问题（见 6.10 章）。

### Q21：DeepSeek-V3 训练系统有哪些可借鉴的设计？

- 画像：LLM；难度：深入（2024 后高频）
- 一句话：FP8 混合精度训练（细粒度 scaling + 高精度累加提升）、DualPipe 双向流水掩盖 all-to-all、aux-loss-free 负载均衡、全链路显存抠优化，最终 2.788M H800 小时训完 671B。
- 展开：详见 12.2 论文解读；重点是"每个设计都对应一个具体的系统瓶颈"，而不是堆技术。
- 追问：DualPipe 相比 1F1B 的改进？——把 EP 的 all-to-all 通信排进双向流水的空隙，通信几乎零暴露，代价是调度复杂度与双倍权重显存（双向各一份副本的考量）。

### Q22：去中心化训练（decentralized training）可行吗？

- 画像：LLM；难度：深入（2025-2026 新热点）
- 一句话：低带宽公网上，高频梯度同步不可行，但两类负载可行——低频同步的联邦优化（DiLoCo 类）与天然解耦的 RL rollout（INTELLECT-2），以及 MoE 专家级切分（SPES）。
- 展开：INTELLECT-2（2505.07291）完成全球分布式 32B RL 训练，关键是 PRIME-RL + TOPLOC 可验证 rollout；SPES（2602.11543）把专家切到节点解决显存墙。核心判断标准是任务的通信耦合度。
- 追问：去中心化训练的最大非技术障碍？——信任（拜占庭节点伪造计算结果），需要可验证计算机制。

### Q23：训练集群的网络拓扑怎么影响并行策略？

- 画像：LLM、云；难度：进阶
- 一句话：通信频率越高的并行维度越要放在带宽越高的域内——TP 放 NVLink 域（机内 900GB/s）、PP/DP 跨 IB 节点（50GB/s/卡）、EP 尽量高带宽域。
- 展开：拓扑感知调度（9.6 章）：8 卡整机的任务尽量不调散；rail-optimized IB 网络让同号网卡间走同一轨道；画一张"带宽地图"再排并行维度是标准动作。
- 追问：NVL72 改变了什么？——scale-up 域从 8 卡扩到 72 卡，TP/EP 可以全放进高速域，并行策略设计空间变大（见 2.10 章）。

### Q24：如何评估"加机器"的收益（扩展性分析）？

- 画像：云、LLM；难度：进阶
- 一句话：测 strong scaling（固定模型加卡）与 weak scaling（同比放大），看加速比曲线在哪个点开始偏离线性——拐点由通信占比决定。
- 展开：加速比偏离线性的原因是通信占比上升与气泡；Amdahl 视角：串行/通信部分决定上限；实测画出 throughput vs 卡数曲线比理论可靠。
- 追问：什么时候加卡反而变慢？——并行维度被迫改变（如 TP 跨节点）、batch 太小导致通信藏不住、全局 batch 撞收敛上限。

### Q25：训练框架选型：Megatron vs DeepSpeed vs FSDP？

- 画像：全部；难度：基础
- 一句话：超大预训练用 Megatron（3D/EP 控制力最强）、HuggingFace 生态微调用 DeepSpeed（ZeRO 开箱即用）、长期原生路线用 FSDP2；RL 场景看框架支持（verl 双后端）。
- 展开：详见 13.2 章项目档案与选型决策树；多芯片场景另有 FlagScale（上游框架的插件化多芯改造）。
- 追问：torchtitan 的定位？——PyTorch 官方的极简预训练参考实现，学习"现代训练框架怎么搭"的最佳读本。
