# 14.2 推理引擎与 Serving 题

> 共 30 题。公司画像缩写：**LLM**=大模型公司、**芯片**=芯片厂、**云**=云厂商与平台团队、**车**=自动驾驶/具身智能。对应仓库第 5 章与 12.1/12.4 论文。

---

### Q1：Prefill 和 Decode 的计算特性有什么区别？

- 画像：全部；难度：基础（必考）
- 一句话：Prefill 并行处理全部输入 token，是 compute-bound 的大 GEMM；Decode 每步只处理 1 个新 token 但读全部权重和 KV cache，是 memory-bound 的 GEMV。
- 展开：这决定了优化方向完全不同——prefill 要堆算力（大 TP、大 batch），decode 要堆带宽（量化降字节、小 TP 大并发）；两者的 SLO 也不同（TTFT vs TPOT）。
- 追问：为什么 decode 增大 batch 能提吞吐但几乎不影响单 token 延迟？——权重读取被 batch 内请求摊薄，算术强度上升。

### Q2：KV Cache 显存怎么算？

- 画像：全部；难度：基础（必考，要能手算）
- 一句话：2（K和V）× 层数 × KV头数 × 头维度 × 2字节(FP16) × 序列长度 × batch。
- 展开：以 7B 模型（32 层、32 头、128 维）为例：每 token 每请求 = 2×32×32×128×2B = 1MB；4k 上下文单请求约 4GB。GQA/MLA 会把 KV 头数/维度项大幅降低（见 5.11 章 kv_cache_compare.py）。
- 追问：GQA 把 32 头收成 8 组，KV cache 降多少？——恰好 4 倍（线性于 KV 头数）。

### Q3：PagedAttention 解决什么问题？

- 画像：全部；难度：基础
- 一句话：KV cache 的显存碎片与预留浪费——借鉴操作系统分页，把 KV 按固定大小 block 分配，用 block table 间接寻址，显存利用率从约 60% 提到 90%+。
- 展开：连续分配要求预留 max_len，实际长度分布造成巨大内部碎片；分页后按需分配；block 还天然支持前缀共享（copy-on-write）。
- 追问：block 大小的取舍？——大 block 碎片浪费大，小 block 页表开销与 gather 效率差；vLLM 默认 16 token。

### Q4：Continuous Batching 的原理？和静态 batching 差在哪？

- 画像：全部；难度：基础（必考）
- 一句话：迭代级调度——每个 decode step 后重新组 batch，完成的请求立刻退出、新请求立刻插入，而不是等整批最长的请求生成完。
- 展开：静态 batching 的 GPU 利用率被批内最长序列拖死；CB 让吞吐随并发近线性增长；工程难点在调度器状态管理与抢占（显存不足时 swap/recompute）。
- 追问：vLLM 显存不够时怎么处理运行中的请求？——preemption：swap out 到 CPU 或 recompute（丢弃 KV 后续重算）。

### Q5：TTFT 和 TPOT 分别由什么决定？怎么分别优化？

- 画像：全部；难度：基础
- 一句话：TTFT ≈ 排队时间 + prefill 时间（算力敏感）；TPOT = decode 每步时间（带宽敏感，主要由权重+KV 读取量决定）。
- 展开：优化 TTFT——缩短排队（准入控制）、加速 prefill（chunked prefill、prefix cache 命中）；优化 TPOT——量化、减小 KV、增大有效 batch。
- 追问：chunked prefill 是什么？——把长 prefill 切块与 decode 混跑，避免长 prompt 阻塞 decode（保 TPOT），代价是 TTFT 略增。

### Q6：Speculative Decoding 的原理与收益来源？

- 画像：LLM、车；难度：进阶（高频）
- 一句话：小 draft 模型连续猜 k 个 token，大模型一次前向并行验证，接受前缀部分——把"逐 token 串行"变成"一次前向产多个 token"，收益 = 接受率 × k。
- 展开：数学上保证输出分布与目标模型一致（rejection sampling）；收益依赖接受率（draft 质量与任务类型，代码类高、创意类低）；不省总算力，省的是"带宽受限下的墙钟时间"。
- 追问：什么时候投机解码没收益甚至负收益？——大 batch 场景（batch 大时 decode 已接近 compute-bound，验证的额外算力不再免费）。

### Q7：Prefix Cache 的价值和实现方式？

- 画像：LLM；难度：进阶
- 一句话：相同前缀（system prompt、多轮历史、few-shot 示例）的 KV 只算一次，跨请求复用；实现有 vLLM 的 block 哈希复用和 SGLang 的 RadixAttention 前缀树。
- 展开：命中率高时 TTFT 可降一个量级；radix tree 天然支持多分支共享；淘汰策略（LRU）与显存上限权衡。
- 追问：prefix cache 和 paged attention 什么关系？——分页提供了共享的物理基础（block 可被多个序列引用），prefix cache 是建立其上的复用策略。

### Q8：为什么要做 PD（Prefill/Decode）分离？代价是什么？

- 画像：LLM、云；难度：进阶（2024 后高频）
- 一句话：两阶段计算特性相反、SLO 不同、最优并行配置不同——混部互相干扰；分离后各自优化，代价是 prefill→decode 的 KV 跨实例传输。
- 展开：DistServe（2401.09670）与 Mooncake（2407.00079）是代表作（见 12.1 论文解读）；KV 传输量 = 每请求 KV 大小，需要高带宽互联或放置亲和；长上下文场景收益最大。
- 追问：PD 分离后 prefill 实例和 decode 实例的比例怎么定？——按负载的输入/输出长度分布与两阶段的单卡速率求解配比，目标是双侧都恰好满足 SLO（goodput 最大化）。

### Q9：vLLM 的整体架构讲一下？

- 画像：LLM；难度：进阶（源码向）
- 一句话：入口（OpenAI API/离线 LLM 类）→ Processor → Scheduler（continuous batching + 抢占）→ KVCacheManager（paged block 分配）→ Worker/ModelRunner（执行 + CUDA Graph）→ 采样输出。
- 展开：V1 架构重写了调度路径，多进程隔离 API 与引擎；注意力后端可插拔（FlashAttention/FlashInfer/Triton）。
- 追问：vLLM 的 CUDA Graph 怎么用？——decode 按 batch 档位捕获静态图，prefill 走 eager；档位间 padding。

### Q10：单卡能跑多大的模型？怎么估算？

- 画像：全部；难度：基础
- 一句话：权重显存 = 参数量 × 每参数字节（FP16 2B、INT8 1B、INT4 0.5B），再加 KV cache 与激活/workspace；80GB 卡 FP16 约能装 35B 以内（留 KV 空间）。
- 展开：快速心算——70B FP16 需 140GB（2×80GB 起）；INT4 后 35GB（单卡可跑但 KV 紧张）；估算时要给 KV cache 和 CUDA context/workspace 留 20-30%。
- 追问：权重装得下但跑不起来，常见原因？——KV cache 预算被挤没（长上下文高并发），或激活/workspace 峰值超了。

### Q11：MoE 模型推理的特殊性？

- 画像：LLM；难度：进阶（2024 后高频）
- 一句话：总参数巨大但激活参数小——瓶颈从算力变成显存容量与专家间 all-to-all 通信；多卡部署是为了"装下所有专家"（EP）。
- 展开：decode 时小 batch 导致专家负载不均（热门专家拖累整体）；优化手段：冗余专家、负载均衡 bias、fused MoE kernel（Triton）、DeepEP 低延迟通信；参考 5.11 章。
- 追问：MoE 推理为什么常用"DP attention + EP MoE"的组合？——attention（尤其 MLA）不适合 TP 切分就复制（DP），MoE 部分必须 EP 摊开。

### Q12：MLA 对推理系统的影响？

- 画像：LLM；难度：深入
- 一句话：KV cache 大降一个量级（只存低秩 latent），但计算形态改变（吸收矩阵使等效头维变大）且 latent 无法按头 TP 切分——推理部署转向 DP attention。
- 展开：DeepSeek-V2/V3 的核心架构（见 12.3 论文）；KV 小了 → 更长上下文/更大并发成为可能；kernel 需要专门适配（FlashMLA 等）。
- 追问：MLA 的 KV cache 为什么小？——MHA 存全部头的 K/V，MLA 只存低秩压缩向量（V3 每层 576 维），压缩率约一个量级。

### Q13：长上下文推理的系统方案有哪些？

- 画像：LLM；难度：进阶
- 一句话：三条主线——KV 分层 offload（HBM→DDR→SSD，如 Mooncake/LMCache）、稀疏注意力（Quest/NSA 类）、线性/混合架构（Kimi Linear/MiniCPM-SALA 类）。
- 展开：三者在 TTFT、吞吐、精度、实现复杂度上各有取舍（见 5.12 章对比表）；生产系统常组合使用（prefix cache + offload + 稀疏）。
- 追问：1M 上下文单请求 KV 多大？——看模型结构：GQA 模型可达数百 GB（必须 offload 或 context parallel），MLA/线性架构可压到单卡可承受（见 5.11/5.12 章估算脚本）。

### Q14：怎么做 serving 的容量规划（capacity planning）？

- 画像：云、LLM；难度：进阶
- 一句话：从 SLO（TTFT/TPOT）和业务负载（QPS、输入输出长度分布）反推单卡 goodput，再算出实例数 = 峰值 QPS / 单实例 goodput ×（1+冗余）。
- 展开：必须实测而非理论估——用真实负载分布压测；考虑波峰波谷（auto-scaling 的 warmup 延迟）；预留头room 应对流量毛刺；llm-d 的 well-lit paths 提供了方法论参照。
- 追问：为什么用 goodput 而不是峰值吞吐做规划？——峰值吞吐是 SLO 违约状态下测的，按它规划线上必崩。

### Q15：Continuous batching 下，吞吐与延迟怎么权衡？

- 画像：LLM；难度：进阶
- 一句话：增大 running batch 提吞吐但增 TPOT（每步更慢）——存在一条 Pareto 前沿，调度器的 max_num_seqs 等参数就是在前沿上选点。
- 展开：batch 增大时 decode 从纯 memory-bound 逐渐向 compute-bound 过渡，吞吐增长有拐点；调度策略（FCFS/SJF/优先级）影响尾延迟。
- 追问：怎么选线上 max batch？——在 SLO 约束下找吞吐最大的工作点，而不是直接拉满。

### Q16：推理引擎里 CUDA Graph 用在哪？为什么 decode 特别适合？

- 画像：LLM；难度：进阶
- 一句话：decode 每步要 launch 数十个小 kernel，CPU 提交开销占比高；CUDA Graph 把整步录制成图一次提交，消除启动开销。
- 展开：decode 形状相对固定（每步 q_len=1），满足 Graph 的静态形状要求；batch 变化用档位 padding 解决；prefill 形状多变不适合。
- 追问：Graph 捕获的内存代价？——每个档位的图要常驻一份捕获时的中间缓冲，档位太多会浪费显存。

### Q17：如何设计多机多卡的推理部署方案（给一个 671B MoE 模型）？

- 画像：LLM、云；难度：深入
- 一句话：671B FP8 权重约 671GB → 至少 8×141GB（H200）或 2 台 8×80GB；MoE 部分 EP、attention 部分 DP/复制、prefill/decode 分离视负载而定。
- 展开：先算权重再算 KV cache 预算决定并发能力；EP 跨节点要评估 all-to-all 带宽（NVLink 域内 vs IB 跨节点差一个量级）；DeepSeek 官方部署方案（大 EP）是参照。
- 追问：EP 放在 NVLink 域内还是跨节点？——通信量小且 decode 低延迟优先时尽量域内；追求大 EP 摊薄权重则跨节点（DeepEP 类的 low-latency 模式支撑）。

### Q18：推理的成本大头是什么？怎么降成本？

- 画像：云、全部；难度：进阶
- 一句话：decode 阶段的权重+KV 带宽消耗 × 输出 token 数；降本路径：量化（FP8/INT4）、提 batch 利用率、prefix cache 复用、投机解码、错峰调度。
- 展开：成本核算口径是"每百万 token 的 GPU 小时"；利用率是第一杠杆（业界平均 <50%）；输出 token 比输入贵得多（输入一次 prefill，输出逐 token decode）。
- 追问：为什么"输出 token 定价通常是输入的 3-5 倍"？——decode 是 memory-bound 且逐 token 执行，单位算力成本远高于并行的 prefill。

### Q19：vLLM 和 SGLang 怎么选？

- 画像：LLM；难度：基础
- 一句话：通用 serving 选 vLLM（生态最大、硬件支持最全）；前缀复用高/结构化输出/RL rollout 场景 SGLang 更强；极限 NVIDIA 性能看 TRT-LLM。
- 展开：两者核心功能已高度互卷；选型看团队熟悉度、目标模型的支持质量（新模型往往一边先支持）、与周边栈（如 RL 框架）的集成。
- 追问：llm-d 和它们什么关系？——llm-d 是引擎之上的 K8s 编排层（智能路由/PD 分离/KV 分层/SLO 扩缩容），不是竞品（见 13.1 节）。

### Q20：服务被流量打满时，系统的正确行为是什么？

- 画像：云；难度：进阶
- 一句话：准入控制 + 优雅降级——预测式早期拒绝（Mooncake 的思路）保住已接纳请求的 SLO，而不是照单全收全部违约。
- 展开：排队深度监控、按优先级降级（长输出请求限流）、返回 429 + retry-after；关键是"过载时牺牲谁"要有明确策略。
- 追问：怎么检测"即将过载"而不是"已经过载"？——看队列等待时间与 KV 使用率的前瞻指标，而非等延迟飙高。

### Q21：Prompt 很长（100k+）时 TTFT 优化手段？

- 画像：LLM；难度：进阶
- 一句话：prefix cache 命中（最优）、chunked prefill 保 TPOT、稀疏 prefill（MInference 类）、多卡 context parallel 分摊。
- 展开：100k prefill 的算力需求 = 2×参数×100k FLOPs，量级显著；prefix cache 命中率是长 prompt 业务的第一指标；MInference（2407.02490）用动态稀疏加速 prefill。
- 追问：chunked prefill 的 chunk 大小怎么选？——太小 prefill 效率低，太大 decode 被阻塞；典型取与 decode 单步时间同量级。

### Q22：多租户 serving 怎么做隔离？

- 画像：云；难度：进阶
- 一句话：三个层次——硬件隔离（MIG/整机）、实例隔离（每租户独立推理实例）、逻辑隔离（同一实例内的配额、优先级、限流）。
- 展开：隔离性与利用率矛盾：MIG 隔离好但粒度固定；逻辑隔离利用率高但有干扰风险；按租户 SLA 等级混合使用（见 9.6 章 MIG 装箱脚本）。
- 追问： noisy neighbor 问题怎么监测？——按租户分别统计 TTFT/TPOT 的 p99，异常突增时 trace 到同实例的其他租户负载。

### Q23：OpenAI 兼容 API 网关层要做哪些事？

- 画像：云、LLM；难度：基础
- 一句话：协议适配、鉴权限流、路由（按模型/租户/前缀亲和）、负载均衡、可观测性（按请求的 TTFT/TPOT/token 数埋点）。
- 展开：前缀亲和路由能显著提 prefix cache 命中率（llm-d 的智能路由就是强化这点）；流式响应（SSE）的背压处理；失败重试与熔断。
- 追问：为什么网关路由策略会影响 GPU 效率？——路由决定前缀复用率与实例负载均衡，直接决定集群整体 goodput。

### Q24：推理场景选卡：A100/H100/L20/4090 怎么考虑？

- 画像：全部；难度：基础
- 一句话：看三样——显存容量（装不装得下权重+KV）、显存带宽（decode 速度）、互联（多卡扩展性）；成本敏感场景算每 token 成本而非单卡价格。
- 展开：H100 带宽 3.35TB/s 是 A100（1.6-2TB/s）的近 2 倍，decode 直接受益；L20/4090 类卡显存小、无 NVLink，适合小模型或纯离线；本仓库 1.12 章有完整选型指南。
- 追问：为什么 decode 密集场景带宽比算力重要？——decode 是 GEMV，算术强度约 2 FLOPs/字节，远低于任何卡的 roofline 拐点。

### Q25：流式输出（streaming）对系统设计的影响？

- 画像：LLM、车；难度：基础
- 一句话：连接长时间持有（几分钟级），网关要支持 SSE、背压与断连检测；首个 token 前与后续 token 的延迟特征完全不同（TTFT vs TPOT 分别优化）。
- 展开：断连要及时释放 KV（否则显存泄漏）；客户端慢消费时的缓冲策略；负载均衡要考虑连接时长（长连接导致新实例预热慢）。
- 追问：abort 一个请求引擎要做什么？——从 running batch 摘除、释放 block、通知调度器，且不能影响同 batch 其他请求。

### Q26：SGLang 的 RadixAttention 是什么？

- 画像：LLM；难度：进阶
- 一句话：把所有请求的 KV cache 组织成按 token 前缀的基数树，新请求匹配最长已缓存前缀只算增量，多分支/多轮共享天然高效（见 12.1 论文解读）。
- 展开：相比 vLLM 的 block 哈希复用，radix tree 对"多分支 fork"场景（agent、并行采样）表达更自然；LRU 逐出控制总量。
- 追问：什么时候 RadixAttention 没收益？——请求间无重复前缀的负载（完全独立单轮问答）。

### Q27：多模态（VLM）推理比纯文本多了哪些系统问题？

- 画像：LLM、车；难度：进阶
- 一句话：图像编码器（ViT）引入第二个计算阶段，image token 数量大且可变（分辨率相关），prefill 更重、负载更不均匀。
- 展开：image token 数 = (H/14)×(W/14) 量级，一张大图几千 token；ViT 与 LLM 的资源配比需要分别规划；视频理解更夸张（帧 × 每帧 token）。
- 追问：VLM 的吞吐瓶颈通常在哪？——高分辨率输入下 prefill（ViT + 大量 image token 的 LLM prefill）占主导，与纯文本的 decode 主导不同。

### Q28：端侧/车端推理和云端推理的设计差异？

- 画像：车；难度：进阶
- 一句话：端侧是"硬实时 + 资源封顶"——固定延迟预算、无弹性扩容、功耗约束；云端是"SLO + 弹性"——追求 goodput 与成本。
- 展开：端侧用静态 batch、固定 shape、TensorRT 静态优化；关键任务 pinning（安全相关模型常驻显存）；降级策略预先设计（见 5.10 章 edge_colocated_scheduler.py）。
- 追问：VLA 模型的推理预算怎么算？——action_tokens = 维度 × 每维 token × horizon；required_tps = action_tokens / 控制周期预算（见 5.10 章估算器与 openpi 案例）。

### Q29：推理引擎升级/发版怎么做不抖动？

- 画像：云；难度：进阶
- 一句话：滚动升级 + 预热——新实例先加载模型、预热 CUDA Graph 与 prefix cache，健康检查通过后摘流，灰度按流量比例切。
- 展开：vLLM 启动的模型加载与 graph 捕获可达分钟级，未预热直接接流量会 TTFT 爆炸；金丝雀实例先接 1% 流量观察 SLO。
- 追问：怎么验证新版引擎的性能没退化？——性能回归门禁：固定负载的 benchmark 对比（见 9.2 章 regression_gate.py）。

### Q30：离线批量推理（batch inference）和在线 serving 的系统差异？

- 画像：LLM、云；难度：进阶
- 一句话：离线追吞吐（巨大 batch、无延迟约束、可抢占填谷），在线追 SLO（并发与延迟平衡）；离线任务是与在线混部、提升集群利用率的理想负载。
- 展开：离线可用离线引擎模式（vLLM offline LLM API）跑满 GPU；配合调度器做波谷填谷（见 9.6 章混部）；llm-d 也把 batch 处理作为独立能力（OpenAI Batch API）。
- 追问：离线推理任务为什么适合被抢占？——无用户在线等待，被抢占后 checkpoint 恢复重跑代价低（对比在线请求中断=用户可见事故）。
