# 3.1 AI 编译器基础

## 课程概述

AI 编译器是连接**高层模型描述**与**底层可执行代码**的桥梁。训练框架（PyTorch、TensorFlow）产出的模型只能表达“算什么”，而 GPU/NPU/CPU 等硬件需要知道“怎么算”。AI 编译器负责把模型自动转换为高效、可移植、可部署的可执行代码。

很多初学者把 AI 编译器理解成“把 ONNX 算子翻译成 CUDA kernel 的脚本”，这只对了一小部分。生产级 AI 编译器至少要同时回答四个问题：

1. **正确性**：算子语义能否等价转换？动态 shape 怎么处理？多后端如何保证数值一致？
2. **表达力**：静态图 vs 动态图、控制流、稀疏性、混合精度如何表达？
3. **优化能力**：图优化、算子融合、布局变换、内存规划、常量折叠能否自动化完成？
4. **工程落地**：编译速度是否可接受？多平台能否一键出包？CI/CD 如何集成？

本节先把 AI 编译器的骨架搭起来：三段式 Pipeline、为什么需要 AI 编译器、以及量化/HPC/多平台的全链路协同。后续各节会在这个骨架上继续深化 TVM 架构、前端、中端 Pass、后端、Laser 框架、迁移实战与编译耗时优化。

学完本节后，你应该能够：

- 画出 AI 编译器的三段式 Pipeline（前端 → 中端 → 后端），并说明每个阶段的核心职责。
- 解释为什么手写算子无法扩展到多平台、多模型场景。
- 说明量化、HPC 算子、多平台编译在 AI 编译器链路中如何协同。
- 区分静态图编译器与动态图编译器在 shape 处理上的核心差异。

## 1. AI 编译器在模型部署链路中的位置

可以把一个模型部署链路粗略分成五层：

```text
训练框架：PyTorch / TensorFlow / JAX，产出动态图或 checkpoint
模型导出：ONNX / TorchScript / FX，得到静态化计算图
AI 编译器：前端解析 → 中端图优化 → 后端代码生成
运行时引擎：Runtime、Serving、内存池、调度器
硬件执行：CUDA kernel、Tensor Core、NPU DSA、CPU SIMD
```

AI 编译器覆盖**模型导出 → 硬件执行**之间的全部转换工作。它不是简单地把算子翻译成 kernel，而是要在不改变数值语义的前提下，把图变得更适合硬件执行。

一个典型模型在 AI 编译器中的流转路径：

```text
ONNX / TorchScript 模型
  → 前端解析：构建 Relay / Relax 计算图
  → 中端优化：图优化 Pass（DCE、常量折叠、算子融合、布局变换）
  → 后端编译：TIR + CUDA/CUTLASS/TensorRT Codegen
  → 生成 deployable artifacts（.so / .aom / .trt）
  → 运行时加载执行
```

![AI 编译器链路](images/4_0_ai_compiler_pipeline.png)

注意：如果任何一阶段的假设（shape、dtype、layout、后端能力）与其他阶段不匹配，部署链路就会出现数值错误、编译失败、性能崩溃或产物无法加载。

## 2. 为什么需要 AI 编译器

### 2.1 手写算子不可扩展

手写 kernel 在小规模 demo 中可行，但面对以下场景会不可扩展：

- **模型迭代快**：新模型、新算子层出不穷，手写 kernel 跟不上。
- **硬件种类多**：NVIDIA GPU、AMD GPU、NPU、ARM CPU 指令集差异大。
- **优化组合爆炸**：融合、量化、布局、内存排布、动态 shape，人工组合难以穷尽。
- **性能要求苛刻**：推理延迟、p99 抖动、吞吐，需要自动化搜索（Ansor、MetaSchedule）。

AI 编译器的核心价值：

> **用统一的中间表示（IR）和可复用的优化 Pass，把模型自动转换为高性能、可移植的硬件代码。**

### 2.2 多平台适配成本高

假设一个 Transformer 模型要部署到：

- A100 GPU（CUDA + Tensor Core）
- 某 NPU（自定义指令集）
- ARM CPU（NEON / SIMD）

手写三套 kernel 的成本极高，且模型每改一次，三套代码都要同步。AI 编译器通过同一套 IR 和不同后端 Codegen，把多平台适配问题转化为“后端实现”问题，而不是“重写模型”问题。

```text
模型（PyTorch/ONNX）
  → 前端 → 统一 IR
         ├── GPU backend: CUDA/CUTLASS/TensorRT
         ├── NPU backend: NPU SDK
         └── CPU backend: LLVM/ARM NEON
```

## 3. 编译 Pipeline 核心流程

三段式 Pipeline 是 AI 编译器的主干：

```text
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   前端 FrontEnd  │ ──→ │  中端 MiddleEnd  │ ──→ │  后端 BackEnd   │
└─────────────┘     └─────────────┘     └─────────────┘
       │                    │                    │
  ONNX/PT解析          图优化 Pass           代码生成/调度
  动态 shape 处理       算子融合/常量折叠      硬件 kernel 生成
  自定义算子注册        内存规划/布局变换      runtime 打包
```

各阶段输入输出：

| 阶段 | 输入 | 输出 | 核心问题 |
| ---- | ---- | ---- | -------- |
| 前端 | ONNX/TorchScript/模型脚本 | 高层 IR（Relay/Relax） | 图结构、算子语义、动态 shape、控制流 |
| 中端 | 高层 IR | 优化后的高层 IR | 冗余消除、融合、内存、布局、数值等价 |
| 后端 | 优化后的高层 IR | 底层 IR / 硬件代码 | 调度、Codegen、runtime、打包 |

### 3.1 前端：把模型变成 IR

前端负责把不同框架的模型格式转换为统一的中间表示。需要处理：

- 算子映射：ONNX 的 `Conv` 对应 TVM 的 `nn.conv2d`。
- 动态 shape：batch、sequence length 可能是符号变量。
- 控制流：if/while/loop 如何表达。
- 自定义算子：框架特有算子如何注册到 IR。

### 3.2 中端：优化 IR

中端在**不改变模型推理逻辑与计算精度**的前提下，对图进行结构化改写。核心目标：

- 减少冗余算子（死代码、无意义 Cast/Reshape）。
- 合并算子，减少 kernel launch 和显存读写。
- 优化布局，适配硬件计算格式。
- 规划内存，降低峰值显存。
- 常量折叠，把编译期能算完的提前算完。

### 3.3 后端：把 IR 变成硬件代码

后端负责把优化后的 IR 生成目标硬件代码：

- CUDA Codegen：把 TIR 打印成 CUDA C++，调用 nvcc 编译。
- CUTLASS/TensorRT：识别特定模式，卸载到高性能库。
- NPU/CPU：调用对应 SDK 或 LLVM 生成指令。
- Runtime 打包：把 kernel、权重、元数据打包成可加载产物。

## 4. 全链路协同：量化、HPC、多平台

AI 编译器不是孤立工作，它需要与全链路协同：

```text
量化模块 ──→ 插入 Q/DQ 节点 → 编译器识别量化模式 → 后端生成 INT8/FP16 kernel
HPC 算子库 ──→ CUTLASS/cuBLAS 算子模板 → 后端匹配并调用
多平台目标 ──→ 同一 IR 经不同后端 → GPU/NPU/CPU 各自出包
```

### 4.1 量化与编译器协同

```text
PyTorch 模型 (FP32)
  → 量化工具插入 Quantize/Dequantize
  → 前端解析为 Q/DQ 节点
  → 中端：FoldConstant 合并 scale，FuseOps 融合 QConv/ReLU/DQ
  → 后端：生成 INT8 Tensor Core/CUTLASS kernel
```

编译器需要识别量化模式，否则 Q/DQ 会被当成普通算子，无法利用硬件 INT8 加速。

### 4.2 HPC 算子与编译器协同

CUTLASS、cuBLAS、oneDNN 等 HPC 库提供手工优化的高性能算子。编译器后端通过模式匹配，把 `MatMul + BiasAdd + ReLU` 映射到 CUTLASS 的 epilogue 融合实现。

### 4.3 多平台编译协同

```text
同一 Relax IR
  ├── GPU backend: CUDA Codegen + CUTLASS
  ├── NPU backend: Legalize + NPU SDK
  └── CPU backend: LLVM + x86/ARM SIMD
```

关键挑战：不同硬件的算子支持、数据布局、内存模型不同。中端需要保留足够抽象的 IR，后端负责硬件适配。

## 6. 常见误区

### 6.1 “编译器只负责生成代码”

错。编译器还要保证数值等价、处理动态 shape、决定融合策略、规划内存布局、优化编译速度本身。忽略其中任何一环，部署都会失败或性能不达标。

### 6.2 “手写 kernel 一定比编译器快”

在单一算子、单一硬件上，手写专家 kernel 通常最快。但模型越来越大、算子组合越来越多，编译器通过融合、布局优化、自动搜索，在整体图上往往能获得更高收益。

### 6.3 “所有平台可以用同一个后端配置”

不同硬件的内存带宽、Tensor Core 布局、算子支持差异很大。一套 Pass pipeline 直接套用所有后端，通常会有性能损失或编译失败。需要针对后端做 Legalize 和 Layout 适配。

## 7. 本节小结

1. AI 编译器是连接模型与硬件的桥梁，核心职责是**正确性、表达力、优化能力、工程落地**。
2. 三段式 Pipeline：**前端解析 → 中端图优化 → 后端代码生成**，每个阶段输入输出和核心问题不同。
3. 手写算子无法扩展到多平台、多模型、快速迭代的场景，AI 编译器通过统一 IR 解决可移植问题。
4. 量化、HPC 算子、多平台编译需要与编译器全链路协同，否则优化收益无法落地。
