# Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving

> 论文信息：arXiv 2407.00079 / 月之暗面（Moonshot AI）、清华大学 / 2024-07 / 一句话概括：Kimi 生产环境的 serving 平台，以 KV Cache 为中心做 PD 分离，把 GPU 集群里闲置的 CPU/DRAM/SSD 组织成分布式 KV 缓存池，并用"预测式早期拒绝"应对真实过载流量。

## 1. 背景与要解决的问题

Kimi 的业务特征是**长上下文**（早期就主打 20 万至 200 万字）：KV cache 体积大、prefill 成本高、不同请求间前缀重复率高（相同文档被反复提问）。同时真实线上流量波动剧烈，过载是常态而不是异常。

这带来三个问题：

1. KV cache 太大，单 GPU 显存存不下所有热数据，但集群里 CPU 内存和 SSD 大量闲置。
2. Prefill 与 decode 的资源需求差异在长上下文下被进一步放大。
3. 过载时传统"照单全收再排队"会导致全部请求 SLO 违约——需要有取舍地拒载。

## 2. 核心设计

1. **KVCache 为中心的解耦架构**：prefill 集群与 decode 集群分离（沿用并发展 DistServe 路线），但把 KV cache 本身当作一等公民来调度——请求调度跟着 KV 数据走，而不是数据跟着算力走。
2. **分布式分层 KV 缓存池**：利用 GPU 集群中空闲的 CPU DRAM 和 SSD 构建跨节点的 KV cache 池，热点前缀在集群级复用（跨请求共享 prefix cache），显著降低重复 prefill。
3. **KVCache 中心化调度器**：调度决策同时考虑当前负载、SLO 约束和 KV cache 位置/命中情况，在"最大化有效吞吐"与"满足延迟 SLO"之间平衡。
4. **预测式早期拒绝（early rejection）**：不假设所有请求都必须处理——在入口处预测请求能否按时完成，过载时提前拒绝，保住已接纳请求的 SLO，避免雪崩。

## 3. 关键数据

- 论文报告：在模拟场景下，满足 SLO 的前提下吞吐相比基线最高提升 525%；在真实负载下支撑了 Kimi 的生产服务（长上下文场景优势最明显）。
- 分层缓存 + 前缀复用使大量长文档问答请求免去重复 prefill，这是长上下文业务成本下降的关键来源。

## 4. 计算/通信/显存三角取舍分析

- **换来的**：显存侧——把"显存墙"转化为"分层存储问题"，等效 KV 容量扩大一个数量级；计算侧——前缀复用直接省掉重复 prefill 的计算。
- **牺牲的**：通信侧——KV 在 GPU/CPU/SSD/跨节点之间搬运，依赖高速互联与精细的预取调度；系统复杂度大幅上升。
- 本质：这是"用存储和调度换计算"的极端样本——当 prefill 成本高于 KV 存储+传输成本时，缓存一切可缓存的。

## 6. 局限性与启发

- 局限：架构与 Kimi 的长上下文业务强绑定，短请求高并发场景优势减弱；早期拒绝策略涉及产品体验取舍；论文对调度器内部算法披露有限。
- 启发：
  - 顶级 serving 系统的差异化不在 kernel，而在**调度与数据放置**。
  - "过载时保护已接纳请求"是生产系统必修课，与学术评测的"全部跑完再统计"思路完全不同。
  - 读懂 Mooncake 就读懂了"为什么长上下文是一门 infra 生意"。

## 7. 面试视角

- **Q：Mooncake 和 DistServe 的区别？** A：DistServe 提出 PD 分离解决阶段干扰；Mooncake 在此基础上以 KV cache 为中心，加了分布式分层缓存池、跨请求前缀复用和面向过载的准入控制，是生产级完整方案。
- **Q：长上下文 serving 的最大成本是什么，怎么降？** A：重复 prefill 的计算成本和 KV 存储成本；前者靠前缀复用，后者靠分层缓存。
- **Q：过载时 serving 系统该怎么办？** A：预测式早期拒绝，牺牲部分请求保住整体 SLO，避免全部违约。
