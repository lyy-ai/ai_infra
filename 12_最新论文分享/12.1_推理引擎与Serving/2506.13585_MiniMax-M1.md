# MiniMax-M1: Scaling Test-Time Compute Efficiently with Lightning Attention

> 论文信息：arXiv 2506.13585 / MiniMax / 2025 年 6 月 / 首个开源权重的大规模混合注意力（hybrid-attention）推理模型，用 Lightning Attention 支撑百万级上下文与超长 test-time compute。

## 1. 背景与要解决的问题

2025 年推理模型的范式变成了"用更长的思考链换取更高的智力上限"（test-time compute scaling）。但这条路在 serving 侧撞上两堵墙：

- **长上下文 + 长输出的双重代价**。推理模型不仅要读长输入，还要生成几万 token 的思考过程。标准 softmax attention 的计算与 KVCache 开销随长度平方增长，1M 级上下文下既慢又贵。
- **RL 训练与推理的成本耦合**。推理模型靠大规模 RL 训练，而 RL 需要反复采样生成海量 rollout，推理效率直接决定训练成本。推理慢 2 倍，RL 预算就翻 2 倍。
- **现有开源方案缺位**。当时能支撑百万上下文的长思考模型基本是闭源的，社区缺少可复现、可部署的开源参照。

MiniMax-M1 要回答的问题是：**能否设计一种混合注意力架构，让模型原生支持 100 万 token 上下文，并使 test-time compute 的扩展成本可控，同时还能用可承受的算力完成大规模 RL 训练？**

## 2. 核心设计

要点 1：**混合 MoE + Lightning Attention 架构**。M1 基于 MiniMax-Text-01 开发，总参数 456B、每 token 激活 45.9B。核心是把 softmax attention 与 lightning attention（一种线性复杂度的注意力）混合使用：大部分层用线性注意力摊薄长序列成本，少数层保留全注意力保住质量。

要点 2：**原生 1M token 上下文**。模型原生支持 100 万 token 上下文，是 DeepSeek R1 上下文规模的 8 倍，使"长输入 + 长思考"在同一会话内成为可能。

要点 3：**线性注意力摊薄 test-time compute 成本**。Lightning attention 让生成长度方向的计算与 KVCache 增长从平方级降为近似线性，这是"思考预算可以从 40K 扩到 80K 而不失控"的系统前提。

要点 4：**CISPO 强化学习算法**。为匹配 RL 效率需求，论文提出 CISPO：对重要性采样权重（importance sampling weights）做 clip，而不是像常规做法那样 clip token 更新本身，从而提升 RL 训练效率与稳定性，性能优于其他竞争性 RL 变体。

要点 5：**双思考预算发布**。开源发布 40K 与 80K 两个思考预算版本的模型，其中 40K 版本是 80K 训练的中间阶段产物，方便社区研究思考预算与能力的关系。

## 3. 关键数据

以下数字均来自论文摘要：

- 模型规模：总参数 **456B**，每 token 激活 **45.9B**。
- 上下文长度：原生支持 **100 万 token**，为 DeepSeek R1 上下文规模的 **8 倍**。
- RL 训练成本：在 **512 张 H800 GPU** 上仅用 **三周**完成全部 RL 训练，租金成本约 **53.47 万美元**。
- 模型定位：与 DeepSeek-R1、Qwen3-235B 等强开源权重模型相当或更优，在复杂软件工程、工具使用、长上下文任务上优势尤其明显。
- 发布形态：40K 与 80K 两个思考预算版本均开源。

## 4. 计算/通信/显存三角取舍分析

- **牺牲部分表达能力（计算换计算）**。线性注意力层对长程精确检索（如"大海捞针"式定位）的表达弱于全注意力，这是为平方复杂度买单的方式：用混合架构把全注意力限制在少数层，把平方成本限制在可接受范围，本质是"把计算预算花在刀刃上"。
- **显存换长度：KVCache 增长从平方变线性**。标准 attention 下 1M 上下文的 KVCache 是灾难性的；线性注意力层只需维护固定大小的状态，KVCache 随长度线性（对线性层而言是常数级状态）增长，使百万上下文在 serving 侧变得可承载。这是显存维度上最关键的换取。
- **训练成本换推理成本（跨阶段转移）**。混合架构与 CISPO 的协同让 512 卡三周完成 RL，本质是把"架构设计阶段的复杂度"（线性注意力 kernel、混合层训练稳定性）转化为"每次 rollout 的便宜"，RL 场景下这笔交换极其划算，因为 rollout 数量以亿计。
- **批处理友好度的隐性代价**。混合架构意味着同一模型内存在两类访存模式迥异的层，推理引擎需要对两类层分别优化调度与 kernel，系统复杂度上升，换取的是端到端吞吐。

总结取舍：M1 用**架构复杂度与少量注意力表达能力**，换**上下文长度与 test-time compute 的线性扩展能力**，并把红利同时兑现到推理 serving 与 RL 训练两侧。

- **5.11 MoE推理与MLA**：456B/45.9B 的 MoE 结构对应 MoE 推理的专家并行、路由与激活内存问题；可与 DeepSeek 系 MLA 的 KVCache 压缩路线比较（M1 用的是线性注意力路线）。
- **5.3 ContinuousBatching**：超长生成（40K-80K 思考预算）对 continuous batching 的调度、抢占与显存压力管理提出更极端的要求，是该章节讨论问题的放大器。
- **5.2 PagedAttention与KVCache管理**：混合架构下部分层无 KVCache、部分层有 KVCache，给 KV 管理子系统的设计带来新维度（分层异构状态管理）。

## 6. 局限性与启发

局限性：

- 混合架构的收益高度依赖 lightning attention 层与 softmax 层的配比，论文摘要未披露配比细节，复现时需要参考正文与开源代码。
- 线性注意力层对需要精确长程检索的任务理论上存在表达上限，混合比例是质量与效率的权衡点，不是免费的。
- 摘要中的成本数字（512 卡、三周、53.47 万美元）是 RL 阶段成本，不含预训练，引用时不要扩大解释。
- 与全注意力模型在同等 FLOPs 下的严格帕累托对比，摘要未给出，需谨慎下"全面超越"的结论。

启发：

- **test-time compute 时代的瓶颈在生成侧**：当输出动辄几万 token，decode 成本与 KVCache 增长才是首要约束，架构创新（线性/混合注意力）比纯系统工程更能改变成本曲线。
- **推理效率与训练效率是同一件事**：RL 训练本质是大规模受控推理，serving 优化（吞吐、KVCache）的进步会直接降低训练成本。
- **混合架构是务实路线**：与其追求纯线性注意力的"圣杯"，不如用少量全注意力层保底质量，这是工程上已被验证可行的折中。

## 7. 面试视角

可能问题："推理模型输出几万 token 的思考链，serving 成本主要卡在哪，怎么解？"

一句话答案：卡在 decode 阶段 attention 的平方计算与 KVCache 的平方/线性增长；架构层面可用 MiniMax-M1 式的混合线性注意力把长程成本降为近似线性（其 456B MoE 模型原生支持 1M 上下文），系统层面配合 continuous batching 与 KVCache 分层管理摊薄长尾生成成本。
