# SGLang: Efficient Execution of Structured Language Model Programs

> 论文信息：arXiv 2312.07104 / UC Berkeley、Stanford 等（LMSYS 团队）/ 2023-12（持续演进至今）/ 一句话概括：为"复杂 LLM 程序"（多轮调用、控制流、结构化输出）设计的 serving 系统，前端提供编程原语，运行时靠 RadixAttention 做 KV 复用、压缩状态机加速结构化输出。

## 1. 背景与要解决的问题

LLM 应用早已不是"单轮问答"：Agent 要多轮调用、few-shot 要重复长前缀、结构化输出（JSON）要约束解码、并行分支要 fork 会话。这些场景的共同点是**请求之间存在大量可复用的 KV 前缀**，但当时的推理框架把每次调用当独立请求，前缀被反复重算。

问题：如何让"程序化的 LLM 调用"既好写（前端抽象）又跑得快（运行时复用）？

## 2. 核心设计

1. **前端语言**：提供 generation、fork/join 并行、控制流等原语，把多步 LLM 调用表达成一个程序，运行时能看到完整的调用图（这是系统优化的信息来源）。
2. **RadixAttention**：把所有请求的 KV cache 组织成一棵 Radix Tree（基数树），key 是 token 序列前缀；新请求进来时沿树匹配最长已缓存前缀，只算增量部分；LRU 逐出。树结构天然支持多分支共享（fork 场景）。
3. **压缩有限状态机（Compressed FSM）**：结构化输出（如 JSON schema 约束解码）把正则/语法编译成状态机，SGLang 把多条相邻的确定路径压缩成"一跳多 token"，加速约束解码。
4. **API 层缓存（cache-aware 调度）**：调度时感知前缀位置，倾向把同前缀请求路由到持有缓存的实例。

## 3. 关键数据

- 论文报告：在 agent 控制、逻辑推理、few-shot、多轮对话等任务上，相比当时的 SOTA 推理系统吞吐最高提升 6.4 倍（收益主要来自 RadixAttention 的前缀复用，复用率高的 workload 收益最大）。
- SGLang 后续演进为独立的开源推理框架（与 vLLM 并列的第一梯队），RadixAttention 成为其标志性技术。

## 4. 计算/通信/显存三角取舍分析

- **换来的**：计算侧——前缀只算一次，多分支/多轮场景省掉大量重复 prefill。
- **牺牲的**：显存侧——要留存更多历史 KV（用 LRU 控制总量）；调度侧——缓存命中最大化与负载均衡存在冲突（把请求送到有缓存的卡，可能造成热点）。
- 本质：用显存和调度复杂度换计算量。workload 的前缀重复率越高，交换越赚；纯随机无重复请求时近似零收益。

## 6. 局限性与启发

- 局限：RadixAttention 的收益高度依赖 workload 前缀重复率；基数树管理与逐出增加运行时复杂度；约束解码的状态机方法只适用于可形式化描述的格式。
- 启发：
  - **把应用层信息暴露给系统层**（前端程序结构 → 运行时优化）是系统设计的通用方法论。
  - KV cache 的复用粒度从"单次请求内"扩展到"整个集群的历史请求"，是 serving 优化的重要轴线（后续 Mooncake 等把这条线推到极致）。

## 7. 面试视角

- **Q：RadixAttention 的原理？** A：把 KV cache 按 token 前缀组织成基数树，请求匹配最长已缓存前缀只算增量，多分支天然共享，LRU 逐出控制显存。
- **Q：RadixAttention 什么时候没用？** A：请求间没有重复前缀的 workload（如完全随机的单轮问答）。
- **Q：SGLang 与 vLLM 的设计差异？** A：SGLang 起于"LLM 程序执行"视角（前缀树复用 + 结构化输出），vLLM 起于"显存分页管理"视角（PagedAttention）；如今两者功能高度互卷，差异在工程细节与生态。
