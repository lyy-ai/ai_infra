# Recipes for Pre-training LLMs with MXFP8

> 论文信息：arxiv 2506.08027 / NVIDIA（Asit Mishra, Dusan Stosic, Simon Layton, Paulius Micikevicius）/ 2025-05-30（2506 号段）/ 系统给出用 Blackwell 微缩放（MX）格式 MXFP8-E4M3 做预训练的完整配方，做到与 BF16 训练曲线匹配，验证至 8B 参数、15T token。

## 1. 背景与要解决的问题

FP8 训练已被验证可行，但现有 FP8 训练方案（如 DeepSeek-V3 的做法）有两个结构性限制：

1. **缩放粒度粗**：per-tensor 或 per-block 的 scale 需要软件维护，对异常值敏感，因此不是所有张量都敢量化——很多方案只量化 GEMM 输入，激活、梯度的部分路径仍走高精度。
2. **工程链路复杂**：延迟缩放（delayed scaling）、amax 历史滑窗等机制需要框架深度配合。

Blackwell 引入的 **Microscaling（MX）格式**改变了前提：硬件原生支持"细粒度 per-block scale + 窄浮点元素"的数据布局，scale 是数据格式的一部分而非软件约定。这意味着可以量化更多张量、且运算直接在硬件上高效执行。

但"硬件支持"不等于"会用"：MX 格式有多种元素类型（E4M3/E5M2/FP4 等）、多种块大小、多种舍入和转换方式，选错了训练就不稳。这篇论文的价值就是给出**经过大规模验证的选型配方**。

## 2. 核心设计

1. **选定 MXFP8-E4M3 作为主力格式**：在 MX 家族的多个候选（不同指数/尾数分配）中，论文实验证明 MXFP8-E4M3 是预训练的甜点——精度足够覆盖前向权重/激活，配合块级 scale 后动态范围也够用。
2. **特定的数值转换算法是关键变量**：论文强调，同样的 MXFP8-E4M3，不同的 number conversion（高精度到 MX 格式的舍入/饱和策略）会导致训练稳定性天差地别。选对转换算法后，训练曲线可以匹配 BF16。这是全文最核心的"配方"成分。
3. **全量张量量化**：借助 MX 格式的细粒度 scale，量化覆盖面比传统 FP8 方案更广——更多张量（包括此前不敢量化的路径）都可以压到 MXFP8。
4. **硬件原生执行**：因为 MX 是 Blackwell 的原生格式，量化后的 GEMM 不需要软件模拟缩放，避免了"量化省的算力被 scale 管理吃回去"的老问题。
5. **大规模验证方法学**：不是只跑小模型 toy 实验，而是在最大 8B 参数、15T token 高质量数据集上验证——这个规模足以暴露长训练下的误差累积问题。

## 3. 关键数据

- 验证规模：模型最大 **8B 参数**，训练数据最多 **15T token**（高质量数据集）。
- 核心结论：使用 **MXFP8-E4M3 + 特定数值转换算法** 的训练，可以**匹配 BF16 的训练过程**（training sessions that match those carried out in BF16）。
- 摘要未给出具体 loss 差值或 benchmark 分数，引用时以"匹配 BF16"这一结论为准。

## 4. 计算/通信/显存三角取舍分析

- **计算**：MXFP8 走 Blackwell 原生 MX Tensor Core 路径，计算峰值与 FP8 相当，但因为量化覆盖的张量更多（传统 FP8 方案中保留高精度的路径也能压下来），端到端算力利用率更高。代价几乎为零——scale 管理由硬件数据格式承担，这是 MX 相对软件 FP8 方案的本质优势。
- **通信**：更多张量低比特化意味着分布式训练中的通信（梯度、激活）也有压缩空间，不过本文重点是预训练数值配方，通信侧未作为主要卖点。
- **显存**：量化张量增多直接降低激活显存占用；master weight 与优化器状态仍需高精度，整体显存收益小于"位宽减半"的理论值。

核心取舍：**把 scale 管理从软件负担变成数据格式属性**。这看似是工程细节，实质是降低了低比特训练的工程门槛——配方化之后，MXFP8 可以像 BF16 一样成为默认选项。

## 6. 局限性与启发

局限性：

- 验证规模上限是 8B 参数，前沿模型（百亿到千亿以上）上的结论需要外推。
- 论文聚焦 MXFP8，对 MXFP4 只作为格式家族背景提及——真正的 4-bit 训练由后续工作（如 NVFP4 预训练论文）承接。
- "匹配 BF16"是训练曲线层面的结论，具体下游任务的细微差异需看正文。

启发：

- **数据格式本身是算法设计空间**：MX 格式把"scale 粒度"从超参数变成了数据类型属性，这种硬件-格式-算法的协同设计是后摩尔时代的主旋律。
- 低比特训练的竞争焦点正在从"能不能做"转向"配方是否简单可复制"——谁能把配方收敛到"无脑默认"，谁就赢了工程 adoption。
- 这篇（MXFP8 配方）与 NVFP4 预训练论文连起来读，正好构成 NVIDIA 在 Blackwell 时代的低比特训练路线图：先把 FP8 做成默认，再把 4-bit 做到可用。

## 7. 面试视角

**可能的问题**："Blackwell 的 MX 格式相比 Hopper 时代的 FP8 训练有什么本质进步？"

**一句话答案**：MX 把细粒度 per-block scale 做成了硬件原生数据格式，scale 不再靠软件滑窗维护，因此可以安全量化更多张量；配合选对的数值转换算法，MXFP8-E4M3 预训练在 8B/15T token 规模上能匹配 BF16 训练曲线。
