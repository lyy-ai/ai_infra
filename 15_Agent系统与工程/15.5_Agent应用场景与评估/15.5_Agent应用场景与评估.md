# 15.5 Agent 应用场景与评估

> 学习目标：了解 Agent 的主要落地场景及其负载特征，掌握 Agent 系统的评估方法论（结果评估 vs 过程评估），以及常见的失败模式与可靠性工程手段。

## 1. 主要应用场景

### 1.1 编程（Coding Agent）

最成熟的场景（见 15.4 专题）：issue 修复、功能开发、代码审查、重构迁移、测试生成。负载特征：长会话（几十到几百轮）、高前缀复用、工具调用密集。

### 1.2 深度研究（Deep Research）

模型自主进行多轮"搜索 → 阅读 → 综合"循环，产出带引用的研究报告（各厂商 2025 年的标配功能）。负载特征：超长输入（几十上百个网页）、超长输出、单次任务 token 消耗可达百万级——是 prefix cache 与长上下文技术的天然受益者。

### 1.3 数据分析与办公自动化

Agent 写代码操作数据（pandas/SQL）、生成图表与报告；办公场景操作文档/表格/邮件。负载特征：代码执行沙箱是刚需；错误容忍度中等（结果可人工复核）。

### 1.4 客服与业务运营

客服 agent 调用订单/物流/退款 API 处理用户请求；运营 agent 执行审批流。负载特征：高并发、短轨迹（3-10 轮）、强确定性要求——通常用显式工作流（LangGraph 类）而非完全自主循环，且动作白名单严格。

### 1.5 RPA 与 GUI 操作（Computer Use）

模型直接看屏幕截图、操作鼠标键盘（computer use / browser use 类）。负载特征：多模态输入（每轮带截图，token 消耗大）、环境状态复杂、动作延迟敏感；目前是"演示惊艳、生产谨慎"的阶段，可靠性是主要瓶颈。

### 1.6 具身智能（Embodied Agent）

VLA 模型驱动机器人（见 5.10 章与 openpi）：感知 → 规划 → 动作。负载特征：硬实时约束（控制频率）、端侧部署、安全优先。

## 2. Agent 评估方法论

Agent 评估比模型评估难一个维度：**评估对象从"输出文本"变成"行为轨迹"**。

### 2.1 结果评估（Outcome-based）

只看最终任务是否完成：SWE-bench（补丁是否通过测试）、τ-bench（客服场景终态是否正确）、OSWorld/WebArena（操作系统/网页任务的终态检查）。

- 优点：客观、可自动化。
- 缺点：无法区分"漂亮的成功"与"侥幸的成功"；对失败原因无诊断力。

### 2.2 过程评估（Process/Trajectory-based）

分析轨迹质量：步骤效率（是否绕路）、工具使用正确率、无效动作比例、自我纠错能力。常用 LLM-as-judge 或人工标注。

- 优点：有诊断力，能指导改进。
- 缺点：贵、主观性、评判模型自身的偏差。

### 2.3 成本与效率评估

Agent 评估的第三根轴：**单位任务的 token 消耗与墙钟时间**。两个 agent 解题率相同，成本差 5 倍是常见现象——生产选型必须看"成功率-成本"帕累托前沿，而不是单一成功率。

### 2.4 主要 benchmark 速览

| Benchmark | 场景 | 判定方式 |
|-----------|------|---------|
| SWE-bench (Verified) | GitHub issue 修复 | 补丁通过项目测试 |
| τ-bench / τ²-bench | 客服对话（航空/零售/电信） | 终态数据库一致性 |
| OSWorld | 真实 OS 任务 | 系统终态检查 |
| WebArena / WorkArena | 网页操作 | 页面终态/信息正确性 |
| Terminal-Bench | 终端命令行任务 | 环境终态检查 |

## 3. 常见失败模式（生产环境真实分布）

1. **目标漂移**：长轨迹中逐渐偏离原始任务（对策：todo list、周期性重述目标）。
2. **工具误用**：参数错误、选错工具（对策：工具描述工程、调用前 schema 校验）。
3. **环境误读**：把工具报错当成功继续（对策：错误信息显式化、关键步骤验证节点）。
4. **循环卡死**：重复同一无效动作（对策：重复检测 + 强制换路 + 步数熔断）。
5. **过度自信**：没验证就宣布完成（对策：要求"声明完成前必须给出验证证据"的提示规则）。
6. **上下文中毒**：早期错误信息留在上下文里持续误导后续决策（对策：错误修正后改写/压缩历史）。
7. **权限越界**：尝试超出授权的操作（对策：权限系统硬拦截，而非提示词软约束）。

## 4. 可靠性工程清单（生产 Agent 上线前）

- [ ] 每个工具都有：schema 校验、超时、重试策略、明确的错误描述。
- [ ] 关键动作有确定性验证（编译/测试/状态检查），不依赖模型自我声明。
- [ ] 预算熔断：步数、token、墙钟三重上限。
- [ ] 权限最小化：默认拒绝，按需白名单；危险操作人工确认。
- [ ] 完整轨迹日志：可回放、可审计（出问题后能定位是哪一步错了）。
- [ ] 评估集回归：每次模型/harness 升级跑固定任务集，成功率与成本双指标门禁。
- [ ] 注入防护：不可信内容（网页/邮件/用户粘贴）做标记隔离，不直接当指令执行。

## 6. 面试视角

- **Q：Agent 怎么评估？** A：三根轴——结果（任务成功率，SWE-bench/τ-bench 类终态判定）、过程（轨迹质量：绕路率/工具正确率）、成本（单位任务 token 与时间）；生产看成功率-成本帕累托前沿。
- **Q：Agent 上线最大的风险是什么？** A：可靠性（错误沿轨迹累积）与安全性（权限越界、prompt 注入）；对应的工程手段是验证节点、预算熔断、权限硬拦截与轨迹审计。
- **Q：哪些场景适合 agent，哪些不适合？** A：适合——结果可验证、错误可恢复、价值密度高（编程、研究、数据分析）；不适合——错误不可逆（资金操作）、强实时（毫秒级控制）、完全不可验证的开放判断。
