# 15.2 Agent Harness 架构解剖

> 学习目标：理解"模型之外的一切"——Agent Harness（智能体运行时外壳）的六大核心组件：循环驱动、工具系统、上下文管理、权限与安全、状态持久化、子代理与协议。这是理解 Claude Code/OpenCode 等现代 Coding Agent 的基础。

## 1. 什么是 Harness

业界共识逐渐形成：**Agent = Model + Harness**。模型负责"想"，Harness（挽具/外壳）负责其他一切：

```text
┌───────────────────────── Harness ──────────────────────────┐
│  Agent Loop（循环驱动）                                      │
│    ├── System Prompt 装配（角色/工具说明/环境信息/记忆注入）    │
│    ├── Tool System（工具注册、参数校验、执行、结果封装）          │
│    ├── Context Manager（上下文窗口管理：截断/压缩/隔离）         │
│    ├── Permission & Sandbox（权限模式、危险操作拦截、沙箱）       │
│    ├── Session & State（会话持久化、断点恢复、任务追踪）          │
│    └── Subagent / Protocol（子代理、MCP/A2A 等外部协议）         │
└──────────────────────┬─────────────────────────────────────┘
                       │ messages in / tool calls out
                 ┌─────┴─────┐
                 │    LLM     │
                 └───────────┘
```

关键认知：**同一个模型，配不同 Harness，表现出来的"智能"天差地别**。2024-2026 年 Agent 产品的竞争很大程度上是 Harness 工程质量的竞争（模型公司提供参考实现，产品公司在 Harness 上做差异化）。

## 2. 组件一：Agent Loop（循环驱动）

核心循环的实现要点：

- **停止条件**：模型输出不含工具调用（判定为完成）、步数上限、token 预算上限、用户中断。
- **并行工具调用**：模型一步可发多个独立调用（如同时读三个文件），Harness 并行执行后一起回填——延迟优化的重要手段。
- **流式处理**：边生成边解析工具调用，生成完立即执行（不等完整响应）。
- **中断与恢复**：用户随时打断（Ctrl-C），Harness 要保证工具执行的副作用可处理（半完成的文件编辑）。

## 3. 组件二：Tool System（工具系统）

工具系统是 Harness 与世界的接口，设计要点远超"注册几个函数"：

1. **工具描述就是提示工程**：工具的名称、docstring、参数描述直接决定模型用得对不对。差描述导致模型误用（如把 `grep` 当 `find` 用）。
2. **结果封装**：工具输出要"为模型而设计"——截断策略（太长怎么办）、结构化（带行号的文件内容）、错误描述（"文件不存在"还要给出"你是否想找这些相似路径？"）。
3. **确定性优先**：能确定性执行的逻辑不要留给模型（如编辑冲突检测、语法校验放在工具内部）。
4. **最小完备集**：工具不是越多越好。Claude Code 的核心工具只有十几个（read/write/edit/bash/glob/grep...）——工具少而精，模型选择准确率高；工具泛滥反而降低决策质量。

## 4. 组件三：Context Manager（上下文管理）

Harness 技术含量最高的组件。策略谱系：

| 策略 | 机制 | 代表 |
|------|------|------|
| 硬截断 | 丢弃最老消息（危险：丢失关键上下文） | 简单 demo |
| 摘要压缩 | 超阈值时让模型总结早期历史，替换为摘要 | Claude Code compaction |
| 工具结果外置 | 大输出存文件/存储，上下文只留引用 | 多种 harness |
| 子代理隔离 | 脏活派给 subagent，主上下文只收结论 | Claude Code Task 工具 |
| 分层记忆 | 重要事实写入持久记忆文件，每次会话注入 | CLAUDE.md / memory |

上下文管理的本质矛盾：**信息完整性 vs 窗口经济性**——丢多了 agent 变"健忘"，塞满了成本高且模型注意力被稀释（长上下文下模型对中间内容的利用下降，"lost in the middle"现象）。

## 5. 组件四：Permission & Sandbox（权限与安全）

Agent 能改文件、执行命令，安全模型是产品化的分水岭：

- **权限模式谱系**：全自动（YOLO/dangerously-skip-permissions，仅限沙箱）→ 白名单自动 + 危险操作确认（默认）→ 全人工确认（plan 模式，只读不写）。
- **细粒度规则**：按工具 + 参数模式授权（"允许 npm test，但 bash rm -rf 要确认"），规则可持久化到项目配置。
- **沙箱执行**：不可信代码（模型生成的脚本、第三方包）在隔离环境执行（容器/gVisor/Firecracker 微 VM）——云端 agent 产品（如各类云端 coding agent）的标配。
- **注入防护**：工具结果可能包含恶意指令（网页/ issue 里的"忽略之前的指令"）——prompt injection 是 Agent 特有攻击面，对策包括内容标记、权限最小化、危险操作二次确认。

## 6. 组件五：Session & State（状态持久化）

- **会话持久化**：完整消息历史落盘（JSONL 等），支持崩溃恢复与会话回放（resume/rewind）。
- **任务追踪**：长任务用显式任务列表（todo list）跟踪进度——这同时是给模型看的"外部工作记忆"，防止长轨迹中丢失目标。
- **状态 vs 无状态**：引擎层（模型 API）无状态，全部状态在 Harness 侧——这让模型提供方可以替换（多 provider 支持的基础）。

## 7. 组件六：Subagent 与协议

- **Subagent（子代理）**：主 agent 通过工具调用派生子 agent：独立上下文、可限定工具子集与系统提示、并行执行、结果汇总回主上下文。用途：上下文隔离（探索类脏活）、角色特化（审查/测试）、并行加速。
- **MCP（Model Context Protocol）**：Anthropic 2024 末发起的开放协议，标准化"工具/数据源接入"——任何服务实现 MCP server（暴露 tools/resources/prompts），任何 Harness 实现 MCP client 即可接入。价值：工具生态与 Harness 解耦（一次实现，处处可用）。
- **A2A（Agent2Agent）**：Google 2025 年发起的协议，标准化 agent 之间的发现与协作（跨组织的多 agent 互操作）。与 MCP 的关系：MCP 解决"agent 接工具"，A2A 解决"agent 接 agent"。

## 8. 设计取舍总结

| 取舍 | 牺牲 | 换取 |
|------|------|------|
| 上下文压缩 | 历史细节可能丢失 | 长任务可持续、成本可控 |
| 工具最小集 | 个别场景表达力不足 | 模型选择准确率高 |
| 权限确认 | 打断自动化流程 | 安全可控、用户信任 |
| 子代理 | 额外 token 开销 | 上下文隔离、并行 |
| 严格沙箱 | 环境逼真度下降（网络/依赖受限） | 安全边界 |

## 10. 面试视角

- **Q：Agent 系统的架构分层？** A：模型层（无状态推理）+ Harness 层（循环/工具/上下文/权限/状态/子代理）+ 环境层（工具背后的真实世界与沙箱）；模型可替换的关键是状态全在 Harness 侧。
- **Q：上下文爆炸怎么处理？** A：压缩摘要、工具结果外置引用、子代理隔离、分层持久记忆；核心是"上下文是稀缺资源，每个 token 都要论证其存在价值"。
- **Q：MCP 解决了什么问题？** A：工具接入的 N×M 问题——N 个 Harness × M 个工具的重复适配，标准化后各实现一次即可互通。
