# 15.4 Coding Agent 专题（Claude Code / OpenCode / Aider / Cursor 原理）

> 学习目标：理解为什么编程是 Agent 的第一个杀手级场景，以及主流 Coding Agent 的架构原理与设计模式差异——终端派（Claude Code/OpenCode/Aider）vs IDE 派（Cursor/Windsurf），以及它们的共同组件与关键取舍。

## 1. 为什么 Coding 是 Agent 的第一个杀手级场景

1. **奖励可验证**：代码有编译器、测试、类型检查做确定性裁判——Agent 的错误能被立刻发现并自动修正（这正是 15.1 节"验证节点"的理想形态）。
2. **文本原生**：代码、diff、日志都是文本，模型的输入输出零损耗。
3. **工具体系现成**：shell、git、grep、编译器——环境即工具，无需专门建设。
4. **价值密度高**：编程是高价人力活动，自动化收益立竿见影。
5. **数据飞轮**：使用过程产出海量高质量轨迹数据，反哺模型训练（coding 是 agentic RL 的第一富矿）。

## 2. Claude Code 原理解剖（终端派的标杆）

Claude Code 是 Anthropic 的终端原生 coding agent，被公认为当前 harness 设计的标杆之一。按 15.2 的组件模型拆解：

1. **Agentic 循环**：模型自主驱动的"探索 → 计划 → 编辑 → 验证"循环；一次任务几十轮工具调用是常态。
2. **工具集（少而精）**：文件读写编辑（Read/Write/Edit）、搜索（Glob/Grep）、执行（Bash）、网络（WebFetch/WebSearch）、任务管理（TodoWrite）、子代理（Task）、笔记（NotebookEdit）等约二十个。注意**没有"专门读代码的 AST 工具"**——刻意的取舍：用通用工具 + 强模型，胜过维护一堆特化工具。
3. **搜索优先的探索**：理解代码库靠 agentic search（glob 找文件 → grep 找符号 → read 精读），而不是预建索引——优点是对任何代码库零配置即时可用，且永远读到最新状态。
4. **任务管理（TodoWrite）**：长任务显式维护 todo list——既是进度追踪，也是给模型的"外部工作记忆"，显著降低长轨迹跑偏率。
5. **上下文压缩（Compaction）**：接近窗口上限时自动摘要早期对话保留关键状态，任务可以跑几个小时不"失忆"。
6. **权限模式**：白名单自动执行 + 危险操作确认 + plan 只读模式三档；规则可按工具+命令模式细粒度配置并持久化到项目。
7. **记忆体系（CLAUDE.md）**：项目级/用户级记忆文件自动注入上下文——团队规范、构建命令、架构约定写一次，每次会话生效。
8. **可扩展点**：Subagent（自定义角色 + 独立上下文）、Hooks（生命周期事件挂钩自定义命令）、MCP（接入外部工具生态）、Headless 模式（脚本化/CI 集成）。

**设计哲学总结**：强模型 + 简单通用的工具 + 精心的上下文工程，而不是复杂的编排框架——"模型是发动机，harness 只做底盘"。

## 3. OpenCode 原理（开源对照组）

OpenCode 是 SST 团队的开源终端 coding agent（MIT 协议），是研究"一个现代 coding agent harness 怎么实现"的最佳开源样本：

1. **Provider 中立**：模型可插拔（Anthropic/OpenAI/本地模型等）——体现"状态全在 harness 侧"的架构原则，换模型不换工作流。
2. **客户端/服务器架构**：agent 逻辑在服务端进程，TUI（终端界面）只是客户端——天然支持远程驱动、多界面（TUI/桌面/IDE 插件）、会话共享。
3. **与 Claude Code 对照的组件**：同样有文件/搜索/执行工具集、子代理、权限模式、MCP 支持、会话持久化——验证 15.2 的组件模型是行业收敛的共识，而非某家专利。
4. **学习路径**：读它的源码能完整看到一个生产级 harness 的循环驱动、工具抽象、上下文管理与 TUI 渲染分层（对照 13.5 的源码阅读方法论）。

## 4. Aider 与编辑格式问题（一个关键的技术分岔口）

Aider（开源、Python）把"模型怎么改代码"这个问题显式化了——**编辑格式（edit format）是 coding agent 的核心技术点**：

| 编辑格式 | 机制 | 优点 | 缺点 |
|---------|------|------|------|
| 整文件重写 | 模型输出完整新文件 | 简单可靠 | token 消耗大、大文件不可行 |
| diff/udiff | 输出标准 diff | 省 token | 模型 diff 格式易错、应用失败率高 |
| search/replace 块 | 输出"原文块→新文块"对 | 定位准、容错好（Aider 与 Claude Code 的 Edit 都采用） | 原文块不唯一时需处理歧义 |

Aider 的另一特色是 **repo map**：用 tree-sitter 提取全库符号签名生成"地图"注入上下文，让模型不读文件也知道代码库结构——这是"agentic search"之外的另一条探索路线（预索引 vs 动态搜索）。

## 5. IDE 派：Cursor / Windsurf / Copilot agent mode

IDE 派与终端派的核心差异在**上下文来源与人机界面**：

1. **上下文优势**：IDE 知道用户打开了哪些文件、光标在哪、选中了什么、lint 错误是什么——这些"用户注意力信号"终端派拿不到，IDE 派天然拥有。
2. **预建索引**：IDE 派普遍对代码库预建嵌入索引（codebase indexing），检索走"语义搜索 + 精确读取"混合；终端派主打零配置的 agentic search。两条路线在实践中互相渗透。
3. **交互粒度**：IDE 派保留"逐条 diff 确认"的细粒度人工介入界面；终端派更倾向"给一个目标，跑完看结果"的粗粒度委托。
4. **趋势**：两派在合流——IDE 加 agent 模式（Copilot agent mode、Cursor agent），终端派出 IDE 插件（Claude Code 的 VS Code/JetBrains 集成）。

## 6. 云端异步派：Codex / Devin / GitHub Copilot Workspace

第三条路线是把 agent 跑在云端沙箱：用户提需求 → agent 在云容器里独立工作 → 产出 PR 给人 review。

- 架构关键：**沙箱基础设施**（每个任务一个隔离容器，预装依赖）+ 异步任务管理 + PR 产物化。
- 与本地派的取舍：不占用本地环境、天然并行多任务，但环境逼真度（内部系统访问、机密配置）是硬约束。
- 这本质是"agent 即服务"的 infra 问题（呼应 15.6 节的沙箱与调度讨论）。

## 7. 共同的设计模式（面试可以总结的"收敛共识"）

1. 工具集小而通用（文件/搜索/执行/网络 + 少量特化），拒绝工具泛滥。
2. 上下文工程是核心竞争力：探索策略（搜索 vs 索引）、压缩、子代理隔离。
3. 编辑走 search/replace 块或工具内校验，避免裸 diff。
4. 显式任务追踪（todo list）对抗长轨迹跑偏。
5. 权限分层 + 危险操作确认，信任是逐步建立的。
6. 记忆文件（CLAUDE.md 类）承载项目知识，比微调便宜一万倍。
7. 可验证环节自动化（跑测试/编译）是可靠性的最大杠杆。

## 8. 评测：SWE-bench 与它的局限

- **SWE-bench**（普林斯顿）：从真实 GitHub issue 构造任务，agent 产出补丁，跑项目测试判定解决与否；Verified 子集（人工筛过的 500 题）是当前 coding agent 的通用标尺。
- **局限**：只测"修 issue"一种形态；测试可被针对性过拟合；不衡量成本（解题花多少 token）与交互体验。看榜单时同时关注"解题率 vs 平均成本"两条曲线。

## 10. 面试视角

- **Q：Claude Code 为什么强？** A：强模型 + 简单通用工具集 + 顶级上下文工程（agentic search/compaction/todo/subagent）；它的设计哲学是"不替模型做决策，只为模型扫清障碍"。
- **Q：终端派和 IDE 派 coding agent 的差异？** A：上下文来源（动态搜索 vs IDE 索引+用户注意力信号）、交互粒度（目标委托 vs 逐条确认）、环境假设（任意终端 vs 绑定编辑器）；两派正在合流。
- **Q：coding agent 怎么改代码（编辑格式）？** A：主流是 search/replace 块（定位准、容错好），整文件重写适合小文件，裸 diff 因格式错误率高已被多数产品放弃。
