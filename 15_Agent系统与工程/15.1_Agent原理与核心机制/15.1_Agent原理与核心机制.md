# 15.1 Agent 原理与核心机制

> 学习目标：理解 LLM Agent 的本质（一个由模型驱动的循环）、四种经典模式（ReAct/Plan-Execute/Reflexion/Multi-Agent）、以及 Agent 系统的三个核心工程问题（上下文爆炸、错误累积、循环失控）。

## 1. Agent 的本质：模型 + 循环

传统 LLM 应用是"一问一答"（单次前向）；Agent 是把模型放进一个**循环**里：

```text
┌──────────────────────────────────────────────┐
│  loop:                                       │
│    观察(环境状态/工具结果) → 思考(模型推理)    │
│      → 行动(调用工具/输出) → 观察新结果 → ...  │
│  直到模型判断"任务完成"或达到停止条件           │
└──────────────────────────────────────────────┘
```

模型在循环中扮演"决策者"：每一步根据全部历史上下文决定下一步动作。这个简单的结构变化带来了质的不同：

- **能力边界扩展**：模型不再局限于训练数据内的知识，可以通过工具获取实时信息、操作外部世界。
- **错误可以累积**：单轮问答的错误是静态的，Agent 的错误会沿轨迹传导放大——**可靠性成为第一工程问题**。
- **成本结构改变**：一个 Agent 任务的 token 消耗是单轮问答的 10-100 倍（每轮都携带全部历史）。

## 2. 四种经典模式

### 2.1 ReAct（Reasoning + Acting）

最基础的模式：每一步显式交替"思考（Thought）→ 行动（Action）→ 观察（Observation）"。

```text
Thought: 我需要先找到配置文件的位置
Action: glob("**/*.yaml")
Observation: ["config/deploy.yaml", ...]
Thought: 找到了，现在读取它
Action: read("config/deploy.yaml")
...
```

- 优点：决策过程可解释、实现简单（现代模型的 tool calling 已内化此模式）。
- 缺点：无全局规划，容易"走一步看一步"陷入局部。

### 2.2 Plan-and-Execute

先让模型产出完整计划（步骤列表），再逐步执行，必要时 replan。

- 优点：长任务有全局结构，不易跑偏；计划可被人审查后再执行。
- 缺点：计划基于执行前的信息，环境变化时计划失效，replan 成本高。

### 2.3 Reflexion（反思）

任务失败或结束后，让模型回顾轨迹、总结失败原因写入"经验记忆"，下次尝试时注入上下文。

- 优点：不更新权重就实现"从失败学习"。
- 缺点：反思质量受模型自我评估能力限制；记忆膨胀需要管理。

### 2.4 Multi-Agent

多个角色化 agent 协作：编排者（orchestrator）+ 工作者（worker）、辩论（debate）、流水线（pipeline）。

- 优点：角色分工带来上下文隔离（每个 agent 的 context 更小更专注）；并行子任务。
- 缺点：协调成本与 token 消耗倍增；多 agent 的错误传播更难调试。**工程共识：能单 agent 解决就不要上多 agent**——多 agent 是上下文隔离的手段，不是目的。

## 3. 工具调用（Tool Use）的原理

工具调用是现代 Agent 的基石，机制上分四层：

1. **工具描述**：以 JSON Schema 描述工具名、参数、用途，注入 system prompt。
2. **模型决策**：模型输出结构化调用请求（工具名 + 参数 JSON）——现代模型原生训练了 tool calling 能力，输出受约束解码（constrained decoding）保证格式合法。
3. **Harness 执行**：运行时解析调用请求、执行真实工具（文件操作/API 调用/代码执行）、把结果作为新消息追加进上下文。
4. **循环继续**：模型看到工具结果，继续决策。

关键认知：**工具结果进入上下文 = 环境信息进入模型的唯一通道**。工具设计（返回什么、返回多少、错误怎么描述）直接决定 Agent 的能力上限——这就是"工具工程"（tool engineering）。

## 4. 记忆（Memory）的三个层次

| 层次 | 载体 | 生命周期 | 工程问题 |
|------|------|---------|---------|
| 工作记忆 | 上下文窗口内的对话历史 | 单次会话 | 会爆（见下节） |
| 情景记忆 | 会话摘要、经验笔记（如 CLAUDE.md、memory 文件） | 跨会话 | 写什么、何时更新 |
| 语义记忆 | RAG 检索的外部知识库 | 长期 | 检索质量、相关性 |

Agent 的记忆设计 = "把什么信息、以什么形式、在什么时机放进上下文"——上下文是唯一真实的工作记忆，其余都是往上下文里填东西的策略。

## 5. 三个核心工程问题

### 5.1 上下文爆炸

每轮循环 = 系统提示 + 全部历史（思考 + 工具调用 + 工具结果）一起进模型。工具结果（文件内容、日志、网页）动辄几千 token，几十轮后上下文轻松突破 100k+。对策：

- **压缩/摘要**：历史超过阈值时用模型摘要早期轮次（Claude Code 的 compaction）。
- **工具结果截断**：大输出截断 + 保留引用（存文件，上下文里只留路径和摘要）。
- **子代理隔离**：把"读一堆文件找答案"类任务派给 subagent，主上下文只接收结论（见 15.2 节）。

### 5.2 错误累积

N 步任务、每步成功率 p，整体成功率 ≈ p^N。p=0.95、N=20 时只剩约 36%。对策：

- **缩短轨迹**：更强的单步能力（好模型）胜过精巧的多步框架。
- **验证节点**：关键步骤后插入确定性校验（编译、测试、schema 校验），失败立即回退而非继续错下去。
- **预算熔断**：步数/token 上限，防止错误轨迹无限烧钱。

### 5.3 循环失控

Agent 陷入重复无效动作（反复读同一个文件、反复调用同一个失败的 API）。对策：重复检测（最近 k 步动作去重）、强制推进（注入"请换个思路"提示）、步数硬上限。

## 7. 面试视角

- **Q：Agent 和"多轮对话"的本质区别？** A：Agent 的循环由模型自主驱动（自己决定何时调工具、何时停止），且动作会改变外部世界状态；多轮对话只是用户与模型的交替。
- **Q：Agent 系统最大的工程挑战是什么？** A：可靠性（错误沿轨迹累积，p^N 效应）与上下文管理（工具结果导致的上下文爆炸），两者都比"框架选型"重要。
- **Q：什么时候该用多 agent？** A：当单个上下文装不下或角色间需要上下文隔离时（如代码审查 agent 不应看到实现 agent 的思维过程）；多 agent 是隔离手段而非能力增强手段。
