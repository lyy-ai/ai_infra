# 15.3 主流 Agent 框架与生态

> 学习目标：摸清 Agent 开发框架的格局与选型逻辑——从代码优先的编排框架（LangGraph/CrewAI/AutoGen）到模型厂官方 SDK（OpenAI Agents SDK），到低代码平台（Dify/Coze），以及两大协议（MCP/A2A）的生态意义。

## 1. 格局总览

Agent 框架按抽象层级分四类：

```text
低代码平台   │ Dify / Coze(扣子) / n8n        —— 拖拽编排，业务人员可用
角色扮演框架 │ CrewAI / MetaGPT / AgentVerse   —— 多 agent 角色分工
状态机框架   │ LangGraph                       —— 图结构显式控制流
轻量 SDK    │ OpenAI Agents SDK / smolagents  —— 薄封装，贴近模型能力
协议层      │ MCP（工具接入）/ A2A（agent 互操作）—— 跨框架的标准化
```

行业趋势（2024-2026 的演进共识）：**框架越来越薄**——早期框架试图用复杂编排弥补模型能力不足；模型变强后，"给模型好工具 + 简单循环"往往胜过复杂编排。选型时先问：这个框架提供的价值是模型做不到的，还是只是在替模型"代驾"？

## 2. 主要项目档案

| 框架 | 背景 | 核心抽象 | 适用场景 | 仓库 |
|------|------|---------|---------|------|
| **LangGraph** | LangChain 团队 | 图（节点=计算/模型调用，边=条件转移），显式状态机 + checkpoint 持久化 | 需要精确控制流、可中断恢复的生产级 agent | github.com/langchain-ai/langgraph |
| **CrewAI** | 社区 | 角色（role）+ 任务（task）+ 团队（crew）的多 agent 编排 | 快速搭建角色分工型多 agent 原型 | github.com/crewAIInc/crewAI |
| **AutoGen / AG2** | 微软 → 社区分叉 | 以"对话"为原语的多 agent 框架，agent 间消息驱动 | 研究型多 agent 对话/辩论实验 | github.com/microsoft/autogen |
| **OpenAI Agents SDK** | OpenAI | 轻量：agent + handoff（移交）+ guardrail（护栏）+ tracing | OpenAI 生态内的快速开发 | github.com/openai/openai-agents-python |
| **smolagents** | HuggingFace | 极简；特色是 CodeAgent——agent 直接写 Python 代码当动作（而非 JSON 工具调用） | 教学、轻量原型 | github.com/huggingface/smolagents |
| **MetaGPT** | 社区 | 把软件公司角色（PM/架构师/工程师）建模为 agent 流水线 | 多角色协作生成软件的实验 | github.com/FoundationAgents/MetaGPT |
| **Dify / Coze** | 国内平台 | 可视化工作流 + 知识库 + 插件市场 | 企业内部快速搭建 AI 应用（RAG+轻 agent） | github.com/langgenius/dify |

## 3. 两种设计哲学的对照

**显式编排（LangGraph 代表）**：开发者画图，模型只在节点内做局部决策。
- 优点：可控、可测试、可复现；适合容错要求高的生产场景。
- 缺点：流程僵化，模型能力被编排上限封顶。

**自主循环（Claude Code/OpenCode 等 harness 代表）**：开发者给工具和目标，模型自己决定路径。
- 优点：能力随模型升级自动提升；能处理编排者没想到的路径。
- 缺点：行为不可完全预测，需要权限/预算等安全网。

实践中的主流答案是**混合**：外层用显式流程控制关键节点（如必须人工审批的环节），节点内部用自主循环。

## 4. MCP 详解（生态最重要的一块拼图）

**Model Context Protocol**（Anthropic 2024 年 11 月发起，现已成为事实标准）：

```text
Host（Claude Code / IDE / 任意 Harness）
  └── MCP Client ──（stdio / HTTP+SSE）── MCP Server
                                              ├── tools（可调用函数）
                                              ├── resources（可读取的数据）
                                              └── prompts（预设模板）
```

- **解决的问题**：工具接入的 N×M 重复适配。没有 MCP 时，每个 Harness 都要为 GitHub/数据库/浏览器各写一套集成；有了 MCP，工具方实现一次 server，所有支持 MCP 的 Harness 直接用。
- **生态现状**：主流 agent 产品（Claude Code、Cursor、OpenCode 等）均已支持；社区已有数千个开源 MCP server（数据库、云服务、设计工具、支付等）。
- **学习建议**：给自己常用的内部系统写一个 MCP server，是理解"工具工程"的最佳练手项目。

## 5. A2A 与多 agent 互操作

**A2A（Agent2Agent）**（Google 2025 年发起）：定义 agent 的"能力名片"（Agent Card）与任务委托协议，让不同厂商/框架的 agent 能互相发现、委派任务、交换产物。

- 与 MCP 的分工：MCP 是 agent→工具的协议，A2A 是 agent→agent 的协议。
- 现状判断：协议本身在快速演进，多 agent 互操作的真实落地仍以"同组织内自定义 RPC"为主——A2A 值得跟踪，但还不是必修课。

## 6. 选型决策树

```text
需求是什么？
├── 企业内部 AI 应用（RAG+简单流程，非技术团队维护）→ Dify/Coze
├── 生产级 agent 服务（要控制流、可恢复、可观测）→ LangGraph
├── 快速原型/研究多 agent 协作 → CrewAI / AutoGen
├── 深度绑定某家模型 API → 对应官方 SDK（OpenAI Agents SDK 等）
└── 做 agent 产品/工具 → 不套框架，自己写 harness（参考 15.2 组件模型）
                          + MCP 接工具生态
```

## 8. 面试视角

- **Q：LangGraph 和直接写 while 循环的区别？** A：LangGraph 提供显式状态机 + checkpoint（可中断恢复）+ 可视化与观测生态；while 循环简单灵活但持久化/恢复要自己做。简单场景 while 循环足够，生产复杂流程 LangGraph 的收益在工程化。
- **Q：现在学 Agent 框架的建议？** A：先学原理（15.1/15.2），框架按需要再学——框架半年一迭代，原理（循环/工具/上下文/权限）不过时；警惕"会十个框架但讲不清 agent loop"的本末倒置。
- **Q：MCP 会不会成为行业标准？** A：已经是事实标准（主流产品全支持）；它的意义类似 LSP 对 IDE——把工具生态从具体产品里解放出来。
