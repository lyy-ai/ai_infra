# 15.6 Agent 与 AI Infra 的结合

> 学习目标：这是本章与本仓库主线的汇合点——Agent 负载给推理 infra 带来的新问题（长会话/前缀复用/工具调用往返）、Agentic RL 的基础设施（rollout=环境交互、沙箱池）、以及 Agent 任务的成本模型。

## 1. Agent 负载的独特性（对推理系统而言）

Agent 流量和普通聊天流量的负载特征完全不同：

| 维度 | 普通聊天 | Agent 负载 |
|------|---------|-----------|
| 会话长度 | 几轮到几十轮 | 几十到几百轮工具调用 |
| 上下文增长 | 缓慢 | 每轮 +数千 token（工具结果），单会话轻松破 100k |
| 前缀重复率 | 中（多轮共享历史） | **极高**（system prompt+工具说明+全部历史逐轮累积重发） |
| 输出长度 | 数百 token | 每轮短输出（一次工具调用），但总轮数多 |
| 延迟敏感度 | TTFT 敏感 | **每轮都敏感**——循环内串行，100 轮 × 每轮 3s = 5 分钟任务 |
| 并发模式 | 请求间独立 | 长会话保持 + 子代理扇出（一个任务瞬时多个并发流） |

## 2. Agent 负载下的 Serving 优化要点

### 2.1 Prefix Cache 是第一生命线

Agent 每轮请求 = 旧前缀（系统提示+工具说明+历史，可能 100k+）+ 增量（最新工具结果，几百 token）。没有 prefix cache，每轮都重算整个前缀的 prefill——成本直接爆炸且 TTFT 不可接受。

- **会话亲和路由**变得关键：同一会话的请求必须路由到持有其 KV 的实例（llm-d 的前缀感知路由、Mooncake 的 KVCache 中心化调度的价值在 Agent 场景被放大）。
- **前缀稳定是 harness 设计约束**：system prompt、工具列表、历史消息的任何中间插入/修改都会使后续前缀失配——这就是为什么主流 harness 都把可变内容（时间戳、动态状态）放到消息尾部而不是头部。**KV cache 友好性已经成为 harness 设计的硬指标。**

### 2.2 长上下文技术直接兑现

单会话 100k-1M 上下文使 5.12 章的技术从"锦上添花"变成"生存必需"：KV 分层 offload（冷历史落 CPU/SSD）、稀疏/线性注意力架构、上下文压缩（harness 侧 compaction 与模型侧稀疏化互补）。

### 2.3 子代理扇出与并发治理

一个 Agent 任务可能扇出多个子代理并行（每个是独立的长会话）——对 serving 是"脉冲式并发"：单个用户任务瞬时放大成 N 条长会话流。容量规划必须按"任务数 × 平均扇出 × 每流 KV"估算，而非按请求 QPS。

### 2.4 工具调用往返（Round-trip）延迟

Agent 的墙钟时间 ≈ 轮数 ×（模型推理 + 工具执行 + 编排开销）。模型推理只是其中一环：

- 工具执行本地化（文件/ shell 在同一机器）vs 远程化（MCP over HTTP）差一个量级。
- 并行工具调用、推测性预取（预测下一步可能要读的文件提前加载）是 harness 侧的延迟优化。
- 对引擎侧：decode 小批量低延迟比大 batch 高吞吐更重要——Agent 负载的 batching 配比与吞吐型流量不同。

## 3. Agentic RL：后训练的新基础设施

Agent 能力是 RL 训出来的，而 Agentic RL 的 rollout 不是"生成一段文本"，是"与环境交互一条轨迹"：

1. **rollout = 轨迹**：actor 在真实/模拟环境中多轮交互（调工具、读结果、再决策），一条轨迹几十轮、几百 k token——rollout 成本与长尾问题比单轮 RLHF 严重一个量级。
2. **环境成为新的基础设施**：代码沙箱池（每个 rollout worker 需要隔离的代码执行环境）、浏览器农场、工具模拟器——环境的吞吐与稳定性直接决定 RL 训练速度。环境是"第三种算力"（训练 GPU、推理 GPU 之外）。
3. **异步化是必然**：轨迹长度方差极大（10 轮到 500 轮），同步批量 rollout 的长尾不可接受——AReaL 式全异步架构（12.6 论文）在 agentic RL 中是刚需而非优化。
4. **可验证奖励（RLVR）的主场**：coding（测试通过）、数学（答案核对）的确定性奖励让 agentic RL 避免了奖励模型的 hack 问题——这也是 coding agent 进步最快的深层原因。
5. **框架支持**：verl/slime/ROLL 都在加强 agentic 能力（多轮 rollout、工具调用环境、轨迹级数据流）——见 13.3 章。

## 4. 沙箱基础设施（Sandbox Infra）

Agent（尤其 coding agent）让"代码执行沙箱"从边缘需求变成核心 infra：

- **隔离技术选型**：容器（Docker，快但共享内核）→ gVisor（用户态内核，平衡）→ 微 VM（Firecracker/Kata，强隔离，云端多租户必选）。
- **关键指标**：冷启动时间（毫秒级才能随 rollout 按需创建）、镜像预置依赖的完备度、并发密度（一台物理机跑多少沙箱）。
- **资源治理**：沙箱内代码不可信——CPU/内存/磁盘/网络四层限额；出口网络默认白名单（防数据外泄与挖矿）。
- **回收与泄漏**：Agent 任务的沙箱生命周期管理（僵尸沙箱是云成本黑洞）。

## 5. Agent 任务的成本模型

Agent 使"每请求成本"变成"每任务成本"，估算框架：

```text
单任务成本 = 轮数 × (平均上下文 × prefill单价(1-前缀命中率) + 输出token × decode单价)
          + 沙箱/工具执行成本 + 失败重试的放大系数
```

量级直觉（用本目录 `agent_cost_model.py` 验证）：

- 单轮问答：一次 prefill+decode，成本基准 1×。
- 典型 coding agent 任务：50 轮 × 平均 60k 上下文，即使前缀命中率 90%，成本也是单轮的 50-100 倍。
- 前缀命中率从 90% 提到 99%，Agent 成本可能再降一半——**在 Agent 时代，prefix 命中率就是利润率**。

## 6. 对从业者的启示（AI Infra 岗位视角）

1. **Agent 是推理 infra 的下一波需求主体**：各家 agent 产品的用量增长正在重塑 serving 集群的负载画像（长会话、高复用、扇出并发）——懂 Agent 负载特征的 infra 工程师稀缺。
2. **环境工程是新岗位方向**：沙箱池、工具模拟、评测基础设施——"AI Infra for Agents"正在形成独立分工。
3. **Agentic RL 是训练与推理的真正合流点**：同时懂 vLLM 优化与 FSDP 训练的人在这个方向有结构性优势（呼应 6.11 章的初衷）。
4. **Harness 工程介于产品与 infra 之间**：上下文工程（KV 友好性）、会话亲和、成本治理——这些同时是产品问题与 infra 问题。

## 8. 面试视角

- **Q：Agent 负载对推理系统的新挑战？** A：超长会话与上下文增长（KV 容量）、极高前缀复用（prefix cache 与会话亲和路由成生命线）、子代理扇出的脉冲并发、循环串行导致的每轮延迟敏感。
- **Q：Agentic RL 和普通 RLHF 的系统差异？** A：rollout 从单次生成变成多轮环境交互轨迹——环境（沙箱池）成为第三种算力，轨迹长尾使异步化成为刚需，可验证奖励（代码测试）是奖励设计的主线。
- **Q：怎么估算一个 Agent 产品的推理成本？** A：按任务而非按请求——轮数 ×（上下文 × prefill 成本 × (1-前缀命中率) + 输出 × decode 成本），前缀命中率是最大杠杆。
