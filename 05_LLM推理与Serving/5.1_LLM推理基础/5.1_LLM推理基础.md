## 1. 什么是 LLM 推理？

### 1.1 与训练的区别

| 阶段 | 目的 | 是否更新权重 | 计算特点 | 主要资源消耗 |
|------|------|-------------|---------|-------------|
| **训练** | 让模型学习知识 | 是 | 前向 + 反向传播，batch 大 | 大量计算、显存、数据 |
| **推理** | 用训练好的模型生成答案 | 否 | 仅前向传播，通常是 autoregressive | 显存、访存带宽、解码延迟 |

训练的本质是“优化参数”，推理的本质是“使用参数生成文本”。

### 1.2 推理两个阶段

LLM 推理通常分为两个阶段：

1. **Prefill（预填充 / 提示处理）阶段**
   - 将用户输入 prompt 一次性喂给模型。
   - 计算 prompt 中每个 token 的 KV Cache。
   - 输出 prompt 最后一个 token 的 logits。

2. **Decode（解码 / 生成）阶段**
   - 自回归地逐个生成新 token。
   - 每次生成都需要把新生成的 token 作为输入，并复用之前计算好的 KV Cache。

```
Prompt: "今天天气"

Prefill:  今 → 天 → 天 → 气   (一次性处理，生成 KV Cache)
Decode:   很 → 好 → 。        (逐个生成，复用 KV Cache)
Output:   "今天天气很好。"
```

## 2. LLM 推理完整链路

### 2.1 输入处理

用户输入通常是原始字符串，例如：

```text
请介绍一下机器学习中的梯度下降算法。
```

### 2.2 分词（Tokenization）

Tokenizer 将字符串切分为 token ID 序列。不同模型的 token 划分粒度不同：

```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
text = "请介绍一下机器学习中的梯度下降算法。"
inputs = tokenizer(text, return_tensors="pt")
print(inputs["input_ids"])  # 形状: [1, n_tokens]
```

输出可能是类似 `[151644, 8948, 198, ...]` 的整数序列。每个整数代表词表中的一个 token。

### 2.3 嵌入层（Embedding）

Token ID 通过 Embedding 层映射为连续向量：

```
Token ID: [t1, t2, t3, t4]
Embedding: [v1, v2, v3, v4]  (每个 vi 是 d_model 维向量)
```

### 2.4 Transformer 层前向传播

经过多层的 Self-Attention 和 FFN 计算，模型输出每个位置的 logits：

```
logits = model(input_ids)  # 形状: [batch_size, seq_len, vocab_size]
```

### 2.5 解码生成

取最后一个位置的 logits，通过 softmax 得到概率分布，采样生成下一个 token。然后把这个新 token 拼接到序列末尾，再次输入模型，循环往复。

## 3. 自回归生成（Autoregressive Generation）

### 3.1 核心思想

LLM 生成文本的方式是**逐个预测下一个 token**：

$$
P(y_1, y_2, \ldots, y_T \mid x) = P(y_1 \mid x) \times P(y_2 \mid x, y_1) \times \cdots \times P(y_T \mid x, y_1, \ldots, y_{T-1})
$$

每次只生成一个 token，然后把生成的 token 作为历史，继续生成下一个。

### 3.2 为什么需要 KV Cache？

在自回归生成中，第 t 步需要计算 token t 与所有历史 token 的注意力。如果不做缓存，每步都要重新计算所有历史 token 的 Key 和 Value，造成大量重复计算。

**KV Cache 就是把这些历史 K、V 张量存起来，避免重复计算。**

### 3.3 带 KV Cache 的生成流程

```python
# 简化示意
kv_cache = None
for i in range(max_new_tokens):
    outputs = model(input_ids, past_key_values=kv_cache)
    logits = outputs.logits[:, -1, :]
    next_token = sample(logits)
    input_ids = next_token.unsqueeze(0)
    kv_cache = outputs.past_key_values
```

实际使用时，现代框架（如 transformers）会自动处理 `use_cache=True` 和 `past_key_values`。

## 4. KV Cache 详解

### 4.1 KV Cache 是什么？

对于每一层 Transformer，每个 token 都会生成一个 Key 向量和一个 Value 向量：

- Key: `[batch_size, num_kv_heads, seq_len, head_dim]`
- Value: `[batch_size, num_kv_heads, seq_len, head_dim]`

在 decode 阶段，每生成一个新 token，就把它的 K、V 追加到 cache 中。这样 Self-Attention 只需要计算新 token 的 query，然后与所有历史 K 做内积。

### 4.2 KV Cache 显存占用估算

对于单个序列：

```
KV Cache (bytes) = 2 × num_layers × num_kv_heads × seq_len × head_dim × bytes_per_element
                 = 2 × L × H_kv × S × D × sizeof(dtype)
```

例如 Qwen2.5-7B-Instruct：

- `num_layers = 28`
- `num_kv_heads = 4`
- `head_dim = 128`
- `seq_len = 8192`
- `dtype = fp16`

```
KV Cache = 2 × 28 × 4 × 8192 × 128 × 2 bytes
         ≈ 469 MB
```

如果 `batch_size=4`，且每个序列长度为 8192，则 KV Cache 约为 1.9 GB。

### 4.3 KV Cache 增长特点

- 随 `batch_size` 线性增长。
- 随 `seq_len` 线性增长。
- 随 `num_layers` 和 `num_kv_heads` 线性增长。
- 与 `hidden_size` 的关系：通常 `head_dim = hidden_size / num_heads`，因此也与 hidden_size 相关。

### 4.4 KV Cache 的局限性

1. **显存占用大**：长上下文 + 大 batch 时，KV Cache 可能超过模型权重本身。
2. **碎片化**：变长序列导致 cache 分配不均匀。
3. **需要优化**：因此诞生了 PagedAttention、KV Cache 量化、MQA/GQA、FlashAttention 等技术。

## 5. 解码策略（Decoding Strategies）

### 5.1 贪心解码（Greedy Decoding）

每次选择概率最大的 token：

```python
next_token = torch.argmax(logits, dim=-1)
```

- 优点：确定性、速度快、可重复。
- 缺点：容易生成重复、 boring 的文本，缺乏多样性。

### 5.2 Beam Search（束搜索）

同时维护多个候选序列（beam），每步选择概率乘积最高的 k 个：

```python
model.generate(..., num_beams=4, early_stopping=True)
```

- 优点：在翻译、摘要等任务上通常质量更高。
- 缺点：显存占用增加，不适合开放域生成。

### 5.3 采样解码（Sampling）

从概率分布中随机采样，引入多样性：

```python
model.generate(
    ...,
    do_sample=True,
    temperature=0.7,
    top_k=50,
    top_p=0.9,
)
```

#### Temperature

控制分布的平滑程度：

- `temperature < 1`：更保守，倾向于高概率 token。
- `temperature > 1`：更随机，增加多样性。

#### Top-k Sampling

只从概率最高的 k 个 token 中采样。

#### Top-p Sampling（Nucleus Sampling）

从累计概率达到 p 的最小 token 集合中采样。

#### Repetition Penalty

惩罚重复出现的 token，缓解模型“车轱辘话”：

```python
repetition_penalty=1.1
```

## 6. 推理性能指标

### 6.1 核心指标定义

| 指标 | 英文 | 含义 | 说明 |
|------|------|------|------|
| **首 token 延迟** | TTFT (Time To First Token) | 从接收请求到输出第一个 token 的时间 | 主要受 Prefill 阶段影响 |
| **每 token 延迟** | TPOT (Time Per Output Token) | 生成每个后续 token 的平均时间 | 主要受 Decode 阶段影响 |
| **总延迟** | Latency | 完整生成所有 token 的时间 | Latency ≈ TTFT + TPOT × (N-1) |
| **吞吐** | Throughput | 单位时间内生成的 token 数或请求数 | 通常越高越好 |
| **每秒 token 数** | TPS (Tokens Per Second) | 生成阶段每秒生成的 token 数 | 常用单请求吞吐指标 |
| **并发数** | Concurrency | 同时处理的请求数量 | 受显存和计算限制 |

### 6.2 指标计算示例

假设：
- Prefill 耗时 100ms
- Decode 每 token 耗时 50ms
- 生成 128 个新 token

则：
- TTFT = 100 ms
- TPOT = 50 ms
- Latency = 100 + 50 × 127 = 6.45 s
- TPS = 1 / 0.05 = 20 tok/s
- Throughput（单请求）= 20 tok/s

### 6.3 指标之间的关系

- **Latency 与 Throughput 通常是 trade-off**：降低 latency 可能需要减少 batch，从而降低 throughput。
- **TTFT 与 TPOT 关注点不同**：TTFT 影响用户体验的“等待感”，TPOT 影响流式输出的流畅度。
- **长上下文会同时影响 TTFT 和 TPOT**：Prefill 时间随 prompt 长度增加；KV Cache 增大也会增加每步 decode 成本。

## 7. LLM 推理显存分析

### 7.1 显存占用组成

总显存 ≈ 模型权重 + KV Cache + 激活值 + 框架/计算图开销

| 组成部分 | 影响因素 | 说明 |
|---------|---------|------|
| **模型权重** | 参数量、精度 | FP16 约 2 bytes/param；INT8 约 1 byte/param；INT4 约 0.5 bytes/param |
| **KV Cache** | batch_size、seq_len、num_layers、num_kv_heads、head_dim、dtype | 长上下文和大 batch 时占主导 |
| **激活值** | batch_size、seq_len、hidden_size | 前向传播中的中间张量 |
| **框架开销** | 计算图、CUDA context、缓存分配器 | 通常几十 MB 到几 GB |

### 7.2 显存估算示例

以 Qwen2.5-7B-Instruct，FP16 推理为例：

- 模型权重：7B × 2 bytes = 14 GB
- KV Cache（batch=1, seq_len=4096）：2 × 28 × 4 × 4096 × 128 × 2 bytes ≈ 234 MB
- 激活值：较小，通常几十到几百 MB
- 总显存：约 15 GB

如果 batch=4，seq_len=8192：

- KV Cache：2 × 28 × 4 × 8192 × 128 × 2 bytes × 4 ≈ 1.9 GB
- 总显存：约 16 GB

### 7.3 显存瓶颈判断

1. 如果权重占主导 → 考虑量化模型权重。
2. 如果 KV Cache 占主导 → 考虑减少 batch、缩短上下文、KV Cache 量化、PagedAttention。
3. 如果激活占主导 → 考虑梯度检查点（训练场景更多见）或 FlashAttention。

## 8. 代码实践：使用 transformers 进行推理

该脚本位于 `examples/basic_inference.py`，包含：

4. **TTFT 与 TPOT** 分离测量。
5. **Greedy / Sampling / Beam Search** 三种解码策略对比。

下面将脚本中的核心代码片段拆解出来，便于理解每个环节。

### 8.1 基础生成代码

```python
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

model_name = "Qwen/Qwen2.5-7B-Instruct"

tokenizer = AutoTokenizer.from_pretrained(model_name, trust_remote_code=True)
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    trust_remote_code=True,
    torch_dtype=torch.float16,
    device_map="auto",
)

prompt = "请介绍一下机器学习中的梯度下降算法。"
inputs = tokenizer(prompt, return_tensors="pt").to(model.device)

with torch.no_grad():
    outputs = model.generate(
        **inputs,
        max_new_tokens=128,
        do_sample=True,
        temperature=0.7,
        top_p=0.9,
        repetition_penalty=1.1,
    )

response = tokenizer.decode(outputs[0], skip_special_tokens=True)
print(response)
```

### 8.2 测量推理性能

```python
import time
import torch

inputs = tokenizer(prompt, return_tensors="pt").to(model.device)
num_input_tokens = inputs["input_ids"].shape[1]

start = time.time()
with torch.no_grad():
    outputs = model.generate(
        **inputs,
        max_new_tokens=128,
        do_sample=True,
        temperature=0.7,
        top_p=0.9,
    )
end = time.time()

num_output_tokens = outputs.shape[1] - num_input_tokens
latency = end - start
tps = num_output_tokens / latency
print(f"Latency: {latency:.3f}s")
print(f"Generated tokens: {num_output_tokens}")
print(f"TPS: {tps:.2f}")
```

### 8.3 分离 Prefill 与 Decode 时间

```python
import time

# Prefill 阶段：只跑一次 forward，获取第一个输出 token
start = time.time()
prefill_outputs = model.generate(
    **inputs,
    max_new_tokens=1,
    do_sample=True,
    temperature=0.7,
    top_p=0.9,
)
ttft = time.time() - start
print(f"TTFT: {ttft*1000:.2f} ms")

# Decode 阶段：继续生成后续 token
new_input = prefill_outputs
start = time.time()
full_outputs = model.generate(
    new_input,
    max_new_tokens=127,
    do_sample=True,
    temperature=0.7,
    top_p=0.9,
)
decode_time = time.time() - start
num_decode_tokens = full_outputs.shape[1] - new_input.shape[1]
tpot = decode_time / num_decode_tokens * 1000
print(f"TPOT: {tpot:.2f} ms")
print(f"TPS: {1000/tpot:.2f}")
```

> 注意：上述代码使用 `model.generate()` 测量 TTFT 不是最精确的方式，因为 `generate()` 内部有额外开销。更精确的方法可以直接调用 `model(**inputs)` 测量一次完整 forward 的时间。

## 9. 常见推理优化方向

### 9.1 量化（Quantization）

- 权重量化：INT8、INT4、NF4、GPTQ、AWQ。
- KV Cache 量化：INT8、FP8、2-bit KIVI。

### 9.2 高效注意力实现

- **FlashAttention / FlashAttention-2**：减少 HBM 访存，提升 attention 计算效率。
- **PagedAttention**：将 KV Cache 分块管理，减少内存碎片，提高并发。

### 9.3 批处理与调度

- **Continuous Batching**：动态批处理，提高 GPU 利用率。
- **Speculative Decoding**：用小模型预测多个 token，再用大模型验证，加速 decode。
- **Medusa / Lookahead Decoding**：类似思想，通过预测加速生成。

### 9.4 服务化框架

- **vLLM**：基于 PagedAttention 的高吞吐 LLM 服务引擎。
- **TensorRT-LLM**：NVIDIA 高性能推理框架。
- **TGI (Text Generation Inference)**：Hugging Face 的推理服务框架。
- **SGLang**：支持结构化生成与多轮对话优化。

## 10. 常见问题与排查

### 10.1 推理时出现 OOM

- 检查 prompt 长度是否过长。
- 检查 batch size 是否过大。
- 使用 `torch_dtype=torch.float16` 或量化模型。
- 使用 `device_map="auto"` 让模型自动分配到多卡或 CPU。

### 10.2 生成速度慢

- 确认是否启用了 `use_cache=True`（默认开启）。
- 检查 GPU 是否被正确利用。
- 考虑使用 FlashAttention 或更高效的服务框架。
- 减少 `max_new_tokens` 或降低采样温度。

### 10.3 输出重复或质量差

- 提高 `repetition_penalty`。
- 调整 `temperature` 和 `top_p`。
- 使用更长的 prompt 或 few-shot 示例。

### 10.4 结果不稳定

- 采样策略会导致随机性，设置 `temperature=0` 或 `do_sample=False` 获得确定性输出。
- 设置随机种子。

## 12. 本节小结

1. LLM 推理分为 **Prefill** 和 **Decode** 两个阶段：Prefill 处理 prompt 并构建 KV Cache，Decode 自回归生成后续 token。
2. **KV Cache** 是避免重复计算、提升 decode 效率的关键，但会随 batch 和序列长度线性增长。
3. 常见解码策略包括 **Greedy、Beam Search、Sampling（Top-k/Top-p/Temperature）**，各有适用场景。
4. 关键性能指标：**TTFT、TPOT、Latency、Throughput、TPS**，它们之间存在 trade-off。
5. 显存主要由 **模型权重、KV Cache、激活值** 组成，优化方向因病因而异。
6. `transformers` 提供了开箱即用的推理接口，但实际生产环境需要更专业的服务化框架。
