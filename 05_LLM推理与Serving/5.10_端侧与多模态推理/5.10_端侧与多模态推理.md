# 5.10 端侧与多模态推理

## 课程概述

最后一节把视角从数据中心推向 **端侧（edge/on-device）**：机器人、车载、手机、AR/VR、摄像头与嵌入式盒子。端侧多模态推理的目标不是单纯追求云端吞吐，而是在 **内存、功耗、散热、离线可用、隐私与实时性** 约束下，让多模态模型稳定工作。

本节课覆盖三个方向：

- 开源大模型适配：Qwen 系列、VLA 系列
- 端侧多模态模型轻量化与推理优化
- 端侧共线多模态模型部署

学完本节后，你将能够：

1. 估算 Qwen-VL / VLA 类模型在端侧的权重、KV Cache、图像 token 与 workspace 内存。
2. 说明 VLA 模型 action chunk 的 token 预算与控制频率之间的关系。
3. 设计端侧多模型共线部署的资源准入、优先级与降级策略。

---

## 1. 端侧多模态推理的约束

| 维度 | 云端 Serving | 端侧多模态推理 |
|------|--------------|----------------|
| 算力 | 数据中心 GPU，可扩容 | SoC/NPU/小型 GPU，固定且有限 |
| 内存 | 几十 GB 到数 TB | 几 GB 到几十 GB，且与系统共享 |
| 功耗/散热 | 相对宽松 | 严格，长时间运行会降频 |
| 网络 | 可用云端检索/工具 | 可能离线，必须本地闭环 |
| 延迟 | TTFT/TPOT SLO | 控制回路 deadline，错过可能不安全 |
| 模型数量 | 通常单模型服务 | ASR/VLM/LLM/TTS/规划/安全监控共存 |

端侧设计原则：

> 先定义 **必须实时完成的任务**（安全、控制、语音唤醒），再决定大模型/VLM 能分到多少内存与算力。

## 2. 开源大模型适配：Qwen 系列

### 2.1 Qwen / Qwen-VL 适配点

适配 Qwen 系列多模态模型时，不只要加载权重，还要对齐整条输入链路：

- tokenizer 与 chat template。
- image processor：resize、normalization、patch size、tile 策略。
- vision encoder 与 projector 的 dtype、输入 shape。
- image token 在 prompt 中的位置与特殊 token。
- KV Cache：文本 token 与 image token 是否共享同一 KV 空间。
- 量化：LLM 权重、vision encoder、projector 是否分开量化。

对应脚本：

```bash
python examples/edge_multimodal_memory_estimator.py
```

脚本估算：

```text
weight_gib = params_b × bits / 8
kv_gib = 2 × layers × kv_heads × head_dim × dtype_bytes × (image_tokens + text_tokens)
total ≈ llm_weight + vision_weight + projector + kv + workspace
```

典型结论：

- LLM 权重先做 weight-only INT8/INT4，通常收益最大。
- 高分辨率图片会显著增加 image tokens，进而增加 vision prefill 与 KV Cache。
- 端侧不能只看 LLM 权重大小，KV Cache 与 workspace 可能决定能否常驻。

### 2.2 Qwen 端侧部署路径

| 路径 | 适用 | 注意点 |
|------|------|--------|
| llama.cpp / GGUF | CPU/小 GPU，快速验证 | 多模态支持取决于具体分支 |
| MLC LLM | 跨平台编译部署 | 需要模型转换与调优 |
| ONNX Runtime / OpenVINO | Intel/通用 NPU | 图优化与算子覆盖要验证 |
| TensorRT | NVIDIA/Jetson | 性能强，但转换与插件成本高 |
| MNN / NCNN / ExecuTorch | 手机/嵌入式 | 算子覆盖、量化与内存复用是重点 |
| vLLM edge server | 边缘盒子/局域网服务 | 更接近云端体验，但资源占用高 |

## 3. 开源大模型适配：VLA 系列

### 3.1 VLA 的输入输出

VLA（Vision-Language-Action）把视觉、语言指令映射到动作：

```text
image/state + instruction → VLA → action tokens → de-tokenize → robot/vehicle action
```

适配时除了 VLM 的部分，还要处理：

- action tokenizer：连续动作离散化（bins）或回归头。
- action chunk：一次预测未来 H 步动作。
- 控制频率：模型推理频率必须与执行器频率匹配。
- 状态反馈：上一帧动作是否完成，是否需要 replan。

对应脚本：

```bash
python examples/vla_action_budget_estimator.py
```

核心估算：

```text
action_tokens = action_dim × tokens_per_dim × horizon_steps
budget_ms = horizon_steps / control_hz × 1000
required_decode_tps = action_tokens / (budget_ms / 1000)
```

### 3.2 VLA 端侧优化杠杆

- 缩短 `horizon_steps`：更快 replan，但长期一致性变差。
- 减少 `action_dim` 或合并自由度：降低 decode token 数。
- 降低 `tokens_per_dim`：更粗的动作离散化，需验证控制精度。
- 减少 image/prompt tokens：降低 prefill，让更多预算留给 action decode。
- action caching / warm start：若环境变化小，复用上一 chunk 的部分动作。

### 3.3 开源参照：openpi（Physical Intelligence 的 VLA 开源项目）

**openpi**（github.com/Physical-Intelligence/openpi）是机器人基础模型公司 Physical Intelligence（π）的开源仓库，是目前 VLA 领域最完整的开源参照，适合配合本节理解 VLA 推理的系统约束。

**模型矩阵**（均提供在 10,000+ 小时机器人数据上预训练的 base checkpoint，可微调）：

| 模型 | 动作头路线 | 推理特征 |
|------|-----------|---------|
| π0 | flow matching（流匹配）动作头 | 动作生成是多步去噪过程，单步延迟高于一次前向，但动作连续性好 |
| π0-FAST | 自回归 + FAST 动作 tokenizer | 动作被离散成 token 序列逐 token 生成——正是 3.1 节 `action_tokens` 预算模型的直接实例 |
| π0.5 | 在 π0 基础上改进开放世界泛化（knowledge insulation 训练） | 仓库中仅支持 flow matching 头的训练与推理 |

**对 infra 学习者有价值的点**：

1. **两条动作头路线 = 两种推理延迟结构**：flow matching 用"固定步数去噪"换连续动作，自回归（FAST）用"decode 步数 × 每步延迟"换离散动作——对照本节 3.1 的预算公式，可以定量比较两种路线在目标控制频率下的可行性。
2. **官方显存档位表**是端侧/单卡部署的实用参考：推理 > 8GB（RTX 4090 可跑）、LoRA 微调 > 22.5GB、全量微调 > 70GB（A100/H100）；多卡仅支持单节点 `fsdp_devices`，尚不支持多节点训练。
3. **工程栈现实**：原始实现为 JAX，2025 年 9 月增加 PyTorch 支持；依赖 LeRobot 数据格式；官方明确提示"模型为本公司机器人开发，迁移到其他平台不保证成功"——具身模型的泛化边界与部署适配是真实业务难题。
4. **微调成本分层**（LoRA vs 全量）正是第 7 章量化与 6.3 章 ZeRO 显存估算的应用场景。

## 4. 端侧多模态模型轻量化与推理优化

### 4.1 轻量化组合拳

| 技术 | 主要收益 | 风险 |
|------|----------|------|
| Weight-only INT4/INT8 | 权重内存大幅下降 | 精度损失，敏感层需保留高精度 |
| KV Cache 量化 | KV 内存与带宽下降 | 长上下文/多图时误差累积 |
| 剪枝/蒸馏 | 真正减少计算 | 训练成本高，结构变化大 |
| LoRA merge | 部署时无 adapter 开销 | 多任务切换不灵活 |
| image token reduction | 降低视觉 prefill 与 KV | 细粒度视觉能力下降 |
| early exit / smaller VLM | 降低平均延迟 | 最坏情况仍要兜底 |

### 4.2 端侧推理优化清单

- 静态 shape：固定图片分辨率、tile 数、最大文本长度。
- 预分配 buffer：图像、image embedding、KV、logits、action buffer。
- 图捕获：稳定子图用 CUDA Graph / 等效机制降低 launch 抖动。
- 算子融合：layernorm、projection、reshape、dequant、action detokenize。
- 量化策略分层：LLM INT4，vision/projector INT8，敏感 head FP16。
- 热管理：长时间运行按温度动态降分辨率、降帧率或切换小模型。

## 5. 端侧共线多模态模型部署

### 5.1 什么是“共线部署”

端侧常见不是单一 VLM，而是多个模型同时在线：

```text
麦克风 → ASR ┐
摄像头 → VLM ├→ LLM/Planner → TTS/动作/显示
传感器 → Safety Monitor ────────┘
```

这些模型共享同一颗 SoC 的 CPU/GPU/NPU 与内存。共线部署的关键是 **资源准入与优先级**：

- safety monitor 必须 pinned，不能被大模型挤出内存。
- planner/control 有 deadline，不能被 VLM 长推理阻塞。
- VLM 可以作为增强能力，内存不足时降级、延迟或拒绝。

对应脚本：

```bash
python examples/edge_colocated_scheduler.py
```

脚本模拟 `safety / asr / tts / planner / vlm` 共用 8GiB 端侧内存，比较：

- `no_limit`：不做内存准入，大 VLM 与 planner/safety 一起挤占资源。
- `memory_limit`：safety 与 planner pinned，VLM 只有在不破坏 pinned 模型时才允许加载。

### 5.2 工程策略

1. **常驻集最小化**：只把安全、唤醒、控制必需模型常驻。
2. **大模型按需加载**：VLM/LLM 用完可卸载或降级，但必须控制加载抖动。
3. **内存准入**：加载前检查 `used + model_mem <= capacity × safety_ratio`。
4. **优先级与抢占**：safety/control 可抢占 ASR/TTS/VLM；流式任务要可取消。
5. **降级链路**：高精度 VLM → 小 VLM → 模板/规则 → 安全默认行为。
6. **热/电联动**：温度过高时先降 VLM 频率与图片分辨率，而不是影响 safety。

## 6. 常见问题与排查

### 6.1 端侧上 VLM 精度明显下降

- 检查 image processor 与训练时是否一致：resize、normalize、tile、patch。
- LLM INT4 精度损失大时，保留 embedding、lm_head、projector 高精度。
- 用真实端侧图片分布做校准集，而不是只用通用图文数据。

### 6.2 VLA 动作抖动或延迟超标

- action chunk 太长，导致 replan 不及时；缩短 horizon 或提高推理频率。
- action tokens 过多，decode 时间超标；减少 action_dim/tokens_per_dim。
- 图像 prefill 占用过多预算；降低 image tokens 或复用视觉特征。

### 6.3 多模型共线后系统不稳定

- 内存没有准入，大模型把安全/控制模型挤出。
- 模型加载/卸载抖动导致 deadline 偶发 miss；改为常驻小模型 + 大模型懒加载。
- 温度降频后仍按高负载调度；加入热状态到调度策略。

## 8. 本节小结

1. 端侧多模态推理的核心矛盾是：模型越来越大，但端侧内存、功耗与实时性预算是固定的。
2. Qwen-VL 适配要对齐 tokenizer、image processor、projector、image token 与 KV Cache；轻量化通常从 LLM 权重 INT8/INT4 与 image token 控制开始。
3. VLA 适配要额外管理 action tokenizer 与 action chunk：`horizon × control_hz` 决定 replan 延迟预算，`action_dim × tokens_per_dim` 决定 decode 负担。
4. 端侧共线部署必须做资源准入与优先级：safety/control pinned，大模型按需加载，必要时拒绝或降级。
5. 真正可用的端侧系统不是没有大模型，而是大模型失效、超时、降频时，系统仍有安全默认行为。
