# 项目专题：简历项目写法与 vLLM 集群实战

## 课程概述

这一节不讲新算法，而是把前面所有技术点沉淀成 **可写进简历、可复现、可面试追问** 的项目。核心原则：

> 简历项目不是“我搭过”，而是“我在什么硬件/什么负载下，用什么技术，把哪个指标从多少优化到多少，并如何验证”。

本目录包含一个可运行项目骨架：**基于 vLLM 部署 Qwen2-0.5B-Instruct 推理集群并压测**。模型路径：

```text
/data/models/Qwen2-0.5B-Instruct
```

## 1. 简历项目写法：STAR + 指标 + 证据

### 1.1 推荐结构

每个项目 bullet 尽量包含：

```text
场景/约束 → 技术方案 → 关键优化 → 量化结果 → 验证方法
```

示例骨架：

```text
基于 <框架> 搭建 <模型> 推理服务，支持 <能力>；针对 <瓶颈>，
通过 <PagedAttention/Continuous Batching/Prefix Cache/量化/自定义算子> 优化，
在 <硬件> 与 <并发/prompt 分布> 下，将 <吞吐/延迟/显存> 从 <baseline> 优化到 <结果>，
并用 <压测脚本/精度回归/灰度指标> 验证。
```

### 1.2 避免的问题

- 只写“熟悉 vLLM/TensorRT”，没有模型、硬件、负载和指标。
- 只写“提升 4 倍”，没有 baseline 和测试条件。
- 把课程 demo 写成生产系统；面试追问时会露馅。
- 指标互相矛盾：吞吐提升但延迟恶化却不解释。

## 3. Qwen2-0.5B vLLM 集群实战：如何做出“4 倍吞吐”

### 3.1 Baseline 必须先定义

建议至少保留三组数据：

| 实验 | 配置 | 目的 |
|------|------|------|
| baseline | 单实例，`max_num_seqs=1` 或较小并发 | 模拟 naive serving |
| tuned single | 单实例，调大 `max_num_seqs`，开启 prefix caching | 看单机优化空间 |
| cluster | 多实例 + nginx 路由 | 看水平扩容与负载均衡 |

关键参数：

- `MAX_NUM_SEQS`：同时调度的请求数，过小会限制 Continuous Batching。
- `GPU_MEM_UTIL`：显存利用率，过低浪费，过高容易 OOM。
- `MAX_MODEL_LEN`：过长会预留更多 KV 空间，降低并发。
- `ENABLE_PREFIX_CACHING`：相同 system prompt/高重复 prompt 下收益明显。

### 3.2 压测口径

使用 `benchmark_qwen2_concurrency.py` 时，建议记录：

- GPU 型号与显存、CUDA/vLLM 版本。
- 实例数、每实例 `max_num_seqs`。
- 请求数、并发数、prompt 长度分布、max_tokens。
- throughput tok/s、req/s、成功率、p50/p95 延迟。
- 是否使用相同 prompt（`--same-prompt`）以观察 prefix cache 收益。

### 3.3 面试追问准备

- 为什么吞吐能提升？是 batch 变大、KV 管理更好，还是多实例分流？
- 延迟有没有恶化？p95/p99 怎么样？
- 如果并发继续增加到 500，瓶颈会在 GPU、KV Cache、网络还是 nginx？
- Qwen2-0.5B 这么小，为什么还需要集群？答案应偏向实验复现与方法论，而不是夸大生产必要性。

## 6. 本节小结

1. 好简历 = 真实场景 + 明确瓶颈 + 技术方案 + 量化指标 + 可复现证据。
2. Qwen2-0.5B 适合做低成本实验：重点展示你对 vLLM 参数、Continuous Batching、PagedAttention、集群路由与压测方法的理解。
3. “提升 4 倍”必须绑定 baseline、硬件、并发、max_tokens 和延迟指标，否则面试容易被追问。
4. 项目目录中的启动脚本、Nginx 示例与压测脚本可作为简历项目的最小可复现闭环。
