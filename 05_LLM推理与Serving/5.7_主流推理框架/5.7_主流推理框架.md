# 5.7 主流推理框架

## 课程概述

前面几节讲的是“技术点”：KV Cache、PagedAttention、Continuous Batching、Speculative Decoding、Prefix Cache、PD 解耦。实际落地时，团队通常不会从零实现这些能力，而是选择一个推理框架。本节课对主流 LLM 推理/Serving 框架做一个工程化对比，帮助你根据业务场景选型。

学完本节后，你将能够：

1. 说出 vLLM、TGI、TensorRT-LLM、SGLang、LMDeploy、DeepSpeed-MII 的定位差异。
2. 从吞吐、延迟、量化、结构化输出、OpenAI 兼容、PD 解耦等维度比较框架。
3. 用 OpenAI-compatible API 对不同框架做统一冒烟测试。
4. 给出不同业务场景下的初选方案与验证路径。

> 注意：推理框架迭代很快，本节内容用于建立选型框架；具体参数、特性和性能以最新官方文档与实测压测为准。

---

## 1. 选型时应该看哪些维度？

不要只问“哪个最快”，而要先明确业务约束：

| 维度 | 关键问题 |
|------|----------|
| 模型支持 | 是否支持你的模型架构、tokenizer、chat template、多模态？ |
| API 兼容 | 是否暴露 OpenAI-compatible API？是否方便迁移现有应用？ |
| 吞吐/延迟 | TTFT、TPOT、throughput 是否满足 SLO？长 prompt 还是长输出？ |
| KV/Prefix | 是否支持 PagedAttention、Prefix Cache、Chunked Prefill？ |
| 高级优化 | 是否支持 Speculative Decoding、PD Disaggregation、KV Cache 量化？ |
| 量化 | AWQ/GPTQ/FP8/INT8/FP4 支持到什么程度？精度损失是否可接受？ |
| 结构化输出 | JSON schema、grammar、regex、工具调用是否稳定？ |
| 分布式 | 多 GPU TP/PP、跨节点、异构硬件、autoscaling 是否成熟？ |
| 运维 | 日志、指标、tracing、health check、灰度升级是否完善？ |
| 生态 | 文档、社区、issue 响应、与现有栈（HF/NVIDIA/国产模型）匹配度 |

## 2. 主流框架速览

### 2.1 vLLM

**定位**：Python 友好的高吞吐 LLM serving 引擎，核心是 PagedAttention + Continuous Batching。

优势：

- OpenAI-compatible API 成熟，迁移成本低。
- PagedAttention、Prefix Caching、Chunked Prefill、Speculative Decoding 等能力完善。
- 社区活跃，文档和示例丰富。
- 离线 `LLM` 类和在线 server 都好用。

局限：

- 极致 NVIDIA kernel 调优通常不如 TensorRT-LLM。
- 多框架/多模型一致性需要测试，尤其是新模型结构。

典型启动方式（示例，需按版本调整）：

```bash
python -m vllm.entrypoints.openai.api_server \
  --model /data/models/Qwen3.5-9B \
  --dtype float16 \
  --gpu-memory-utilization 0.85 \
  --max-model-len 4096 \
  --port 8000
```

适合：快速搭建 OpenAI 兼容服务、通用在线推理、课程实验和中小规模生产。

---

### 2.2 TGI（Text Generation Inference）

**定位**：Hugging Face 官方推理服务框架，和 transformers 生态衔接紧密。

优势：

- 对 HF 模型支持顺畅，模型卡、tokenizer、pipeline 生态一致。
- 生产化能力完整：路由、指标、流式输出、量化支持。
- 适合已经深度使用 Hugging Face 的团队。

局限：

- 某些最新优化或特定模型结构的支持节奏可能与 vLLM/SGLang 不同。
- 极致定制 kernel 能力通常不如 TensorRT-LLM。

典型启动方式（示例）：

```bash
text-generation-launcher \
  --model-id /data/models/Qwen3.5-9B \
  --port 8000 \
  --max-input-length 4096 \
  --max-total-tokens 8192
```

适合：HF 生态团队、需要稳定生产 API、希望减少自研 serving 代码。

---

### 2.3 TensorRT-LLM

**定位**：NVIDIA 推出的高性能推理框架，目标是在 NVIDIA GPU 上接近硬件极限。

优势：

- kernel、量化、FP8/FP4、in-flight batching 等性能潜力强。
- 对 NVIDIA 新硬件特性支持快。
- 适合对成本极度敏感的大规模 GPU 推理。

局限：

- 构建、配置和调优复杂度更高。
- 模型适配和版本升级成本需要纳入评估。
- 与应用层 OpenAI API 的集成通常需要额外 serving 层。

适合：NVIDIA GPU 为主、追求极限性能/成本、愿意投入工程调优的大规模生产。

---

### 2.4 SGLang

**定位**：强调结构化语言模型程序执行与高效 serving 的框架，代表技术是 RadixAttention。

优势：

- 结构化输出能力强，适合 JSON/grammar/工具调用。
- RadixAttention 对复杂 prompt 程序、前缀共享、Agent 场景友好。
- OpenAI-compatible API 与高吞吐 serving 能力也在持续增强。

局限：

- 生态与最佳实践相对年轻，需要评估版本稳定性。
- 某些企业级运维能力需要结合外部组件补齐。

适合：Agent、结构化输出、复杂 prompt workflow、对 prefix 共享要求高的场景。

---

### 2.5 LMDeploy

**定位**：InternLM/国产模型生态中常用的推理部署框架，提供量化、服务化与评测链路。

优势：

- 对 InternLM、Qwen 等模型支持友好。
- 部署、量化、服务化工具链完整。
- 中文社区与国产模型适配成本较低。

局限：

- 国际社区生态与部分前沿特性需要与 vLLM/SGLang/TensorRT-LLM 对比验证。
- 大规模异构集群能力需结合实际运维体系评估。

适合：国产模型、中文业务、希望快速完成量化与部署的一体化链路。

---

### 2.6 DeepSpeed-MII / FastGen

**定位**：DeepSpeed 生态下的推理加速与服务化方案。

优势：

- 如果团队已经使用 DeepSpeed 做训练/微调，技术栈延续性较好。
- 与微软生态、DeepSpeed 优化经验衔接自然。

局限：

- 与 vLLM/SGLang/TensorRT-LLM 相比，需要结合具体版本评估特性完整度。
- 社区最佳实践相对分散。

适合：已有 DeepSpeed 技术栈，希望复用训练/推理一体化经验的团队。

## 3. 定性对比与选型建议

对应脚本：

```bash
python examples/serving_framework_comparison.py
```

脚本会打印能力矩阵，并按场景加权给出推荐排序。核心结论通常是：

| 场景 | 优先评估 |
|------|----------|
| 快速 OpenAI 兼容上线 | vLLM、SGLang |
| NVIDIA GPU 极限性能 | TensorRT-LLM |
| Hugging Face 生态 | TGI |
| Agent/结构化输出 | SGLang |
| 国产模型/中文生态 | LMDeploy、vLLM |
| 已有 DeepSpeed 栈 | DeepSpeed-MII |

建议的选型流程：

```text
1. 明确 SLO：TTFT、TPOT、throughput、并发、成本上限。
2. 明确模型：架构、上下文长度、多模态、量化格式。
3. 选 2 个候选框架做 smoke test。
4. 用真实 prompt 分布压测，不要只测单句。
5. 观察 p50/p95/p99 延迟、显存、OOM、长尾、重试。
6. 再做灰度上线与回滚预案。
```

## 4. 用 OpenAI-compatible API 做统一冒烟测试

很多框架都能暴露 OpenAI 兼容接口。这样应用层可以先不关心后端是 vLLM、TGI 还是 SGLang。

对应脚本：

```bash
# 默认只打印用法，不请求服务
python examples/openai_compatible_smoke_test.py

# 服务启动后再做真实冒烟测试
RUN_SMOKE=1 \
OPENAI_BASE_URL=http://localhost:8000/v1 \
MODEL_NAME=/data/models/Qwen3.5-9B \
python examples/openai_compatible_smoke_test.py
```

请求体与 OpenAI chat.completions 兼容：

```python
{
  "model": "/data/models/Qwen3.5-9B",
  "messages": [{"role": "user", "content": "请用一句话介绍 KV Cache。"}],
  "temperature": 0.0,
  "max_tokens": 16
}
```

冒烟测试建议检查：

- HTTP 状态码与错误信息是否清晰。
- `choices[0].message.content` 是否符合预期。
- `usage.prompt_tokens / completion_tokens` 是否返回。
- 流式接口是否稳定，是否支持 `stream=true`。
- 并发 8/32/64 时错误率与 p99 延迟。

## 5. 生产上线 Checklist

| 类别 | 检查项 |
|------|--------|
| 正确性 | 输出与 transformers baseline 对齐；chat template 一致；特殊 token 处理正确 |
| 性能 | TTFT/TPOT/throughput；长 prompt 与长输出分别压测；p95/p99 长尾 |
| 显存 | KV Cache 上限、OOM、碎片化、多实例共享 GPU 的隔离 |
| 高级特性 | Prefix Cache、Speculative Decoding、PD 解耦是否真正生效 |
| 量化 | 精度评估、校准集、回归测试、回退到非量化的预案 |
| API | OpenAI 兼容、stream、function calling、logprobs、usage 字段 |
| 运维 | metrics、tracing、日志、健康检查、超时、重试、熔断 |
| 安全 | 多租户隔离、鉴权、速率限制、prompt/log 脱敏 |
| 升级 | 模型升级、框架升级、CUDA 升级的兼容矩阵与回滚方案 |

## 6. 常见问题与排查

### 6.1 “框架 A 比 B 快”能直接信吗？

不能脱离工作负载。A 可能在短 prompt 高并发下更快，B 可能在长上下文或量化模型下更快。一定要用真实 prompt 长度分布、输出长度分布和并发模型压测。

### 6.2 OpenAI 兼容就等于完全兼容吗？

不一定。需要检查：

- `stream`、`usage`、`logprobs`、`stop`、`response_format`。
- function calling / tool choice 的细节。
- 错误码、超时、截断行为。
- chat template 与 system prompt 处理。

### 6.3 高级特性开了但没收益？

例如 Prefix Cache、Speculative Decoding、Chunked Prefill，都可能因为 prompt 太短、输出太长、命中低、accept 低而没有收益。要结合指标确认：

- prefix hit rate
- prefill tokens/s
- speculative acceptance rate
- decode stall / queue wait
- KV cache usage

### 6.4 生产上只选一个框架吗？

不一定。常见做法是：

- 在线通用聊天：vLLM/SGLang。
- 特定大批量离线任务：TensorRT-LLM 或定制 pipeline。
- Agent 结构化输出：SGLang 或带 constrained decoding 的服务。
- 通过统一网关/router 屏蔽后端差异。

## 8. 本节小结

1. 选推理框架不是选“名字”，而是选一组与业务 SLO 匹配的能力：API、KV 管理、量化、结构化输出、分布式与运维。
2. vLLM 适合快速 OpenAI 兼容上线；SGLang 适合 Agent/结构化输出；TGI 适合 HF 生态；TensorRT-LLM 适合 NVIDIA 极限性能；LMDeploy 适合国产模型链路。
3. 真正决策前要做统一 smoke test 和真实负载压测，关注 p95/p99，而不是只看 demo。
4. 生产环境可以通过统一网关接入多个后端，把“应用协议”和“推理引擎”解耦。

## 9. 课后思考

1. 如果你的业务 80% 请求 prompt 小于 128 tokens，但输出经常超过 1024 tokens，选型时更应看重哪些指标？
2. 为什么 OpenAI-compatible API 能降低框架替换成本？还有哪些细节可能不兼容？
3. 设计一个压测方案，比较 vLLM 与 SGLang 在“固定 system prompt + 短问题 + JSON 输出”的 Agent 场景下的 TTFT 与错误率。
4. 如果团队已经用 DeepSpeed 做训练，是否一定应该选择 DeepSpeed-MII 做推理？为什么？
5. 在需要 FP8 量化的大规模 NVIDIA 集群中，如何设计实验比较 TensorRT-LLM 与 vLLM 的单位 token 成本？
