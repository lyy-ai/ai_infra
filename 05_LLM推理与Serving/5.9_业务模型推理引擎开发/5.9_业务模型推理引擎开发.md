# 5.9 业务模型推理引擎开发：BEV/PlanNN 自动驾驶专用推理引擎

## 课程概述

前面课程主要以 LLM 为例讲推理与 Serving。真实业务中的推理引擎往往不是通用聊天服务，而是有强实时、强安全、强硬件约束的专用系统。自动驾驶中的 **BEV 感知 + PlanNN 规划** 是典型代表：多路相机/激光雷达输入，需要在有限算力和功耗下稳定输出感知、预测与规划结果。

本节课以 BEV/PlanNN 为例，讨论业务模型专用推理引擎开发：

- BEV/PlanNN 模型结构与计算热点
- 模型结构优化与算子定制
- 推理流水线并行优化
- 算法-硬件协同设计：硬件友好性设计

学完本节后，你将能够：

1. 说明 BEV 感知与 PlanNN 规划的计算瓶颈与实时性约束。
2. 用估算脚本分析 BEV 分辨率、通道数、历史帧、量化对显存和算力的影响。
3. 设计算子融合/自定义 kernel 的优化流程，并用 roofline 思路判断收益。
4. 用流水线并行提升车载推理吞吐，同时控制端到端延迟与功能安全风险。

## 1. BEV/PlanNN 与通用 LLM Serving 的差异

| 维度 | LLM Serving | BEV/PlanNN 自动驾驶推理 |
|------|-------------|--------------------------|
| 输入 | token 序列 | 多路相机/雷达/IMU/车辆状态 |
| 输出 | 文本 token | 障碍物、车道线、轨迹、规划结果 |
| 延迟目标 | TTFT/TPOT，通常百 ms 到秒级可接受 | 硬实时，常见 10Hz/20Hz，端到端几十 ms |
| 失败成本 | 回答慢或错误 | 可能影响行车安全 |
| 硬件 | 数据中心 GPU | 车载 SoC/GPU/DSA，功耗与散热受限 |
| 形状 | 动态序列长度 | 尽量静态 shape，便于确定性调度 |
| 优化目标 | 吞吐 + SLO | 最坏情况延迟 + 确定性 + 安全冗余 |

关键结论：

> 业务专用推理引擎的第一目标不是“平均最快”，而是 **在硬件约束下稳定满足最坏情况延迟，并可验证、可回退、可监控**。

## 2. BEV/PlanNN 的计算热点

### 2.1 典型流水线

```text
多路相机图像
  ├─► 图像预处理/畸变校正
  ├─► 2D Backbone 提特征
  ├─► View Transform / BEV Pooling
  ├─► BEV Encoder（self/cross/deformable attention, temporal fusion）
  ├─► Detection / Segmentation / Prediction Heads
  ├─► PlanNN 规划网络（轨迹候选、代价评估、规则后处理）
  └─► 控制输出
```

热点通常集中在：

1. **图像 Backbone**：多路相机高分辨率卷积，算力消耗大。
2. **View Transform / BEV Pooling**：大量 gather/scatter，容易 memory-bound。
3. **BEV Encoder Attention**：dense self-attention 是 `N^2`；BEVFormer 类模型常用 deformable attention 降低复杂度。
4. **Temporal Fusion**：历史 BEV feature 读写带来显存带宽压力。
5. **PlanNN**：相对较小，但与规则后处理耦合，要求确定性和低延迟。

### 2.2 BEV 估算

对应脚本：

```bash
python examples/bev_memory_compute_estimator.py
```

核心估算：

```text
BEV feature bytes = bev_h × bev_w × channels × history_frames × dtype_bytes

dense attention FLOPs ≈ 4·N·C² + 2·N²·C
deformable attention FLOPs ≈ 4·N·C² + 2·N·K·C
```

其中 `N = bev_h × bev_w`，`K` 是 deformable attention 的采样点数。脚本会对比 baseline 与优化配置：降低 BEV 分辨率、通道数、历史帧，并使用 INT8。

## 3. 专用推理引擎架构

### 3.1 设计原则

1. **静态化**：固定输入分辨率、BEV 尺寸、历史帧数、batch size，避免运行时动态分配。
2. **预分配**：图像 buffer、BEV feature、中间 tensor、输出轨迹全部预分配，使用内存池。
3. **零拷贝**：尽量让预处理、模型、后处理共享 pinned/device memory，减少 host-device 拷贝。
4. **确定性**：固定 CUDA graph、固定 stream 优先级、固定最坏情况执行路径。
5. **可回退**：关键链路要有轻量 fallback，例如规则规划或上一帧安全轨迹。
6. **可观测**：记录每帧 stage 延迟、丢帧、算子耗时、温度/功耗、数值异常。

### 3.2 推荐执行结构

```text
Sensor Thread → Preprocess Worker → GPU Inference Engine → Postprocess/PlanNN → Safety Monitor → Control
       │                 │                    │                     │                │
       └──────────────► timestamp sync, watchdog, deadline check, fallback trigger ◄──────────┘
```

关键模块：

- **Calibration/Quantization**：离线校准 + QAT，上线前回归精度。
- **Graph Capture**：把稳定子图捕获成 CUDA graph，减少 launch 抖动。
- **Operator Library**：标准 op + 自定义 op，统一做数值验证。
- **Memory Pool**：按最坏情况预留，禁止运行期 malloc。
- **Scheduler**：保证感知、预测、规划、控制按 deadline 调度。

## 4. 模型结构优化与算子定制

### 4.1 结构优化方向

| 优化 | 收益 | 风险 |
|------|------|------|
| 降低 BEV 分辨率 | 显存和 attention 计算显著下降 | 小目标/远处目标精度下降 |
| 减少 BEV channels | 显存带宽下降 | 表征能力下降 |
| 减少历史帧 | 显存与时间融合成本下降 | 速度/遮挡估计变差 |
| deformable/sparse attention | 消除 `N²` 项 | 实现复杂，数值稳定性需验证 |
| 共享 backbone | 多任务复用特征 | 任务间干扰 |
| INT8/FP8 量化 | 显存和带宽下降 | 校准不足导致精度损失 |

### 4.2 算子定制流程

```text
1. Profile：找出 top latency / top memory traffic op。
2. 分类：compute-bound 还是 memory-bound。
3. 融合：reshape/permute/pooling/norm 等优先融合。
4. 自定义 kernel：只针对 top 收益 op，如 BEV pooling、deformable attention、grid sample。
5. 数值验证：与 PyTorch/TensorRT reference 对齐误差、边界条件和确定性。
6. 回归测试：精度、延迟、最坏情况延迟、温度功耗。
```

对应脚本：

```bash
python examples/operator_fusion_roofline.py
```

脚本用简化 roofline：

```text
op_time ≈ max(compute_time, memory_mb / memory_bandwidth) + kernel_launch_overhead
```

融合后减少的是：

- kernel launch 次数；
- 中间 tensor 的显存读写；
- host/device 同步点。

融合不会改变数学计算量，但能显著改善 memory-bound 算子。

## 5. 推理流水线并行优化

对应脚本：

```bash
python examples/ad_pipeline_parallel_simulator.py
```

脚本把一帧拆成：

```text
preprocess_cpu → bev_perception_gpu → prediction → planning_plannn → control
```

对比：

- **Sequential**：一帧完整跑完才跑下一帧，吞吐受总延迟限制。
- **Pipelined**：不同阶段使用不同执行单元，吞吐受最慢 stage 限制。

关键结论：

- 流水线并行主要提升 **吞吐/FPS**，不一定降低单帧端到端延迟。
- 若端到端延迟也必须下降，要优化最慢 stage、减少同步点、重叠 CPU/GPU、降低输入分辨率或动态降帧。
- 车载场景要限制 pipeline 深度，避免为了吞吐引入过大的排队延迟和状态过期。

工程手段：

- CPU 预处理与 GPU 推理用双 buffer 重叠。
- 多 CUDA stream 分离 backbone、BEV encoder、PlanNN，但要控制同步。
- 对 deadline 最近的帧提高优先级，必要时丢弃过期中间结果。
- 每帧记录 timestamp，超过 deadline 触发 fallback，而不是继续排队。

## 6. 算法-硬件协同：硬件友好性设计

### 6.1 硬件友好操作

优先选择：

- 规则 GEMM/CONV，能映射到 tensor core。
- 静态 shape、连续内存访问、对齐的 tensor layout。
- 可融合的 elementwise/norm/activation。
- 可量化的层，配合 QAT 保持精度。

谨慎使用：

- 大量 gather/scatter、动态索引、不规则稀疏访问。
- 频繁 reshape/permute 导致隐式拷贝。
- 动态 shape 和控制流。
- 过大的 attention token 数，尤其是 dense `N²`。

### 6.2 面向车载硬件的设计规则

1. **先定量产后定结构**：目标芯片的算力、显存带宽、功耗先确定，再设计 BEV 尺寸和 backbone。
2. **把 budget 分配给最影响安全的任务**：近处障碍物、车道线、行人优先级高于远处小目标。
3. **让精度损失发生在可接受位置**：量化/降分辨率后要做场景级回归，而不是只看 mAP 平均值。
4. **软硬一起验证最坏情况**：高温降频、传感器丢帧、噪声标定误差下仍要满足安全策略。
5. **保留可解释 fallback**：当学习模块超时或异常时，规则模块能接管最小安全行为。

## 7. 常见问题与排查

### 7.1 优化后精度下降

- 检查是否过度降低 BEV 分辨率/历史帧，远处小目标先受影响。
- INT8 精度损失要分层定位：backbone、view transform、BEV encoder、PlanNN。
- 用 QAT 替代简单 PTQ，或对敏感层保留 FP16。

### 7.2 自定义算子数值不一致

- 对齐 reference 的 index、stride、padding、rounding、accumulation dtype。
- 检查越界、空 batch、极端坐标、NaN/Inf。
- 车载场景必须验证确定性：同一输入多次运行结果一致。

### 7.3 流水线提升了 FPS 但延迟更高

- pipeline 过深，帧在队列中等待。
- 最慢 stage 没优化，其他 stage 空转。
- CPU 预处理或后处理成为瓶颈，GPU 饥饿。
- 需要按 deadline 丢弃过期帧，而不是无限排队。

### 7.4 显存碎片与抖动

- 使用内存池与预分配，禁止运行期 malloc。
- 固定 shape 与 CUDA graph，减少 launch 与分配抖动。
- 对中间 tensor 做 lifetime 分析，复用 buffer。

## 9. 本节小结

1. BEV/PlanNN 专用推理引擎的目标是在车载硬件约束下满足 **最坏情况延迟、确定性与安全冗余**，而不是只追求平均吞吐。
2. BEV 分辨率、通道数、历史帧和量化位宽是显存与算力的关键旋钮；deformable/sparse attention 可避免 dense `N²`。
3. 算子定制应遵循 profile → 分类 → 融合 → 自定义 kernel → 数值验证 → 场景回归的流程。
4. 流水线并行提升 FPS，但车载场景必须限制排队深度，并为超时帧准备 fallback。
5. 算法-硬件协同的核心是让模型结构天然适合目标芯片：静态 shape、连续访问、可融合、可量化、可验证。
