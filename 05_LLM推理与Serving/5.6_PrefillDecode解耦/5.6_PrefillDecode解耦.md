# 5.6 Prefill/Decode 解耦（PD Disaggregation）

## 课程概述

前面我们学习了 PagedAttention、Continuous Batching、Speculative Decoding 与 Prefix Cache。它们大多假设 **Prefill 和 Decode 运行在同一个推理引擎/同一批 GPU 上**。但在生产环境中，Prefill 与 Decode 的资源特征差异很大：长 prompt 的 Prefill 会抢占 Decode 所需的算力与显存带宽，造成 TTFT 和 TPOT 互相影响。

本节课介绍一种更强的服务化拆分方式：**Prefill/Decode Disaggregation（PD 解耦）**。它把 Prefill worker 和 Decode worker 分开部署，Prefill 完成后把 KV Cache 传输给 Decode，由 Decode 专注生成后续 token。

学完本节后，你将能够：

1. 解释为什么 Prefill 与 Decode 的资源瓶颈不同。
2. 分析同引擎耦合服务时 TTFT/TPOT 互相干扰的原因。
3. 画出 PD 解耦的请求生命周期：Prefill → KV Transfer → Decode。
4. 估算 KV Transfer 的数据量、带宽需求与延迟成本。
5. 判断什么业务适合 PD 解耦，什么时候反而会变慢或变复杂。

---

## 1. 为什么 Prefill 和 Decode 应该区别对待？

### 1.1 Prefill 与 Decode 的本质差异

| 维度 | Prefill | Decode |
|------|---------|--------|
| 输入 | 整个 prompt，通常几十到几万 tokens | 每一步只输入 1 个新 token |
| 计算特征 | 大矩阵乘，compute-bound 倾向更明显 | 小批量 GEMV + 大量 KV 读取，memory-bandwidth-bound 倾向更明显 |
| 主要延迟指标 | 影响 TTFT（Time To First Token） | 影响 TPOT/ITL（Time Per Output Token / Inter-Token Latency） |
| 并行方式 | prompt 内 token 可高度并行 | 自回归，token 之间串行 |
| KV Cache | 写入大量 prompt KV | 每步追加 1 个 token 的 KV，并读取历史 KV |
| 调度目标 | 尽快完成 prompt 计算 | 稳定、低抖动地产出下一个 token |

一句话总结：

> **Prefill 更像“批量计算任务”，Decode 更像“低延迟流式任务”。**

把这两类任务放在同一个执行资源上，天然会出现调度冲突。

### 1.2 耦合部署的典型干扰

假设一个请求正在 Decode，每秒要稳定输出 token；此时来了一个 8192 tokens 的长 prompt 请求。若 Prefill 与 Decode 共用同一个 engine：

```text
t0: decode 正在稳定输出
t1: 长 prompt 到达，engine 开始 prefill
t2: prefill 占用大量计算与显存带宽，decode token 间隔被拉长
t3: prefill 完成，decode 才恢复稳定
```

结果是：

- **TTFT 变差**：短请求排在长 prompt 后面，首 token 迟迟不出。
- **TPOT 抖动**：已有请求在生成过程中被长 prefill 卡住。
- **SLO 难做**：TTFT 和 TPOT 需要不同的扩容策略，但耦合部署只能一起扩。

## 2. PD Disaggregation 是什么？

### 2.1 基本架构

PD 解耦把推理服务拆成两类 worker：

```text
Client
  │
  ▼
Router / Scheduler
  │
  ├──────────────► Prefill Worker Pool
  │                  1. 接收 prompt
  │                  2. 计算 prompt KV
  │                  3. 输出 KV blocks + 第一个 token/logits（视实现而定）
  │                           │
  │                           ▼
  │                    KV Transfer Channel
  │                  (NVLink / PCIe / RDMA / shared memory)
  │                           │
  └──────────────► Decode Worker Pool
                     4. 接收 KV blocks
                     5. 接管自回归 decode
                     6. 流式返回 token
```

核心思想：

- **Prefill worker**：优化高吞吐 prompt 计算，追求更快完成 prefill。
- **Decode worker**：优化稳定低延迟生成，追求平滑 TPOT。
- **KV Transfer**：把 Prefill 产生的 KV Cache 安全、快速地交给 Decode。

### 2.2 请求生命周期

```text
1. Router 接收请求，记录 prompt 长度、SLO、会话信息。
2. 选择 Prefill worker：考虑负载、prefix cache 命中、GPU 亲和性。
3. Prefill worker 计算 prompt KV，生成第一个 token 所需的 logits/state。
4. KV blocks 通过传输通道交给 Decode worker。
5. Decode worker 把请求加入 continuous batch，开始稳定 decode。
6. Decode 完成后返回结果，并释放或保留 KV（视会话策略）。
```

### 2.3 与 Chunked Prefill 的关系

Chunked Prefill 是把长 prompt 拆成多个 chunk，与其他 iteration 混合执行，缓解同引擎内的 head-of-line blocking。它解决的是“同一个 engine 里别被长 prefill 一次卡死”。

PD 解耦更进一步：

| 方案 | 作用范围 | 是否分离资源 | 优点 | 局限 |
|------|----------|--------------|------|------|
| Chunked Prefill | 单 engine 内部 | 否 | 实现相对简单，减少长 prefill 卡顿 | 仍然共享 GPU/显存/调度器 |
| PD Disaggregation | 服务架构层 | 是 | TTFT/TPOT 可独立优化和扩容 | KV 传输与调度复杂度显著上升 |

生产系统可以把两者结合：Prefill worker 内部仍然使用 chunked prefill 与 continuous batching。

## 3. 为什么要做 PD 解耦？

### 3.1 独立扩容

Prefill 吞吐和 Decode 吞吐不一定同比例增长。

- 如果业务突然多了很多长文档摘要请求，瓶颈在 Prefill，应该扩 Prefill worker。
- 如果业务是在线聊天，prompt 不长但输出很长，瓶颈在 Decode，应该扩 Decode worker。

耦合部署只能整体扩容，容易造成某一侧资源浪费。

### 3.2 独立优化硬件

- Prefill 更看重计算能力、FlashAttention、大 batch GEMM 效率。
- Decode 更看重显存容量、显存带宽、KV Cache 管理和 batch 调度。

在异构集群中，可以给 Prefill 和 Decode 配不同机型，降低成本。

### 3.3 更稳定的 SLO

很多在线服务会分别约束：

- TTFT：用户多久看到第一个字。
- TPOT/ITL：生成过程是否流畅。

PD 解耦后，Decode worker 不再被长 prompt prefill 直接打断，TPOT 更稳定；Prefill worker 可以独立做排队与批量优化来改善 TTFT。

## 4. PD 解耦的核心代价：KV Transfer

### 4.1 KV Transfer 的数据量公式

标准 Transformer 的 prompt KV 大小近似为：

```text
KV bytes = 2 × num_layers × num_kv_heads × head_dim × dtype_bytes × prompt_tokens
```

其中：

- `2` 表示 K 和 V 两份。
- `num_kv_heads` 越小（GQA/MQA），KV 越小。
- `dtype_bytes` 越小（FP8/INT8 KV），传输越少。

这与 6.1/6.2 中的 KV Cache 显存公式一致，只不过这里关注的是“跨 worker 传输”。

### 4.2 传输时间必须小于收益

PD 解耦是否划算，可以粗略看：

```text
收益 = 耦合部署中 decode 被 prefill 阻塞的时间 + 资源扩容不灵活造成的浪费
成本 = KV transfer 时间 + 额外调度/容错/运维复杂度
```

如果一个 4096-token prompt 的 KV 有数百 MiB，而互连只有低速网络，KV transfer 可能成为新的瓶颈。相反，如果是 NVLink/NVSwitch、同机共享显存或高速 RDMA，成本更容易被接受。

### 4.3 降低传输成本的方法

1. **同机 PD**：Prefill 与 Decode 在同一台机器不同 GPU 上，通过 NVLink/PCIe 或共享主机内存传输。
2. **传输与计算重叠**：Prefill 边算边传已完成的 KV blocks，Decode 尽早接管。
3. **KV Cache 量化**：FP8/INT8 KV 同时降低显存与传输量。
4. **GQA/MQA 模型**：从源头减少 KV heads。
5. **Prefix Cache 亲和调度**：相同前缀尽量路由到已有 prefix cache 的 worker，减少重复 prefill 与传输。
6. **Block 粒度流式交接**：按 KV block/page 传输，而不是等整个 prompt 全部完成后一次性拷贝。

## 5. 调度与路由设计

### 5.1 Router 需要知道什么？

一个好的 PD Router 至少应考虑：

- prompt 长度与预估 prefill 时间。
- 期望输出长度或历史生成分布。
- TTFT/TPOT SLO 优先级。
- Prefill/Decode worker 当前队列深度。
- prefix cache 命中率与亲和性。
- GPU 显存剩余、KV block 可用量、传输带宽。

### 5.2 典型策略

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| 短 prompt 优先 | 短 prompt 更快完成 prefill，降低平均 TTFT | 交互式聊天 |
| 长 prompt 独立队列 | 长文档进入专用 prefill pool，避免阻塞短请求 | 文档摘要/RAG |
| prefix 亲和 | 相同 system prompt 路由到同一 worker | 固定模板、多轮对话 |
| decode 保稳 | Decode worker 限制 prefill 干扰，优先保证 TPOT | 强实时输出 |
| 弹性比例 | 根据负载动态调整 prefill:decode worker 比例 | 流量波动大 |

### 5.3 与 Continuous Batching、Prefix Cache 的协同

- Decode worker 内部仍然需要 Continuous Batching 来保证吞吐。
- Prefill worker 命中 Prefix Cache 时，应尽量减少重复 prefill。
- 如果 Decode worker 也要服务多轮对话，需要考虑历史 KV 是否仍在本地；不在本地时可能需要回取或重新 prefill。

## 6. 什么时候适合 PD 解耦？

### 6.1 适合的场景

| 场景 | 原因 |
|------|------|
| 长 prompt 与短请求混合 | 长 prefill 容易阻塞短请求 decode |
| 在线服务有明确 TTFT/TPOT SLO | 需要分别优化首 token 与流式稳定性 |
| 流量规模大且波动明显 | 独立扩容更经济 |
| 可使用高速互连 | KV transfer 成本可控 |
| 多模型/多租户平台 | 需要更细粒度资源隔离 |

### 6.2 不适合或要谨慎的场景

| 场景 | 原因 |
|------|------|
| prompt 很短、输出很长 | Decode 占主导，PD 收益有限 |
| 集群网络较慢 | KV transfer 可能抵消收益 |
| 小规模部署 | 调度与运维复杂度大于收益 |
| 模型/框架不支持 KV 导出导入 | 需要额外改造 |
| 强一致会话状态 | KV 迁移、故障恢复更难 |

## 7. 代码实践：PD 调度模拟器

本节对应的纯 Python 示例：

```bash
python examples/pd_disaggregation_simulator.py
```

该脚本构造一组长短不一的请求，对比：

- **Coupled**：每个 iteration 只能 prefill 或 decode，长 prefill 会造成 decode stall。
- **Disaggregated**：prefill worker、KV transfer、decode worker 并行推进，decode 不被 prefill 直接阻塞。

建议重点观察：

- `avg TTFT` 与 `p95 TTFT` 是否下降。
- `avg TPOT gap` / `max TPOT gap` 是否更稳定。
- `decode stall iterations` 在 coupled 模式下如何随长 prompt 增加。
- KV transfer 很快时，disaggregated 的优势来自哪里；如果传输变慢，优势会如何被侵蚀。

## 9. 常见问题与排查

### 9.1 做了 PD 解耦却没有收益？

常见原因：

- prompt 太短，prefill 本来就不是瓶颈。
- Decode 占绝对主导，分离后只是增加传输成本。
- KV transfer 带宽不足，传输时间接近甚至超过节省的时间。
- Router 没有考虑 prefix cache 亲和，导致重复 prefill。
- Prefill/Decode worker 比例不合理，某一侧仍然排队。

### 9.2 KV 传输一致性怎么保证？

需要保证 Decode worker 收到的 KV 与 Prefill worker 的计算结果完全一致：

- 使用相同的模型权重、tokenizer、dtype、KV cache dtype。
- 明确 block/page 的 layout、stride、device 放置。
- 传输完成后做校验或版本号检查。
- 多轮对话中要明确历史 KV 的所有权与释放时机。

### 9.3 Decode worker 还需要 PagedAttention 吗？

需要。Decode worker 仍然要管理大量并发请求的 KV blocks。PD 解耦只是改变 KV 的来源，不改变 Decode 阶段对高效 KV 管理的需求。实际系统通常是：

```text
Prefill worker: PagedAttention + Continuous Batching + Prefix Cache
KV transfer: block/page 粒度迁移
Decode worker: PagedAttention + Continuous Batching + Prefix Cache（可选）
```

### 9.4 与多机 Tensor Parallel 有什么区别？

- Tensor Parallel 是把同一层计算切到多张 GPU 上，GPU 之间频繁同步，目标是让单请求能跑/更快。
- PD 解耦是把请求生命周期的不同阶段拆到不同 worker 上，目标是服务化资源隔离与调度优化。

两者可以组合，例如 Prefill worker 内部用 TP，Decode worker 内部也用 TP。

## 11. 本节小结

1. **Prefill 与 Decode 的资源特征不同**：Prefill 偏计算，Decode 偏显存带宽与低延迟流式输出。
2. 同引擎耦合部署容易出现 **长 prefill 阻塞 decode**，导致 TTFT 变差、TPOT 抖动。
3. **PD Disaggregation** 将 Prefill worker 与 Decode worker 分离，通过 KV Transfer 交接请求状态。
4. PD 的核心成本是 KV Transfer；是否划算取决于 prompt 长度、batch、互连带宽与 SLO。
5. Chunked Prefill 是单引擎内的缓解手段，PD 解耦是服务架构层的资源隔离；两者可以结合。
6. 生产落地需要同时设计 Router、prefix cache 亲和、worker 比例、KV layout 一致性与故障恢复。
