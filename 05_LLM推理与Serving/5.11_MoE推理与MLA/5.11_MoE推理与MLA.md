# 5.11 MoE 推理与 MLA

## 课程概述

前面几节讨论的推理优化（PagedAttention、Continuous Batching、PD 解耦）大多以稠密模型为对象。但 2024 年以来，前沿开源模型（DeepSeek-V2/V3、Qwen3-MoE、Mixtral 等）普遍采用 **MoE（Mixture-of-Experts）+ 注意力结构改造（如 MLA）** 的组合，这给推理系统带来了一组全新的 tradeoff。

本节课以 DeepSeek-V3 为主要案例，讲清楚两件事：

1. **MoE 推理为什么难**：总参数量巨大但激活参数量小，显存容量成为第一瓶颈；专家并行（EP）引入 all-to-all 通信；Decode 阶段专家负载严重不均。
2. **MLA 为什么省 KV Cache 又为什么难部署**：低秩压缩把 KV Cache 降一个数量级，但对 TP 不友好，催生了 DP attention 等推理侧新玩法。

学完本节后，你将能够：

1. 解释 MoE 推理"显存瓶颈而非算力瓶颈"的根本原因。
2. 画出 EP 的 dispatch/combine 两次 all-to-all 数据流，并估算通信量。
3. 分析 Decode 阶段专家负载不均的成因与三种工程解法。
4. 推导 MHA/GQA/MQA/MLA 的每 token KV Cache 字节数并做定量对比。
5. 说明 MLA 为什么与 TP 冲突、推理侧为什么用 DP attention 替代。

---

## 1. 背景与动机：MoE 推理的独特性

### 1.1 总参数巨大，激活参数很小

以 DeepSeek-V3 为例：

| 指标 | 数值 |
|------|------|
| 总参数量 | 671B |
| 每 token 激活参数 | 37B |
| 层数 | 61 |
| hidden size | 7168 |
| 路由专家数 | 256（每 token top-8）+ 1 共享专家 |

稠密模型的显存与算力需求是同比例增长的，而 MoE 把两者**解耦**了：

- **显存侧**：必须装下全部 671B 参数（FP8 约 671 GB，BF16 约 1.3 TB），这决定了部署至少需要 8~16 张高端卡。
- **算力侧**：每个 token 只激活 37B 参数，计算量与 37B 稠密模型相当。

> 核心结论：**MoE 推理的第一瓶颈是显存容量，不是算力。多卡部署的首要目的是"装下所有专家"，其次才是分摊计算。**

这正是"计算/通信/显存不可能三角"的典型体现：MoE 用**显存**（多放参数）和**通信**（all-to-all）换来了**计算量**的下降。

### 1.2 Decode 阶段是 memory-bound，MoE 放大了这一点

稠密模型 Decode 时每步要读全部权重，权重读一遍可以供整个 batch 复用，batch 越大越算得动。MoE 则不同：

- 每个 token 只读自己路由到的那几个专家，**batch 内不同 token 读不同的权重**。
- 当 batch 较小时，权重读取的复用度低，显存带宽利用率差。
- 必须用大 batch（几百到几千 token/step）才能把 MoE Decode 从 memory-bound 推向 compute-bound。

这解释了为什么 DeepSeek 官方推理部署倾向"大 EP + 大 batch"：只有足够大的 batch 才能让每张卡上的专家都有活干。

## 2. 核心原理一：推理侧专家并行（EP）

### 2.1 EP 的数据流：dispatch 与 combine

EP 把 E 个专家切到 P 张 GPU 上，每张卡持有 E/P 个专家。一个 MoE 层的执行流程：

```text
1. 各卡本地计算 router，得到每个 token 的 top-k 专家编号
2. dispatch（第一次 all-to-all）：
   把 token 的 hidden state 发送到目标专家所在的卡
3. 各卡本地执行自己持有的专家 FFN
4. combine（第二次 all-to-all）：
   把专家输出按原 token 位置发回并加权求和
```

一次 MoE 层 = **两次 all-to-all**。61 层就是 122 次 all-to-all，通信量随 EP size、batch、hidden size 线性增长。

通信量估算（单方向）：

```text
bytes ≈ n_tokens × top_k × hidden × dtype_bytes × (P-1)/P
```

其中 `(P-1)/P` 是"目标专家在远端"的概率。EP 越大，单卡专家越少，本地命中比例越低，通信占比越接近 100%。**EP 用通信换取了显存（每卡只存 1/P 的专家）**。

### 2.2 EP 与 TP/DP 的组合策略

工业界的共识是 Prefill 与 Decode 用不同的并行策略：

| 阶段 | 推荐策略 | 原因 |
|------|---------|------|
| Prefill | 偏 DP + 中小 EP（或 TP） | 输入 token 多，天然大 batch，专家负载均匀；重点是算力利用率 |
| Decode | 大 EP（如 32~320 卡）+ 大 batch | 每步 token 少，必须把 batch 做大、把专家摊开，才能提高带宽利用率 |

这与 5.6 节 PD 解耦天然配合：Prefill 集群和 Decode 集群可以采用**不同的并行拓扑**，KV 通过传输通道交接。

### 2.3 Decode 阶段的核心矛盾：专家负载不均

假设 Decode batch 有 256 个 token，每 token 选 top-8 中的专家，共 2048 次路由，分摊到 256 个专家，平均每个专家 8 个 token。但路由不是均匀的：

- 热门专家可能收到几十上百个 token，冷门专家一个都收不到（**空闲专家**）。
- 一次 MoE 层必须等**最忙的那张卡**算完才能继续（all-to-all 是同步点）。
- 于是 GPU 利用率被"最忙专家"拖累，其余卡在空转。

batch 越小，相对波动越大，问题越严重。这就是 MoE Decode 的**负载均衡问题**。

### 2.4 负载均衡的工程手段

| 手段 | 思路 | 代价 |
|------|------|------|
| 冗余专家（redundant experts） | 统计历史路由热度，给热门专家复制多份副本放到不同卡 | 额外显存（副本占空间） |
| EPLB（Expert Parallelism Load Balancer） | DeepSeek 开源的专家放置优化器，周期性重排专家到 GPU 的映射，使各卡负载均衡 | 需要在线迁移专家权重 |
| aux-loss-free bias 调整 | 训练/推理时给 router logits 加可动态调整的 bias，偏冷加热，不靠辅助 loss | 路由质量有轻微影响 |

三者的共同思想：**用少量显存或路由质量的牺牲，换取最忙专家负载下降，从而提升整体吞吐。**

### 2.5 DeepEP：为 MoE 而生的 all-to-all 通信库

DeepSeek 开源的 DeepEP 专门针对 MoE 的 dispatch/combine 做了优化：

- **NVLink 域内**：低延迟 kernel，机内 8 卡之间直接走 NVLink。
- **跨节点**：RDMA 传输，支持把 NVLink 与 RDMA 转发解耦。
- **两种模式**：
  - **normal 模式**：高吞吐，面向 Prefill / 训练 backward 这种大批量场景。
  - **low-latency 模式**：面向 Decode，纯 RDMA 路径，通信 kernel 与计算 kernel 占用不同的 SM，实现通信与计算的**重叠（overlap）**，把 all-to-all 藏进计算时间里。

这再次体现 tradeoff：low-latency 模式用**少量 SM 资源**换**通信延迟隐藏**。

## 3. 核心原理二：MLA（Multi-head Latent Attention）

### 3.1 从"存全部 head 的 K/V"到"存低秩 latent"

标准 MHA 每层每 token 要存 `2 × n_heads × d_head` 个元素。MLA（DeepSeek-V2 提出、V3 沿用）的做法：

- 把 K/V 压缩成一个低秩 **latent 向量** `c_t`（维度 `d_c = 512`），缓存时只存它。
- 再加一个携带位置信息的 rope 分量（维度 64）。
- **每层每 token 只需缓存 512 + 64 = 576 个元素**（BF16 即 1152 字节）。
- 用时通过解压矩阵（up-projection）从 latent 重建各 head 的 K/V。

KV Cache 从"按 head 存"变成"按层存一份共享的压缩表示"，相对同规模 MHA 降低一个数量级以上。

### 3.2 吸收矩阵（absorption）：省显存的代价

推理时如果把解压矩阵显式乘出来，等于把 K/V 又膨胀回去了，省显存但费计算和带宽。MLA 的关键技巧是**矩阵吸收**：

```text
q^T · (W_up_K · c) = (q^T · W_up_K) · c
```

把解压矩阵并入 Q/K 投影，直接让 query 与 latent 做注意力，**不需要显式重建 K/V**。代价是：

- 等效 attention 的 head 维数变大（query 侧被投影到 latent 空间的高维），对 GEMM/GEMV kernel 的形状不友好，需要专门优化的 MLA kernel（如 FlashMLA）。
- 这是典型的"显存省下来，kernel 复杂度上去"。

### 3.3 MLA 与 TP 的矛盾 → DP attention

TP 的基本操作是按 head 切分 K/V。但 MLA 的 latent 是**所有 head 共享的一份压缩表示，无法按 head 切分**：

- TP 下每卡只能**复制完整的 latent KV Cache**，TP 越大显存浪费越严重，完全抵消 MLA 的省显存优势。
- 工程解法：**DP attention**——attention 部分做数据并行（每卡复制 KV Cache，处理不同的请求分片），FFN/MoE 部分做 EP。这也是 DeepSeek 官方推理架构的选择。

> 一句话：**MLA 把 KV Cache 从"可切分的多份小数据"变成"不可切分的一份小数据"，于是并行策略从 TP 转向 DP。**

## 4. 定量对比：MHA / GQA / MQA / MLA 的 KV Cache

### 4.1 每 token 每层 KV Cache 字节数公式

| 结构 | 公式（BF16，2 字节/元素） | 示例：hidden 7168，128 头 |
|------|--------------------------|---------------------------|
| MHA | `2 × n_heads × d_head × 2` | 2×128×56×2 = 28,672 B |
| GQA（8 KV 头） | `2 × n_kv_heads × d_head × 2` | 2×8×56×2 = 1,792 B |
| MQA（1 KV 头） | `2 × 1 × d_head × 2` | 2×1×56×2 = 224 B |
| MLA | `(d_c + d_rope) × 2` | (512+64)×2 = 1,152 B |

注：MHA 示例中 d_head = 7168/128 = 56。MLA 的 576 维与 head 数无关。

### 4.2 单请求 128k 上下文的 KV Cache（61 层）

| 结构 | 每 token（61 层） | 128k 上下文 |
|------|--------------------|-------------|
| MHA-128 | 约 1.67 MB | 约 213 GiB |
| GQA-8 | 约 107 KiB | 约 13.3 GiB |
| MQA | 约 13.3 KiB | 约 1.67 GiB |
| MLA | 约 68.6 KiB | 约 8.6 GiB |

MLA 的 KV Cache 约为 MHA 的 1/25、GQA-8 的 2/3。注意 MLA 并非"最小"（MQA 更小），但它在**保模型质量**（ latent 512 维的信息容量远高于 1 个 KV 头）与**省显存**之间取得了平衡——这是"质量/显存"维度的取舍，而非单纯压缩。

详细的跨上下文长度对比与"80GB 卡能容纳多少并发"的估算，运行 `kv_cache_compare.py`。

## 5. 工程实践：vLLM / SGLang 的 MoE 与 MLA 支持

- **Triton fused MoE kernel**：vLLM 与 SGLang 都用 Triton 把"router → 分组 → 各专家 GEMM → combine"融合成少数 kernel，按专家分块做 grouped GEMM，避免逐专家启动 kernel 的开销。
- **EP 支持**：两个框架都已支持 EP（vLLM 的 `--enable-expert-parallel`，SGLang 的 `--enable-ep-moe` 等），并可集成 DeepEP 作为 all-to-all 后端；大 EP + EPLB 的组合主要在 SGLang/官方 DeepSeek 推理栈中落地。
- **MLA 支持**：vLLM 有 MLA 后端（吸收矩阵实现），SGLang 集成了 FlashMLA 等专用 kernel；两者都支持 DP attention 部署形态。
- **PD 解耦 + MoE**：Mooncake、SGLang 的 PD 分离部署中，Prefill 用较小 EP，Decode 用大 EP，是 DeepSeek-V3 类模型的主流生产形态。

## 6. 面试高频问题

**Q1：MoE 模型推理部署的首要瓶颈是什么？**

一句话答案：显存容量——必须装下全部专家，算力反而不是问题。

展开：以 DeepSeek-V3 为例，671B 参数 FP8 也要约 671 GB，单卡放不下，必须多卡；但每 token 只激活 37B，计算量相当于中小稠密模型。所以 MoE 的多卡部署第一目标是"装下专家"（EP），第二目标才是分摊算力。这也解释了为什么 MoE Decode 需要大 batch：batch 小了每张卡的专家利用率低，显存带宽喂不饱。

**Q2：EP 的通信模式是什么？怎么优化？**

一句话答案：每个 MoE 层有 dispatch 和 combine 两次 all-to-all，优化方向是低延迟通信库（DeepEP）+ 通信计算重叠。

展开：dispatch 把 token 按路由发到专家所在卡，combine 把结果发回求和。通信量约为 `n_tokens × top_k × hidden × 2B × (P-1)/P` 单方向。DeepEP 的 low-latency 模式用纯 RDMA 路径并让通信与计算占用不同 SM，把 all-to-all 藏进计算；normal 模式面向 Prefill 追求吞吐。

**Q3：MoE Decode 为什么会有专家负载不均？怎么解决？**

一句话答案：Decode batch 小，路由随机性强，热门专家拖累整步延迟；用冗余专家、EPLB 重排、bias 调路由三种手段。

展开：256 个专家在 batch 只有几百 token 时，按 top-8 路由的总采样次数有限，热门/冷门专家负载差距大，而 all-to-all 是同步点，整层要等最忙的卡。冗余专家给热门专家放副本（费显存），EPLB 周期性优化专家到 GPU 的放置（费迁移），aux-loss-free bias 直接调 router 偏置（轻微影响路由质量）。

**Q4：MLA 为什么能省 KV Cache？省多少？**

一句话答案：把每个 head 的 K/V 压缩成 512 维 latent + 64 维 rope 分量，每 token 每层只存 576 个元素，约为同规模 MHA 的 1/25。

展开：MHA 存 `2 × n_heads × d_head`，MLA 存与 head 数无关的 576 维。以 61 层、128k 上下文算，MHA 约 213 GiB，MLA 约 8.6 GiB。代价是需要"吸收矩阵"技巧避免显式解压，等效 head 维度变大，需要专用 kernel。

**Q5：MLA 为什么与 TP 不兼容？推理怎么办？**

一句话答案：latent 是所有 head 共享的，没法按 head 切，TP 只能整份复制，显存随 TP 线性浪费；推理改用 DP attention。

展开：TP 的语义是"每卡持有 KV 的 1/TP"，但 MLA 的 KV 是一份不可分的压缩表示，复制后 TP 越大浪费越大。工程上 attention 部分改为数据并行（每卡复制 KV、跑不同请求分片），MoE 部分用 EP，这就是 DeepSeek 官方推理的 DP attention + EP 组合。

**Q6：Prefill 和 Decode 的 MoE 并行策略为什么不同？**

一句话答案：Prefill token 多、天然负载均衡，用中小 EP 求算力；Decode token 少，必须大 EP + 大 batch 才能摊平负载并喂饱带宽。

展开：Prefill 一个请求就有几千 token，各专家都能收到足够样本，瓶颈在算力；Decode 每步只有 batch_size 个 token，专家利用率低且波动大，需要大 EP 把专家摊开、用大 batch 提高每专家 token 数。PD 解耦让两阶段可以用不同并行拓扑。

---

## 7. 小结

1. MoE 推理的不可能三角取舍非常鲜明：**用显存（存全部专家）+ 通信（all-to-all）换计算量（只激活 37B）**。显存容量是第一瓶颈，多卡部署的首要目的是装下专家。
2. EP 的每次 MoE 层有 dispatch/combine 两次 all-to-all；DeepEP 用 NVLink 域内 kernel + 跨节点 RDMA、normal/low-latency 双模式把通信开销压下去。
3. Decode 阶段小 batch 导致专家负载不均，最忙专家拖累全局；冗余专家、EPLB、aux-loss-free bias 是三种互补解法。
4. MLA 把 KV Cache 压缩成 576 维 latent（每 token 每层 1152 字节），相对 MHA 省约 25 倍，代价是吸收矩阵带来的 kernel 复杂度与 TP 不兼容性；推理侧因此转向 DP attention。
5. MoE + MLA 的组合（DeepSeek-V3 形态）是当前推理系统最难也最有价值的场景，PD 解耦、大 EP、DP attention、负载均衡器共同构成其生产部署方案。
