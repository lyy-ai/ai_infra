# 5.12 长上下文与显存分层

## 课程概述

上下文长度从 4k 卷到 128k 再到 1M，推理系统面对的瓶颈从"算力"彻底转向"**KV Cache 放在哪、怎么调度**"。单请求的 KV Cache 随长度线性增长，1M 上下文可以轻松达到数百 GB，单卡 HBM 根本放不下。本节系统讲解三条主流技术路线：

1. **显存分层与 KV offload**：HBM → CPU DDR → NVMe SSD 三级存储，冷热分层，跨请求复用。
2. **Context Parallelism / Ring Attention**：把序列维切到多卡，用通信换显存。
3. **稀疏注意力**：NSA / MoBA / 滑动窗口，从算法侧减少"要存、要算"的 KV。

学完本节后，你将能够：

1. 推导 KV Cache 随上下文长度的增长公式，判断何时单卡放不下。
2. 画出 HBM/DDR/SSD 三级显存分层的带宽层级，解释冷热分层的设计依据。
3. 说明 LMCache、Mooncake 两类 KV offload/池化系统的架构差异。
4. 描述 Ring Attention 的执行流程、通信掩盖条件与因果注意力带来的负载不均问题。
5. 对比三条路线在 TTFT、吞吐、精度、实现复杂度上的 tradeoff。

---

## 1. 背景与动机：长上下文的系统瓶颈

### 1.1 KV Cache 随长度线性增长

每 token 的 KV Cache（BF16）：

```text
kv_bytes_per_token = 2 × n_layers × n_kv_heads × d_head × 2字节
```

单请求 KV Cache = `kv_bytes_per_token × seq_len`，**严格线性增长**。

以 5.11 节的 DeepSeek-V3 规模（61 层、MLA 576 维）为例，已经是最省 KV 的结构之一：

| 上下文 | MLA 单请求 KV | 同规模 MHA 单请求 KV |
|--------|---------------|----------------------|
| 4k | 约 0.27 GiB | 约 6.7 GiB |
| 128k | 约 8.6 GiB | 约 213 GiB |
| 1M | 约 68.6 GiB | 约 1.7 TiB |

结论：**即使用 MLA，1M 上下文单请求也要约 70 GB；MHA 结构则完全不可行。** 长上下文本质上是显存系统问题，不是算力问题。

### 1.2 注意力计算量随长度平方增长

Prefill 的 attention FLOPs 是 `O(seq_len^2)`，1M 上下文的 prefill 计算量也极其可观。但工程上先被卡死的一定是显存：算不动可以加卡堆算力，**放不下则必须改变数据的存放位置或数量**——这就是三条路线的分野。

---

## 2. 核心原理一：显存分层与 KV offload

### 2.1 三级存储的带宽层级

| 层级 | 典型带宽 | 相对 HBM | 角色 |
|------|---------|----------|------|
| GPU HBM | 约 3 TB/s | 1x | 当前正在参与计算的 KV |
| CPU DDR | 约 200-400 GB/s（经 PCIe 约 64 GB/s 双向） | 约 1/10 | 温数据：近期可能复用的 KV |
| NVMe SSD | 约 7 GB/s | 约 1/400 | 冷数据：长尾历史 KV |

带宽每降一层掉一个数量级，所以分层设计的核心原则是：**让绝大多数访问命中高层级**。

### 2.2 冷热分层思想

- **热**：当前 step 正在 attend 的 KV（Decode 时每步都要读全部历史 KV 吗？——Dense attention 下是的，所以"正在 decode 的请求"的全部 KV 都应尽量留在 HBM）。
- **温**：暂时挂起的请求、可复用的 prefix KV → offload 到 CPU DDR，命中后经 PCIe 取回。
- **冷**：长尾会话历史、跨请求共享但低频的 prefix → SSD。

LRU 逐出是最常用的层级间替换策略：HBM 满了把最久未用的 block 降级到 DDR，DDR 满了再降级到 SSD。

### 2.3 典型系统

**LMCache**：KV Cache 复用与 offload 引擎，与 vLLM 集成。

- 把 KV Cache 抽象为可跨请求、跨层级存储的数据对象。
- 支持 GPU HBM / CPU DDR / SSD（乃至远端存储）多级缓存。
- 核心价值：**非 GPU 存储层上的 prefix 复用**——HBM 放不下的共享前缀不丢弃，而是降级保存，下次命中只花 PCIe/SSD 读取时间，免去重算 prefill。

**Mooncake**（月之暗面开源，支撑 Kimi 长上下文服务）：KVCache-centric 的 PD 分离架构。

- 以 KV Cache 为中心组织整个集群：全局**分布式 KV cache pool**，prefill 节点与 decode 节点解耦。
- **跨请求 prefix 复用**：相同前缀的 KV 在 pool 中只存一份，多请求共享。
- KV block 通过 RDMA 在节点间传输；调度器以"KV 命中 + 负载均衡"为目标做请求路由。
- 本质：把"每台 GPU 自己的 KV Cache"池化成"全集群共享的分布式 KV 存储"，用**池化换取复用率与容量**。

## 3. 核心原理二：Context Parallelism / Ring Attention

### 3.1 把序列维切到多卡

当单卡放不下整条序列的 KV 时，可以把序列维切到 P 张卡上，每卡只持有 `seq_len / P` 的 KV。Ring Attention 的执行方式：

```text
初始：每卡 i 持有 Q_block_i、K_block_i、V_block_i
第 s 步（s = 0 .. P-1）：
  1. 每卡用本地 Q_block 对当前持有的 K/V block 做 partial attention
     （online softmax 累积，类似 FlashAttention 的分块归并）
  2. 同时把当前 K/V block 发给环上下一卡，接收上一卡发来的 block
  3. 通信与计算重叠执行
P 步后：每卡的 Q_block 都见过全序列的 K/V，得到正确的 attention 输出
```

显存收益：每卡 KV 降为 1/P，**用通信换显存**，支持百万级上下文。

### 3.2 通信能否被计算掩盖？（roofline 判断）

每步通信量 = 一个 K/V block 的字节数，每步计算量 = 一个 Q block 对一个 K/V block 的 attention FLOPs。通信完全被掩盖的条件：

```text
block_flops / gpu_flops_per_sec  >=  block_kv_bytes / ring_bandwidth
```

block 越大，计算/通信比越高，越容易掩盖。所以 Ring Attention 倾向**大 block + 高带宽互联（NVLink/RoCE）**；跨节点带宽不足时通信暴露，扩展效率骤降。定量分析见 `ring_attention_sim.py`。

### 3.3 因果注意力带来的负载不均

注意力是因果的：第 i 个 block 的 Q 只需要 attend 到前 i 个 block 的 K/V。朴素 ring 切分下，靠前的卡计算量小、靠后的卡计算量大，**负载严重不均**。

解法：

- **zigzag 切分（条带化）**：把序列首尾配对切分，使每卡拿到的 block 组合的计算量接近均等。
- **双 ring / 双向传递**：两个方向的 ring 交错推进，进一步摊平。

这又是三角取舍：zigzag 用**调度复杂度**换**负载均衡**。

## 4. 核心原理三：稀疏注意力路线

前两条路线都不减少 KV 总量，只是改变存放位置。稀疏注意力直接从算法侧减少"要存、要算、要读"的 KV：

| 方法 | 思路 | 特点 |
|------|------|------|
| 滑动窗口注意力（Mistral 等） | 每 token 只 attend 最近 w 个 token | 简单、KV 固定为 O(w)，但丢失远程信息 |
| NSA（DeepSeek） | Native Sparse Attention：compression / selection / sliding 三分支，硬件对齐、可训练 | 训练推理一致稀疏，块级选择对齐 Tensor Core |
| MoBA（Kimi） | 把历史 KV 分块，用 MoE 式路由为每个 query 选 top-k 块 | 块稀疏路由，保持全量注意力的表达能力 |

共同思想：**把"显存 + 算力"问题转化为"不规则访存 kernel"问题**。

- 省显存：只需存压缩/选择后实际会用的 KV 表示（selection 路线仍要存全量 KV，但读取量大降）。
- 省算力：attention FLOPs 从 O(L^2) 降到 O(L × k)。
- 代价：稀疏模式不规则，需要专用 kernel（块级 gather + attention），工程复杂度高；且稀疏引入近似，精度需验证。

> 一句话：**稠密长上下文拼的是显存系统，稀疏长上下文拼的是 kernel 工程。**

## 5. 跨请求 prefix 复用与分布式 KV pool 的工程细节

长上下文场景下，跨请求复用价值极高（RAG、agent 多轮对话共享大量前缀）：

- **RadixAttention（SGLang，见 5.5 节）**：用 radix tree 组织 KV block，自动命中最长公共前缀，LRU 逐出。是单机 prefix cache 的代表实现。
- **分布式 KV pool（Mooncake 风格）**：把 radix tree / 前缀索引扩展到集群级，KV block 分布式放置在多台机器的 HBM/DDR 上，命中后通过 **RDMA** 直接远端读取，无需经过对方 CPU。
- **LRU 逐出与层级降级**：HBM 中逐出的 block 不是删除而是降级到 DDR/SSD/pool，保留下次命中的机会——逐出策略从"容量管理"升级为"**层级放置决策**"。
- **KV block 的放置与传输**：block 是传输与放置的基本单位（与 PagedAttention 的 block 对齐），传输走 RDMA/NVLink，调度器需要同时考虑"命中率"与"目标节点负载"，这本质上是缓存系统与调度系统的联合优化。

## 6. Tradeoff 对比：三条路线

| 维度 | KV offload / 分层 | Context Parallel / Ring | 稀疏注意力 |
|------|-------------------|-------------------------|------------|
| 核心取舍 | 显存 ↔ 延迟（带宽降级） | 显存 ↔ 通信（ring all-to-all 式传递） | 显存+算力 ↔ 精度 + kernel 复杂度 |
| TTFT | 命中高层级时低；冷启动/SSD 命中时显著变差 | 随 P 增加可摊薄计算，但通信暴露时变长 | prefill 计算量下降，TTFT 改善明显 |
| 吞吐 | 高（复用率越高越高） | 受 ring 带宽限制，跨节点扩展效率下降 | 高（decode 读 KV 量大降） |
| 精度 | 无损（只移动数据） | 无损（数学等价） | 有损（近似，需训练配合） |
| 实现复杂度 | 中（分层缓存 + 替换策略） | 中高（ring 通信 + zigzag 负载均衡） | 高（稀疏 kernel + 训练改造） |
| 适用场景 | 多轮对话 / RAG / 高复用前缀 | 超长单请求（百万级） | 超长上下文 + 可接受近似的场景 |

工程上三者**正交可组合**：稀疏注意力减少 KV 总量，分层存储放剩余的 KV，Context Parallel 处理单次超长 prefill。Mooncake 等生产系统正是"分层 + 池化 + PD 解耦"的组合体。

## 7. 面试高频问题

**Q1：1M 上下文的 KV Cache 有多大？单卡放得下吗？**

一句话答案：按 `2 × n_layers × n_kv_heads × d_head × 2B × seq_len` 计算，MHA 结构 1M 上下文单请求可达数百 GB 甚至 TiB 级，单卡 HBM 放不下。

展开：以 61 层、128 头、d_head 56 的 MHA 为例，每 token 约 1.67 MB，1M 上下文约 1.7 TiB。即使用 GQA-8 也要约 107 GiB，MLA 压缩到约 68.6 GiB，仍占满一张 80GB 卡。所以长上下文必须配合 GQA/MLA 压缩、显存分层、Context Parallel 或稀疏注意力。

**Q2：KV offload 的层级怎么设计？依据是什么？**

一句话答案：HBM → DDR → SSD 三级，带宽每层降约一个数量级，设计依据是让绝大多数访问命中高层级。

展开：HBM 约 3 TB/s，DDR 经 PCIe 约 64 GB/s 双向，NVMe SSD 约 7 GB/s。正在 decode 的请求 KV 必须留 HBM；挂起请求与可复用 prefix 降级到 DDR；长尾历史到 SSD。LRU 做层级间替换，命中低层级时付出传输延迟换取免重算 prefill。

**Q3：Mooncake 解决了什么问题？**

一句话答案：把 KV Cache 池化成全集群共享的分布式存储，PD 分离 + 跨请求 prefix 复用，支撑 Kimi 长上下文服务。

展开：传统部署每台 GPU 私有 KV Cache，容量受单卡限制、前缀无法跨机复用。Mooncake 以 KVCache 为中心，prefill/decode 节点解耦，全局 KV pool 中相同前缀只存一份，KV block 经 RDMA 在节点间传输，调度按"KV 命中 + 负载"路由请求。

**Q4：Ring Attention 的原理是什么？有什么坑？**

一句话答案：把序列切到 P 卡，K/V block 绕环传递，每步本地 partial attention + 通信重叠，P 步后得到等价结果；坑是因果注意力导致负载不均，需要 zigzag 切分。

展开：每卡只存 1/P 的 KV，用通信换显存支持百万级上下文。通信能否被计算掩盖取决于 block 计算时间与 ring 传输时间的比值（roofline）。因果注意力下靠后的 block 计算量大，朴素切分负载不均，工业实现用 zigzag 条带化或双 ring 摊平。

**Q5：稀疏注意力（NSA/MoBA）与 KV offload 是什么关系？**

一句话答案：正交互补——稀疏从算法侧减少要存要算的 KV，offload 从系统侧改变 KV 的存放位置。

展开：NSA 用 compression/selection/sliding 三分支做硬件对齐的可训练稀疏，MoBA 用 MoE 式路由做块选择。它们把问题从"显存容量 + 算力"转化为"不规则访存 kernel"工程。生产系统可以两者叠加：稀疏减少 KV 总量，分层存储放剩余 KV。

**Q6：长上下文服务中 prefix cache 怎么做到集群级？**

一句话答案：单机用 RadixAttention（radix tree + LRU），集群级用分布式 KV pool + RDMA 传输 + 命中感知调度。

展开：SGLang 的 RadixAttention 在单机内用 radix tree 管理 block 实现最长前缀命中。扩展到集群后，KV block 分布式放置，命中后 RDMA 直读远端显存，调度器路由请求时同时优化前缀命中率与节点负载，LRU 逐出升级为跨层级的放置决策。

---

## 8. 小结

1. 长上下文的第一瓶颈是**显存**：KV Cache 随长度线性增长，1M 上下文 MHA 单请求达数百 GB，必须先靠 GQA/MLA 压缩，再靠系统手段兜底。
2. 显存分层（HBM/DDR/SSD）的依据是带宽层级，核心指标是高层级命中率；LMCache 做多级 KV 复用，Mooncake 把 KV 池化到集群级。
3. Ring Attention 用通信换显存，扩展性取决于计算能否掩盖通信；因果注意力导致负载不均，需 zigzag 切分。
4. 稀疏注意力（NSA/MoBA/滑窗）从算法侧减 KV，把显存问题转化为不规则访存 kernel 问题，代价是精度与工程复杂度。
5. 三条路线在"计算/通信/显存"三角上各让一步，生产系统通常是三者的组合。
