# 5.3 Continuous Batching

## 课程概述

在上一节课（6.2 PagedAttention 与 KV Cache 管理）中，我们学习了如何通过 PagedAttention 高效管理 KV Cache，从而服务更多并发请求。但仅有高效的 KV Cache 管理还不够——**如何组织请求进入 batch，直接决定了 GPU 的利用率和服务吞吐**。

本节课将深入讲解 LLM Serving 中最重要的调度技术之一：**Continuous Batching（持续批处理 / 动态批处理）**。学完本节后，你将能够：

1. 理解 Static Batching 的局限性以及为什么无法满足生产环境需求。
2. 掌握 Continuous Batching 的核心思想：请求随到随处理，而非等待整个 batch 完成。
3. 了解 FCFS（先到先服务）和 Preemption（抢占）两种基本调度策略。
4. 通过模拟代码直观对比 Static Batching 与 Continuous Batching 的吞吐差异。
5. 理解 vLLM 中 Continuous Batching 的实现机制。

---

## 1. Static Batching 的局限

### 1.1 什么是 Static Batching？

**Static Batching（静态批处理）** 是最简单的请求组织方式：

1. 等待一组请求到达（或设置超时）。
2. 把这组请求打包成一个固定大小的 batch。
3. 模型一次性处理这个 batch，直到所有请求都生成完成。
4. 释放 batch，处理下一组请求。

```
Batch 1: [Req1, Req2, Req3]  → 全部完成后才处理 Batch 2
Batch 2: [Req4, Req5, Req6]  → 全部完成后才处理 Batch 3
```

### 1.2 Static Batching 的问题

Static Batching 存在三个严重缺陷：

#### 1.2.1 序列长度差异导致的填充浪费

一个 batch 中的请求通常长度不同。为了组成张量，需要对所有序列进行 padding（填充）到 batch 内最大长度。

```
Req1 prompt: 10 tokens   → padding to 50 tokens
Req2 prompt: 25 tokens   → padding to 50 tokens
Req3 prompt: 50 tokens   → 50 tokens

Padding tokens 也要参与计算，造成大量无效算力。
```

#### 1.2.2 最短请求拖慢整个 batch

Static Batching 必须等待 batch 中**最后一个请求**完成才能释放资源。

```
Batch 1:
  Req1: 生成 10 tokens  → 10ms 完成
  Req2: 生成 50 tokens  → 50ms 完成
  Req3: 生成 100 tokens → 100ms 完成

Batch 1 总耗时 = 100ms
Req1 和 Req2 完成后，GPU 仍在等待 Req3，资源空闲。
```

这就是典型的 **straggler effect（拖尾效应）**：短请求被长请求拖慢，GPU 利用率低下。

#### 1.2.3 无法动态响应新请求

Static Batching 在 batch 执行期间不会接收新请求。如果请求到达率不稳定，系统会出现明显的“忙等”或“空转”。

### 1.3 Static Batching 适用场景

尽管有诸多缺点，Static Batching 在以下场景仍可使用：

- 请求长度高度一致（如固定长度的 embedding 提取）。
- 离线批量任务，对延迟不敏感。
- 作为基线对比实验。

但在交互式 LLM 服务中，Static Batching 几乎不可接受。

## 2. Continuous Batching 原理

### 2.1 核心思想

**Continuous Batching（持续批处理 / 迭代级调度）** 的核心思想是：

> **在每个模型 forward 迭代结束后，重新调度 batch 中的请求。完成的请求立即离开，新到达的请求可以立即加入。**

这与 Static Batching 的关键区别在于调度的**粒度**：

- Static Batching：以 **request（请求）** 为粒度调度。
- Continuous Batching：以 **iteration（迭代 / token）** 为粒度调度。

```
Iteration 1:  [Req1, Req2, Req3]  all prefill + first decode
Iteration 2:  [Req1, Req2, Req3]  (Req1 done? leave; Req4 arrive? join)
Iteration 3:  [Req2, Req3, Req4]  (Req2 done? leave; Req5 arrive? join)
Iteration 4:  [Req3, Req4, Req5]
```

### 2.2 为什么 Continuous Batching 更高效？

1. **没有等待拖尾**：短请求完成后立即离开，不会阻塞长请求之外的其他请求。
2. **没有 padding 浪费**：新请求可以按需加入当前 batch，不需要一次性 padding 到固定长度。
3. **GPU 利用率更高**：每个 iteration 都能保持 batch 接近满载，减少空闲。
4. **延迟更稳定**：新请求不需要等待一个完整 batch 的形成。

### 2.3 与 PagedAttention 的关系

Continuous Batching 和 PagedAttention 是相辅相成的：

- **Continuous Batching** 解决了“何时把请求放进 batch”的问题。
- **PagedAttention** 解决了“这些请求的 KV Cache 如何高效存储”的问题。

如果没有 PagedAttention，Continuous Batching 需要频繁地为变长请求重新分配连续显存，开销巨大。PagedAttention 的 Block 设计天然支持动态分配和释放，使得 Continuous Batching 变得高效可行。

### 2.4 一个直观的例子

假设有 3 个请求，长度分别为：

- Req1: 生成 2 tokens
- Req2: 生成 5 tokens
- Req3: 生成 8 tokens

#### Static Batching

```
Time: 0  1  2  3  4  5  6  7  8
Batch: [R1 R2 R3] 一起处理
R1:    ====           (2 tokens done, but still in batch)
R2:    =======        (5 tokens done, but still in batch)
R3:    ============   (8 tokens done)

Total time = 8 iterations
```

#### Continuous Batching

```
Iteration 1: [R1, R2, R3]  all decode 1 token
Iteration 2: [R1, R2, R3]  R1 done, leaves; R4 joins
Iteration 3: [R2, R3, R4]  decode
Iteration 4: [R2, R3, R4]  R2 done, leaves; R5 joins
Iteration 5: [R3, R4, R5]  decode
Iteration 6: [R3, R4, R5]  decode
Iteration 7: [R3, R4, R5]  R3 done, leaves
Iteration 8: [R4, R5]     decode
```

在这个简化例子中，Continuous Batching 使得 R1 和 R2 可以更快完成，R3 也不会被明显拖慢，同时新请求能够立即加入。

## 3. 调度策略：FCFS

### 3.1 什么是 FCFS？

**FCFS（First-Come First-Served，先到先服务）** 是最简单的调度策略：

- 请求按照到达时间排队。
- 每次从队首选择请求加入 batch，直到 batch 满或队列为空。
- 已经完成的请求从 batch 中移除。

```python
waiting_queue = [Req1, Req2, Req3, Req4, ...]

for iteration:
    # 把 waiting queue 中的请求加入 batch，直到 batch 满
    while len(current_batch) < max_batch_size and waiting_queue:
        current_batch.append(waiting_queue.pop(0))
    
    # 执行一次 forward
    run_forward(current_batch)
    
    # 移除完成的请求
    for req in current_batch:
        if req.is_done():
            current_batch.remove(req)
```

### 3.2 FCFS 的优点

1. **实现简单**：不需要复杂的优先级计算。
2. **公平性好**：先到的请求先得到服务，符合用户直觉。
3. **无饥饿风险**：只要请求到达，最终都会被处理。

### 3.3 FCFS 的缺点

1. **对长请求不友好**：一个长请求会占据 batch 位置，导致后续短请求等待。
2. **无法处理 SLA 差异**：不同用户可能有不同延迟要求，FCFS 一视同仁。
3. **没有抢占机制**：如果一个高优先级请求到达，无法中断当前 batch。

### 3.4 FCFS 适用场景

- 请求到达率相对均匀。
- 所有请求优先级相同。
- 作为 Continuous Batching 的基础调度策略。

## 4. 调度策略：Preemption（抢占）

### 4.1 为什么需要抢占？

在资源有限的情况下，系统可能会遇到以下情况：

1. **新请求到达，但当前 batch 已满**。
2. **新请求优先级更高**（如付费用户、实时任务）。
3. **当前 batch 中的某些请求已经运行了很久，但新请求很短**。

如果没有抢占机制，新请求只能等待当前 batch 中的请求完成或释放。这会导致高优先级请求的延迟急剧上升。

**Preemption（抢占）** 允许系统中断当前正在运行的请求，把资源让给其他请求，稍后再恢复被中断的请求。

### 4.2 抢占的实现方式

在 LLM 推理中，抢占通常涉及以下步骤：

1. **选择被抢占的请求**：通常是运行时间最长、剩余工作量最少或优先级最低的请求。
2. **保存其 KV Cache**：将被抢占请求的 KV Cache 从 GPU 显存转移到 CPU 内存（swap out）。
3. **运行新请求**：使用释放出的 GPU 资源运行新请求。
4. **恢复被抢占请求**：当资源可用时，将 KV Cache 从 CPU 内存换回 GPU 显存（swap in），继续生成。

```
GPU Memory:
  Before: [Req1 KV, Req2 KV, Req3 KV]
  Preempt Req2: swap Req2 KV to CPU
  After:  [Req1 KV, Req3 KV, NewReq KV]
  
  Later: swap Req2 KV back to GPU and continue
```

### 4.3 抢占的代价

抢占虽然提高了调度灵活性，但也有代价：

1. **KV Cache 换入换出开销**：CPU ↔ GPU 数据传输需要时间。
2. **延迟增加**：被抢占的请求完成时间会更长。
3. **实现复杂**：需要维护每个请求的状态和 KV Cache 位置。

### 4.4 vLLM 中的抢占策略

vLLM 实现了两种抢占策略：

#### Swapping

- 将被抢占请求的 KV Cache 块从 GPU 换出到 CPU 内存。
- 恢复时再换入。
- 优点：不丢失计算结果，恢复时直接继续。
- 缺点：CPU 内存占用增加，换入换出有延迟。

#### Recomputation

- 不保存 KV Cache，直接丢弃被抢占请求的中间状态。
- 恢复时重新计算该请求的前向传播。
- 优点：不占用额外 CPU 内存。
- 缺点：重新计算会消耗额外 GPU 算力。

vLLM 默认会根据显存和 CPU 内存情况自动选择较优策略。

### 4.5 抢占 vs FCFS

| 维度 | FCFS | Preemption |
|------|------|-----------|
| 实现复杂度 | 低 | 高 |
| 公平性 | 高 | 取决于策略 |
| 高优先级响应 | 差 | 好 |
| 资源利用率 | 中等 | 高 |
| 额外开销 | 小 | KV Cache swap 或 recompute |
| 适用场景 | 均质请求、低优先级差异 | 多租户、SLA 差异大 |

## 5. vLLM 中的 Continuous Batching 实现

### 5.1 vLLM 调度流程

vLLM 的调度流程可以概括为：

```
1. 新请求到达 → 加入 waiting queue
2. Scheduler 在每个 iteration 开始前运行：
   a. 从 running queue 中移除已完成的请求
   b. 根据资源情况（KV Cache 块、batch size）从 waiting queue 选择新请求加入
   c. 如果需要，对低优先级请求进行抢占（swap out 或 recompute）
3. 形成当前 iteration 的 batch
4. 执行 model forward（包括 prefill 和 decode）
5. 将完成或继续的请求分别放入 appropriate queue
```

### 5.2 vLLM Scheduler 关键参数

| 参数 | 含义 | 作用 |
|------|------|------|
| `--max-num-seqs` | 最大并发序列数 | 控制最大 batch size |
| `--max-model-len` | 模型最大序列长度 | 限制 prompt + generated 的总长度 |
| `--gpu-memory-utilization` | GPU 显存利用率目标 | 控制显存使用上限，留出余量 |
| `--swap-space` | CPU swap 空间大小 | 用于抢占时的 KV Cache 换出 |
| `--enable-chunked-prefill` | 启用 chunked prefill | 将长 prefill 拆成多个 iteration |

### 5.3 Chunked Prefill 与 Continuous Batching

在标准的 Continuous Batching 中，prefill 和 decode 通常不会混合：

- Prefill 需要一次性处理整个 prompt，计算量大。
- Decode 只需要处理一个 token，计算量小。

如果在一个 batch 中同时有 prefill 和 decode，prefill 会拖慢 decode（计算量不均衡）。

**Chunked Prefill** 解决了这个问题：

- 将长 prompt 的 prefill 拆分成多个小块（chunk）。
- 每个 chunk 与其他请求的 decode 一起运行，计算量更均衡。
- 这进一步提高了 GPU 利用率，是 vLLM 的新特性。

## 6. Static Batching vs Continuous Batching 对比

| 维度 | Static Batching | Continuous Batching |
|------|----------------|-------------------|
| 调度粒度 | Request | Iteration / Token |
| Padding 浪费 | 严重 | 几乎没有 |
| 拖尾效应 | 严重 | 几乎没有 |
| GPU 利用率 | 低 | 高 |
| 新请求响应 | 慢（等 batch 满） | 快（iteration 级加入） |
| 实现复杂度 | 低 | 高（需配合 PagedAttention） |
| 吞吐 | 低 | 高（通常 2-10x） |
| 适用场景 | 离线任务、固定长度 | 在线 LLM 服务 |

## 7. 代码实践：Continuous Batching 模拟器

### 7.1 模拟器设计

本节提供一个纯 Python 模拟器，用于对比 Static Batching 和 Continuous Batching：

- 每个请求有 `arrival_time` 和 `num_tokens`（需要生成的 token 数）。
- 模拟器按时间步执行，每个 iteration 处理一个 token。
- Static Batching：等待 batch 满，所有请求完成后再处理下一 batch。
- Continuous Batching：每个 iteration 重新调度，完成即离开，新请求可加入。

对应脚本：`examples/continuous_batching_simulator.py`

```bash
python examples/continuous_batching_simulator.py
```

### 7.2 模拟器核心逻辑

```python
class Request:
    def __init__(self, id, arrival_time, num_tokens):
        self.id = id
        self.arrival_time = arrival_time
        self.num_tokens = num_tokens
        self.generated_tokens = 0
        self.completed = False


def static_batching(requests, max_batch_size=4):
    """静态批处理模拟。"""
    time = 0
    total_completed = 0
    queue = list(requests)
    results = []

    while queue or total_completed < len(requests):
        # 收集一个 batch
        batch = []
        while len(batch) < max_batch_size and queue:
            if queue[0].arrival_time <= time:
                batch.append(queue.pop(0))
            else:
                break

        if not batch:
            time += 1
            continue

        # 等待 batch 中最长请求完成
        max_tokens = max(r.num_tokens for r in batch)
        time += max_tokens

        for r in batch:
            r.generated_tokens = r.num_tokens
            r.completed = True
            results.append((r.id, time, r.num_tokens))
            total_completed += 1

    return results, time


def continuous_batching(requests, max_batch_size=4):
    """持续批处理模拟（FCFS）。"""
    time = 0
    total_completed = 0
    queue = list(requests)
    running = []
    results = []

    while total_completed < len(requests):
        # 新请求加入 running batch
        while len(running) < max_batch_size and queue:
            if queue[0].arrival_time <= time:
                running.append(queue.pop(0))
            else:
                break

        if running:
            # 所有 running 请求前进一个 token
            time += 1
            for r in running[:]:
                r.generated_tokens += 1
                if r.generated_tokens >= r.num_tokens:
                    r.completed = True
                    results.append((r.id, time, r.num_tokens))
                    running.remove(r)
                    total_completed += 1
        else:
            # 没有请求在运行，时间推进到下一个请求到达
            time = queue[0].arrival_time

    return results, time
```

### 7.3 模拟器输出解读

运行脚本后会输出类似：

```
Static Batching:
  Total time: 120 iterations
  Average latency: 85.5 iterations
  Throughput: 1.67 tokens/iteration

Continuous Batching (FCFS):
  Total time: 95 iterations
  Average latency: 42.3 iterations
  Throughput: 2.11 tokens/iteration

Speedup: 1.26x
```

这直观地展示了 Continuous Batching 在吞吐和延迟上的优势。

## 8. 代码实践：vLLM 中的 Continuous Batching

### 8.1 离线批量推理

vLLM 默认使用 Continuous Batching，无需额外配置：

```python
from vllm import LLM, SamplingParams

llm = LLM(model="/data/models/Qwen3.5-9B", dtype="float16")

sampling_params = SamplingParams(
    temperature=0.7,
    top_p=0.9,
    max_tokens=128,
)

prompts = [
    "问题1：什么是机器学习？",
    "问题2：什么是深度学习？",
    "问题3：什么是强化学习？",
]

outputs = llm.generate(prompts, sampling_params)
```

vLLM 的 `LLMEngine` 会自动在内部使用 Continuous Batching 调度这些请求。

### 8.2 启用抢占（Preemption）

通过 `--swap-space` 参数启用抢占：

```bash
python -m vllm.entrypoints.openai.api_server \
    --model /data/models/Qwen3.5-9B \
    --swap-space 4 \
    --max-num-seqs 8
```

`--swap-space 4` 表示允许使用 4 GB 的 CPU 内存作为 swap 空间，用于抢占时的 KV Cache 换出。

### 8.3 启用 Chunked Prefill

```bash
python -m vllm.entrypoints.openai.api_server \
    --model /data/models/Qwen3.5-9B \
    --enable-chunked-prefill
```

## 9. 常见问题与排查

### 9.1 Continuous Batching 是否总是比 Static Batching 好？

不一定。在以下场景，Static Batching 可能更简单有效：

- 所有请求长度一致。
- 离线批量处理，不追求实时性。
- 系统资源充足，不需要复杂调度。

但在在线 LLM 服务中，Continuous Batching 几乎总是更优。

### 9.2 如何选择 max_batch_size？

- 太小：GPU 利用率低。
- 太大：KV Cache 显存压力大，单个 iteration 延迟增加。
- 通常需要通过压测找到最佳值，vLLM 中对应 `--max-num-seqs`。

### 9.3 抢占导致某些请求特别慢怎么办？

- 设置请求的优先级，避免低优先级请求被频繁抢占。
- 增加 `--swap-space` 或使用更高速的 CPU 内存。
- 考虑使用 Recomputation 策略而非 Swapping，如果 CPU 内存不足。
- 限制长请求比例，避免系统被少量长请求拖垮。

### 9.4 Chunked Prefill 什么时候启用？

- 当 prompt 长度差异大、长 prompt 较多时。
- 当希望 prefill 和 decode 混合以提高吞吐时。
- 但可能轻微增加短 prompt 的 TTFT，需根据场景权衡。

## 11. 本节小结

1. **Static Batching** 以请求为粒度调度，存在 padding 浪费、拖尾效应和响应慢等问题。
2. **Continuous Batching** 以迭代为粒度调度，请求完成即离开、新请求可立即加入，显著提高了 GPU 利用率和吞吐。
3. **PagedAttention** 是 Continuous Batching 高效实现的基础，两者结合才能达到最佳效果。
4. **FCFS** 是最简单的调度策略，公平但无法处理优先级差异。
5. **Preemption** 通过 swap out 或 recompute 机制，支持高优先级请求抢占资源，但带来额外开销。
6. **Chunked Prefill** 进一步将 prefill 与 decode 混合，提升长 prompt 场景下的 GPU 利用率。
