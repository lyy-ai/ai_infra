# 5.8 多机多卡 Serving

## 课程概述

当单卡无法容纳模型，或单实例无法满足并发 SLO 时，就需要多机多卡 Serving。本节课把前面学的单机优化（PagedAttention、Continuous Batching、Prefix Cache、PD 解耦）扩展到集群视角，重点讨论四个主题：

- Tensor Parallel Serving
- Pipeline Parallel Serving
- 负载均衡与弹性扩缩容
- 云端 vLLM 框架二次开发

学完本节后，你将能够：

1. 区分 TP、PP、DP（数据并行）以及它们对延迟、吞吐、通信的影响。
2. 估算一个模型在单卡、TP、PP 下的大致显存占用，并给出部署建议。
3. 设计推理服务的负载均衡策略与弹性扩缩容指标。
4. 说明在云端对 vLLM 做二次开发时，哪些应该放在网关层，哪些才需要改框架内核。

## 1. 多机多卡 Serving 的并行维度

| 并行方式 | 切分对象 | 典型通信 | 优点 | 代价 |
|----------|----------|----------|------|------|
| Data Parallel（DP） | 不同请求到不同实例 | 几乎无模型内通信 | 最简单，线性扩容吞吐 | 单请求延迟不变，单实例仍需放下模型 |
| Tensor Parallel（TP） | 单层内部权重/激活/KV heads | 每层 all-reduce | 降低单卡显存，降低单请求延迟 | 通信频繁，强依赖 NVLink/高速互连 |
| Pipeline Parallel（PP） | 不同层到不同 stage | stage 间点对点 | 可跨节点放超大模型，通信少 | pipeline bubble，调度和 microbatch 复杂 |
| Expert Parallel（EP） | MoE experts | all-to-all | 降低 MoE 单卡专家参数 | 通信与路由复杂 |

经验法则：

> **能在单卡放下就先单卡；单卡放不下优先节点内 TP；跨节点或超大模型再考虑 PP；吞吐不足用 DP 扩容；MoE 再考虑 EP。**

## 2. Tensor Parallel Serving

### 2.1 TP 切分什么？

以一层 Transformer 为例，TP 通常切分：

- Q/K/V/O 的权重矩阵与输出通道。
- MLP 的 gate/up/down 权重。
- attention heads / KV heads。
- 对应的 KV Cache（按 head 维度切到不同 GPU）。

每层前向都需要 all-reduce 或 reduce-scatter/all-gather，把各卡结果合并。

### 2.2 TP 的收益与代价

收益：

- 单卡权重显存近似变为 `weight / tp`。
- KV Cache 也可按 heads 切分，降低单卡 KV 压力。
- 单请求计算由多卡并行完成，可能降低 TTFT/TPOT。

代价：

- 每层都有通信，要求 GPU 间低延迟高带宽。
- TP degree 越大，通信占比越高，边际收益下降。
- 跨节点 TP 通常不如节点内 TP 稳定。

### 2.3 TP 适用场景

- 模型权重 + KV 超过单卡显存，但节点内多卡可以放下。
- 对单请求延迟敏感，愿意用多卡换延迟。
- GPU 之间有 NVLink/NVSwitch 或等价高速互连。

不建议：

- 跨普通以太网做高 degree TP。
- 小模型为了“显得高级”强行 TP，通信开销可能超过收益。

## 3. Pipeline Parallel Serving

### 3.1 PP 切分什么？

PP 把模型的层切成多个 stage：

```text
GPU0: layers 0-7
GPU1: layers 8-15
GPU2: layers 16-23
GPU3: layers 24-31
```

请求激活从 stage0 流到 stageN，反向或中间状态按 stage 传递。推理时主要是 forward 的 stage 间传递。

### 3.2 Pipeline Bubble

如果只有一个请求在 pipeline 中流动，前面的 stage 完成后会等待后面的 stage，产生空闲。工程上用 microbatch 填满 pipeline：

```text
microbatch 1: stage0 -> stage1 -> stage2 -> stage3
microbatch 2:        stage0 -> stage1 -> stage2 -> stage3
microbatch 3:               stage0 -> stage1 -> stage2 -> stage3
```

PP 的关键不是“能不能切”，而是“能不能用足够 microbatch 把 bubble 填平”。在线低延迟场景，microbatch 过大会增加排队延迟。

### 3.3 PP 适用场景

- 超大模型，节点内 TP 仍放不下。
- 跨节点部署，stage 间通信量远小于 TP 每层 all-reduce。
- 更关注吞吐而非单请求极限延迟。

不适合：

- 9B/13B 这类单卡或节点内 TP 可放的模型。
- 对 TTFT/TPOT 抖动极敏感、无法积累 microbatch 的在线服务。

## 4. TP/PP 估算与部署建议

对应脚本：

```bash
python examples/parallelism_planner.py
```

脚本按近似公式估算：

```text
weight_per_gpu ≈ total_weight / tp 或 / pp
kv_per_gpu ≈ total_kv / tp 或 / pp
total_per_gpu ≈ weight_per_gpu + kv_per_gpu + runtime_overhead
```

典型结论：

- 9B 级 fp16 模型在 40GB/80GB GPU 上，通常优先单卡或节点内小 degree TP。
- PP 不是“更高级”的默认选项，而是模型大到 TP 也放不下时的手段。
- 在引入 PP 前，先评估量化、降低 `max_model_len`、Prefix Cache、PD 解耦和更合理 batching。

部署建议：

1. **单卡优先**：最简单、延迟最稳。
2. **节点内 TP**：模型/KV 超单卡但节点内可放，且互连足够快。
3. **跨节点 PP + 节点内 TP**：超大模型的常见组合，例如 PP across nodes + TP within node。
4. **DP 扩容吞吐**：单实例 SLO 达标后，用更多实例做水平扩容。

## 5. 负载均衡

### 5.1 推理服务负载均衡不能只看出入口 QPS

LLM 请求成本差异巨大：prompt 长度、输出长度、是否命中 prefix cache、是否 speculative、是否多模态，都会影响单个请求成本。负载均衡要感知“成本”，而不仅是请求数。

常用策略：

| 策略 | 说明 | 适用 |
|------|------|------|
| Round Robin | 简单轮转 | 请求成本接近、实例同构 |
| Least Connections / Least Queue | 发给排队最少的实例 | 通用在线服务 |
| Latency-aware | 根据近期 TTFT/TPOT 选择 | 强 SLO 场景 |
| Prefix/cache-aware | 相同前缀路由到同实例 | 固定 system prompt、多轮对话 |
| Cost-aware | 按 prompt_tokens、历史输出长度估计成本 | 长短请求混合 |

### 5.2 健康检查与背压

- 健康检查不能只看进程存活，还要看 engine ready、KV cache 可用、CUDA 是否健康。
- 实例过载时应返回 429/503 或排队，而不是无限接收导致雪崩。
- 网关要支持超时、重试、熔断；重试要避开刚失败的实例。

## 6. 弹性扩缩容

对应脚本：

```bash
python examples/serving_autoscaling_simulator.py
```

脚本模拟低负载 + 突发流量，对比固定实例与 least-queue + autoscaling。

### 6.1 扩容指标

不要只看 GPU utilization。更可靠的指标组合：

- 请求队列深度 / 平均等待时间。
- TTFT、TPOT 的 p95/p99。
- KV Cache block 使用率、可分配 block 数。
- prefix cache hit rate、acceptance rate（若开启投机）。
- 实例 startup 时间、模型加载时间、CUDA graph 捕获时间。

### 6.2 扩缩容策略

- **Scale-out**：队列深度或 p95 TTFT 超过阈值，且持续 N 个周期。
- **Scale-in**：低负载持续更长时间，先 drain 请求再下线，避免中断流式连接。
- **Cooldown**：防止指标抖动导致反复扩缩。
- **Pre-warm**：新实例启动后先完成模型加载、kernel 编译、CUDA graph 捕获，再接流量。
- **Spot/弹性实例**：适合可中断离线吞吐，不适合强 SLO 在线主链路。

## 7. 云端 vLLM 框架二次开发

### 7.1 先分层：哪些不该改 vLLM 内核

云端二次开发时，建议优先把能力放在外层，而不是直接 fork vLLM 大改内核：

| 层级 | 应该放什么 |
|------|-----------|
| API Gateway | 鉴权、限流、计费、请求校验、灰度、熔断、日志脱敏 |
| Router / Scheduler | 成本感知路由、prefix 亲和、SLO 分流、多后端管理 |
| Observability | metrics、tracing、请求级 TTFT/TPOT、队列深度、KV usage |
| Control Plane | 模型注册、版本管理、实例编排、扩缩容、健康检查 |
| vLLM 内核/插件 | 新模型支持、kernel、scheduler、KV connector、prefix cache 策略 |

原则：

> 能在网关/控制面做的，不要污染推理引擎；必须改引擎时，优先走插件、connector、可配置策略，减少长期 fork 成本。

### 7.2 常见二次开发需求

| 需求 | 推荐实现位置 |
|------|--------------|
| 统一鉴权与限流 | API Gateway |
| 多租户配额与计费 | Gateway + Control Plane |
| OpenAI API 适配 | Gateway Adapter |
| 成本感知路由 | Router |
| 请求级日志/追踪 | Gateway + vLLM metrics hook |
| 自定义调度策略 | vLLM scheduler 插件/配置 |
| KV transfer / PD 解耦 | vLLM KV connector + 自研 transfer service |
| 新模型结构支持 | vLLM model implementation |
| 灰度发布 | Control Plane + Router |

### 7.3 一个云端 Serving 参考架构

```text
Client
  │
  ▼
API Gateway（鉴权/限流/计费/日志）
  │
  ▼
Router（成本感知、prefix 亲和、SLO 分流）
  │
  ├─► vLLM Cluster A（在线聊天，小 prompt，高并发）
  ├─► vLLM Cluster B（长文档，PD 解耦，prefill/decode 分离）
  └─► TensorRT-LLM Cluster C（大批量离线/FP8 优化）
        │
        ▼
Observability（Prometheus + tracing + request logs）
        │
        ▼
Autoscaler（队列深度/TTFT/TPOT/KV usage）
```

### 7.4 工程坑位

- **不要只看 QPS**：LLM 请求成本分布极不均匀。
- **启动时间要计入扩容**：模型加载、torch.compile、CUDA graph 捕获都可能几十秒到几分钟。
- **多版本共存**：框架升级与模型升级要支持灰度和回滚。
- **日志成本高**：请求文本可能很大，需采样与脱敏。
- **指标口径统一**：TTFT、TPOT、queue wait、prefill time、decode time 要定义清楚。

## 9. 本节小结

1. 多机多卡 Serving 先分清 DP/TP/PP/EP：DP 扩吞吐，TP 降单卡显存和延迟，PP 解决超大模型跨节点，EP 面向 MoE。
2. 9B 级模型通常不需要复杂 PP；优先单卡、量化、节点内 TP、Prefix Cache 和 PD 解耦。
3. 负载均衡要感知请求成本与 cache 亲和，而不是简单按请求数轮转。
4. 弹性扩缩容要基于队列深度、TTFT/TPOT、KV usage，并把模型加载与 warmup 时间计入策略。
5. 云端 vLLM 二次开发应分层：网关做鉴权限流，Router 做成本感知，控制面做编排扩缩，只有模型/kernel/调度/KV connector 才进入引擎层。
