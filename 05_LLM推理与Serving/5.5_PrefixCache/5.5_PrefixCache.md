# 5.5 Prefix Cache（前缀缓存）

## 课程概述

在前面课程中，我们学习了 KV Cache、PagedAttention、Continuous Batching 与 Speculative Decoding。它们分别解决了“KV Cache 怎么存”“请求怎么调度”“Decode 怎么少跑几次”的问题。本节课关注另一个非常工程化、但在生产系统收益很大的优化：**Prefix Cache（前缀缓存）**。

Prefix Cache 的核心问题是：

> 如果很多请求的 prompt 拥有完全相同的前缀，为什么还要重复计算这段前缀的 prefill？

学完本节后，你将能够：

1. 区分 KV Cache、Prefix Cache 与 Response Cache。
2. 理解 Prefix Cache 为什么能降低 TTFT 与 prefill 算力消耗。
3. 掌握 vLLM Automatic Prefix Caching（APC）的 Block 级复用机制。
4. 分析 system prompt、多轮对话、RAG、Agent 工具描述等场景的命中率。
5. 通过模拟器和 vLLM 示例观察 Prefix Cache 的收益与边界。

---

## 1. Prefix Cache 是什么？

### 1.1 三个容易混淆的“缓存”

| 名称 | 缓存对象 | 作用阶段 | 是否改变输出分布 |
|------|----------|----------|------------------|
| **KV Cache** | 单个请求内已计算 token 的 K/V | Prefill / Decode | 否，本来就是推理必需状态 |
| **Prefix Cache** | 多个请求共享前缀的 KV Block | Prefill | 否，只复用完全相同前缀的 KV |
| **Response Cache** | 完整 prompt 对应的最终输出 | 请求级 | 可能，如果直接返回旧答案 |

本节课讨论的是 **Prefix Cache**：它缓存的是 prompt 前缀对应的 KV，而不是最终文本答案。

### 1.2 一个典型例子

假设线上服务有固定 system prompt：

```text
你是一个严谨的中文 AI 助手。请遵守以下规则：...
```

每个用户请求都是：

```text
system prompt + 用户问题
```

如果没有 Prefix Cache，每个请求都要对完整 prompt 做 prefill：

```text
请求 1: prefill(system prompt + 问题 1)
请求 2: prefill(system prompt + 问题 2)
请求 3: prefill(system prompt + 问题 3)
```

如果 system prompt 有 1024 tokens，用户问题只有 32 tokens，那么每个请求大约有 97% 的 prefill 计算是重复的。

开启 Prefix Cache 后：

```text
请求 1: prefill(system prompt + 问题 1)，并把 system prompt 的 KV Block 缓存起来
请求 2: lookup(system prompt) 命中，只 prefill(问题 2)
请求 3: lookup(system prompt) 命中，只 prefill(问题 3)
```

收益主要体现在：

- **TTFT 下降**：首个 token 更快返回。
- **prefill 算力下降**：重复前缀不再重复跑模型。
- **吞吐提升**：省下来的算力可以服务更多请求。
- **显存重复减少**：相同前缀的 KV Block 可以共享，而不是每个请求复制一份。

## 2. Prefix Cache 与 PagedAttention 的关系

Prefix Cache 不是替代 PagedAttention，而是建立在 PagedAttention 之上的复用机制。

### 2.1 PagedAttention 提供 Block 化 KV 管理

PagedAttention 把 KV Cache 切成固定大小的 Block，并通过 Block Table 管理 logical block 到 physical block 的映射。这带来两个适合 Prefix Cache 的性质：

1. **Block 是天然复用单位**：相同内容的前缀 Block 可以被多个请求引用。
2. **引用计数与 Copy-on-Write**：共享 Block 被修改前可以安全复用；一旦分叉，只分叉后续 Block。

### 2.2 Prefix Cache 在 Block 之上做“内容寻址”

可以近似理解为：

```text
PagedAttention: request_id -> block_table -> physical blocks
Prefix Cache:   hash(prefix_blocks) -> physical blocks
```

当一个新请求到来时，引擎会把 prompt 按 Block 切分，并尝试从缓存中找到最长连续前缀：

```python
prompt_tokens = tokenize(prompt)
matched_tokens = 0

for block in split_into_full_blocks(prompt_tokens):
    key = hash(block_tokens)
    if key not in prefix_cache:
        break
    reuse(block)
    matched_tokens += block_size

# 只有 matched_tokens 之后的 suffix 需要真正 prefill
prefill(prompt_tokens[matched_tokens:])
```

### 2.3 RadixAttention

SGLang 提出的 RadixAttention 与 Prefix Cache 思想相近，但更强调用 **Radix Tree** 组织 token 前缀，从而支持更灵活的前缀匹配与共享。vLLM 的 APC 更偏向 **Block hash + LRU** 的工程实现。

## 3. vLLM Automatic Prefix Caching（APC）

### 3.1 开启方式

vLLM 中可以通过 `enable_prefix_caching=True` 开启：

```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="/data/liyangyang/models/Qwen3.5-9B",
    dtype="float16",
    enable_prefix_caching=True,
    gpu_memory_utilization=0.55,
    max_num_seqs=32,
    max_model_len=4096,
)

sampling_params = SamplingParams(temperature=0.0, max_tokens=128)
outputs = llm.generate(prompts, sampling_params)
```

对应示例：

```bash
PATH=/data/liyangyang/qwen35_env/bin:$PATH python 5.5_PrefixCache/vllm_prefix_cache.py
```

### 3.2 APC 的关键特征

| 特征 | 说明 |
|------|------|
| 复用粒度 | KV Block，而不是单个 token |
| 匹配方式 | 从 prompt 起始位置开始的最长连续相同前缀 |
| 命中条件 | 前缀 token、模型、tokenizer、dtype、chat template、LoRA/adapter 等上下文一致 |
| 淘汰策略 | 通常是 LRU 或近似 LRU，空间不足时淘汰冷 Block |
| 正确性 | 只复用完全相同前缀的 KV，不改变输出分布 |
| 主要收益 | 降低 TTFT、减少 prefill 计算、减少重复 KV 显存 |

### 3.3 为什么通常只共享完整 Block？

PagedAttention 中 Block 是显存分配与调度的最小单位。若两个请求在前 20 个 token 相同，而 `block_size=16`，则只能共享第 1 个完整 Block：

```text
tokens: 0-15   16-31
req A:  same    same
req B:  same    different at token 20

可共享：Block 0（16 tokens）
不可共享：Block 1（因为内部已经分叉）
```

这也是为什么模拟器 `5.5_PrefixCache/prefix_cache_simulator.py` 中专门演示了 “diff@token31” 与 “diff@token32” 的差异。

> 注意：不同模型在 vLLM 中的 attention block size 可能不同。许多纯 Transformer 模型常见默认值是 16 tokens；但本课程使用的 Qwen3.5 在 vLLM 0.25.0 日志中会把 attention block size 调整为更大的值（例如 528 tokens）。这意味着 **prefix 必须足够长，至少覆盖一个完整 Block**，否则即使 `enable_prefix_caching=True` 也无法命中。示例 `5.5_PrefixCache/vllm_prefix_cache.py` 因此使用了很长的共享前缀，并把 `max_tokens` 调小，让 prefill/TTFT 的差异更容易观察。
>
> 另外，Qwen3.5 这类混合架构还有 Mamba cache blocks 限制：当 `gpu_memory_utilization` 较低时，可用 Mamba cache blocks 可能小于 vLLM 默认 `max_num_seqs=256`，导致 CUDA graph capture 报错 `max_num_seqs exceeds available Mamba cache blocks`。示例脚本已显式设置 `max_num_seqs=32`；如果显存更紧张，可继续降低 `max_num_seqs` 或提高 `gpu_memory_utilization`。

## 4. 命中率分析：哪些场景收益最大？

定义两个指标：

```text
prefix_hit_rate = matched_prefix_tokens / total_prompt_tokens
effective_prefill_tokens = total_prompt_tokens - matched_prefix_tokens
```

`effective_prefill_tokens` 越小，TTFT 越低。

### 4.1 收益大的场景

| 场景 | 原因 |
|------|------|
| 固定 system prompt | 大量请求共享长前缀 |
| 多轮对话 | 新 turn 的 prompt 是历史对话的前缀扩展 |
| Few-shot prompt | 示例部分固定，只有最后问题变化 |
| RAG 固定模板 | instruction、schema、工具描述固定；若检索文档也稳定，收益更大 |
| Agent / function calling | 工具 schema 与系统指令很长且稳定 |
| 批量离线任务共享同一指令 | 同一批请求前缀一致 |

### 4.2 收益小的场景

| 场景 | 原因 |
|------|------|
| 每个请求前缀都不同 | 没有可复用前缀 |
| prompt 很短 | lookup 开销可能接近收益 |
| 生成阶段占主导 | max_tokens 很大时，decode 时间占大头 |
| cache 容量太小 | 前缀 Block 很快被 LRU 淘汰 |
| chat template 不稳定 | 相同语义渲染成不同 token 序列，无法命中 |
| 多租户前缀相似但不完全相同 | 精确匹配失败，命中下降 |

### 4.3 一个经验结论

Prefix Cache 最适合：

> **长固定前缀 + 短变化后缀 + 高并发/多轮复用**

如果业务是“短 prompt + 长输出”，Prefix Cache 的收益通常不如 Continuous Batching、增大 batch、Speculative Decoding 或更快 decode kernel。

## 5. 工程实现细节

### 5.1 Cache Key 应该包含什么？

工程上不能只 hash 一段文本，还要保证复用上下文一致。一个安全的 cache key 至少应覆盖：

- 前缀 token ids（按 Block）
- base model / weights 版本
- tokenizer 版本与 chat template
- dtype / quantization / KV cache dtype
- LoRA / adapter 标识
- 多模态 processor 配置（如果有）
- 影响 prompt 渲染的系统参数

在同一个 vLLM engine 进程内，这些信息通常固定，所以 APC 主要按 token block 做匹配。跨进程、跨版本、跨模型复用则要非常谨慎。

### 5.2 命中后的计算流程

```text
1. tokenize prompt
2. 按 block_size 切分完整 Block
3. 从头开始查询 Prefix Cache，得到最长连续命中前缀
4. 对命中部分：直接引用已有 KV Block
5. 对未命中 suffix：执行 prefill，并写入新的 KV Block
6. 进入 decode 阶段
7. 请求结束后，Block 可按策略保留在 cache 中，等待后续请求复用或被淘汰
```

### 5.3 Copy-on-Write 与分叉

多个请求共享前缀后，一旦 suffix 不同，它们只需要为分叉后的 token 分配新 Block：

```text
req A: [shared block 0][shared block 1][A block 2]
req B: [shared block 0][shared block 1][B block 2]
```

共享 Block 只读；分叉发生在后缀。这与操作系统中的 COW 思想类似。

### 5.4 与 Continuous Batching 的协同

Prefix Cache 降低单个请求的 prefill 成本，Continuous Batching 提高 batch 调度效率。两者结合后：

- 共享前缀的请求更快完成 prefill，进入 decode。
- scheduler 可以更快把 decode 请求组成有效 batch。
- 长 system prompt 场景下，GPU 更倾向于把时间花在 decode，而不是重复 prefill。

## 6. 代码实践：Prefix Cache 模拟器

本节对应的纯 Python 示例：

```bash
python 5.5_PrefixCache/prefix_cache_simulator.py
```

该脚本包含四个场景：

1. **Shared System Prompt**：6 个请求共享 64 个伪 token 的 system prompt。
2. **Multi-turn Conversation**：后续 turn 复用历史对话前缀。
3. **Block Boundary Effect**：前缀差异落在 Block 内部时，只能共享差异前的完整 Block。
4. **LRU Eviction**：缓存容量有限时，冷前缀 Block 被淘汰，命中率下降。

建议重点观察输出中的：

- `matched prefix tokens`：命中了多少前缀 token。
- `computed prompt tokens`：真正需要 prefill 的 token 数。
- `prefix hit rate`：命中率。
- `kv blocks`：开启/关闭 Prefix Cache 时需要的 KV Block 数差异。

## 7. 代码实践：vLLM Prefix Cache

本节对应的 vLLM 示例：

```bash
PATH=/data/liyangyang/qwen35_env/bin:$PATH python 5.5_PrefixCache/vllm_prefix_cache.py
```

脚本做了三件事：

1. 构造一组共享很长 `SHARED_PREFIX` 的问题，第一次运行作为 cold pass，写入 prefix cache。
2. 用完全相同的一组 prompt 再运行两次 warm pass，取较好的一次，观察 prefill 耗时下降。
3. 用一组长度相近但前缀几乎不共享的请求作为对照，说明前缀不共享时收益有限。

核心代码：

```python
llm = LLM(
    model="/data/liyangyang/models/Qwen3.5-9B",
    dtype="float16",
    tensor_parallel_size=1,
    gpu_memory_utilization=0.55,
    max_num_seqs=32,
    max_model_len=4096,
    enable_prefix_caching=True,
)

sampling_params = SamplingParams(
    temperature=0.0,
    top_p=1.0,
    max_tokens=8,
)

outputs_cold = llm.generate(shared_prompts, sampling_params)
outputs_warm = llm.generate(shared_prompts, sampling_params)
```

观察指标：

- cold elapsed vs warm elapsed。
- prompt tokens 相同，但 warm pass 的 prefill 时间应更低。
- unique prefix batch 的耗时通常接近 cold pass，而不是 warm pass。

> 注意：第一次运行 vLLM 仍会有模型加载、kernel 编译与 warmup 开销。比较 Prefix Cache 收益时，应看 engine 初始化完成后的 `llm.generate` 阶段。

## 8. 常见问题与排查

### 8.1 为什么开了 Prefix Cache 却没有变快？

可能原因：

- prompt 太短，重复前缀占比低。
- 请求之间前缀并不完全相同，例如多了时间戳、request id、随机 seed。
- chat template 渲染结果不稳定。
- `max_tokens` 很大，总耗时由 decode 主导。
- cache 容量不足，前缀 Block 被淘汰。
- batch 很小，prefill 并行收益不明显。

### 8.2 Prefix Cache 会改变输出吗？

理想实现不会改变输出分布，因为它只复用完全相同前缀对应的 KV。若输出不一致，更可能是：

- prompt 实际不同，例如 template、空格、换行、token 化差异。
- 使用了不同 LoRA/adapter、量化配置或模型权重。
- 采样参数或随机种子不同。
- 引擎 bug 或版本不兼容，需要升级并复现最小案例。

### 8.3 Prefix Cache 会不会占用更多显存？

会有 tradeoff：

- 共享前缀可以减少多个活跃请求之间的重复 KV。
- 但为了让“未来请求”命中，引擎可能保留一些已经结束请求的前缀 Block。
- 当 KV 空间紧张时，冷 Block 应被淘汰，否则会挤压当前请求的 KV Cache。

### 8.4 多租户场景可以直接共享吗？

只有前缀 token 完全一致时才应该共享。若不同租户 system prompt 相似但包含 tenant id、权限、时间戳等信息，则不应命中。工程上还要考虑隔离与审计要求，避免把不应共享的上下文放入同一 cache namespace。

### 8.5 Prefix Cache 与 Response Cache 怎么选？

- 用户问题相同且允许直接返回旧答案：Response Cache 收益最大，但要处理一致性与时效性。
- 用户问题不同，但 system prompt / 工具 schema / few-shot 示例相同：Prefix Cache 更合适。
- 两者可以同时使用：Response Cache 拦截完全重复请求，Prefix Cache 加速未命中的相似请求。

## 10. 本节小结

1. **Prefix Cache 缓存的是 prompt 前缀的 KV Block**，不是最终答案，因此理论上不改变输出分布。
2. 它最适合 **长固定前缀 + 短变化后缀** 的场景，例如固定 system prompt、多轮对话、few-shot 与 Agent 工具描述。
3. vLLM APC 以 Block 为粒度做精确匹配，通常只能共享完全相同的连续完整 Block。
4. Block 边界会影响命中率：前缀在 Block 内部分叉时，只能复用分叉前的完整 Block。
5. Prefix Cache 与 PagedAttention、Continuous Batching 是互补关系：前者减少重复 prefill，后两者提升 KV 管理与调度效率。
6. 生产落地时要关注命中率、TTFT、cache 容量、淘汰策略、chat template 稳定性与多租户隔离。

5. 在 RAG 场景中，检索结果每个请求都不同，还能如何利用 Prefix Cache？提示：把稳定部分放在 prompt 前部，把变化部分放在后部。
