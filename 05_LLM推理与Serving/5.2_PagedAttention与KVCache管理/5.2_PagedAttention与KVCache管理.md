## 1. KV Cache 的瓶颈：为什么要优化它？

### 1.1 KV Cache 的显存占用公式回顾

```
KV Cache (bytes) = 2 × num_layers × num_kv_heads × seq_len × head_dim × sizeof(dtype) × batch_size
```

当以下任一因素增大时，KV Cache 都会线性增长：

- **batch_size**：并发请求越多，KV Cache 越多。
- **seq_len**：上下文越长，KV Cache 越多。
- **num_layers / num_kv_heads / head_dim**：模型越大，KV Cache 越多。

### 1.2 传统 KV Cache 分配的痛点

在朴素的 transformers 实现中，每个请求的 KV Cache 通常采用**预分配连续显存**的方式：

```python
# 为每个请求预分配最大长度的 KV Cache
kv_cache = torch.zeros(batch_size, num_layers, num_kv_heads, max_seq_len, head_dim)
```

这种方式存在三个严重问题：

1. **显存预留浪费**：每个请求都按最大可能长度预分配，但实际生成长度通常远小于最大值。例如 prompt 支持 8192，但用户平均只生成 256 个 token，大量显存被预留但未被使用。

2. **内存碎片化**：不同请求生成长度不一，释放后留下大量不连续的小块，导致后续大请求无法分配。

3. **无法动态共享**：不同请求之间无法共享公共前缀（如 system prompt、few-shot 示例），每个请求都重复存储。

### 1.3 实际业务中的挑战

| 场景 | 问题 |
|------|------|
| 多轮对话 | 每轮对话都复制历史 KV Cache，显存占用翻倍 |
| 长文档 | 长 prompt 导致 KV Cache 巨大，无法高并发 |
| System prompt 共享 | 每个请求都重新计算相同的 system prompt，浪费算力和显存 |
| 变长请求 | 长短不一的请求导致 batch 填充（padding）浪费显存 |

## 2. PagedAttention：核心思想

### 2.1 类比操作系统虚拟内存

PagedAttention 借鉴了操作系统中**虚拟内存（Virtual Memory）**的设计思想：

- 操作系统把物理内存划分为固定大小的 **页（Page）**，进程的虚拟地址空间映射到不连续的物理页上。
- 类似地，PagedAttention 把 KV Cache 划分为固定大小的 **块（Block）**，每个请求的 KV Cache 逻辑上连续，但物理上可以不连续。

### 2.2 核心概念

#### Block（块）

- 每个 Block 包含固定数量的 token 的 K/V 向量。
- 例如每个 Block 容纳 16 个 token 的 K/V。
- Block 是显存分配的最小单位。

#### Logical Block / Physical Block

- **Logical Block**：某个请求视角下连续的 KV Cache 块，用 block number 表示。
- **Physical Block**：GPU 显存中实际分配的 KV Cache 块。
- 通过 Block Table 维护 logical → physical 的映射关系。

#### Block Table

每个请求都维护一个 Block Table：

```
Request A: [logical_block_0 → physical_block_5]
           [logical_block_1 → physical_block_2]
           [logical_block_2 → physical_block_9]

Request B: [logical_block_0 → physical_block_5]  (共享 A 的第一块！)
           [logical_block_1 → physical_block_7]
```

### 2.3 PagedAttention 的优势

1. **按需分配**：请求生成多少 token，就分配多少 Block，不浪费。
2. **消除外部碎片**：所有 Block 大小相同，分配和回收简单高效。
3. **支持共享**：通过 Block Table 映射，多个请求可以共享相同的 Physical Block（Copy-on-Write）。
4. **高吞吐**：结合 Continuous Batching，可以服务更多并发请求。

### 2.4 PagedAttention 算法示意

传统 Attention 的输入是一个连续的 KV Cache 张量：

```python
# 传统方式：K, V 是连续的
scores = Q @ K.transpose(-2, -1) / sqrt(d_k)
attn = softmax(scores)
output = attn @ V
```

PagedAttention 中，K 和 V 被分散在多个 Block 中：

```python
# PagedAttention 方式：K_blocks 和 V_blocks 是 Block 列表
for block_id in block_table:
    K_block = K_blocks[block_id]  # [num_heads, block_size, head_dim]
    V_block = V_blocks[block_id]
    # 计算当前 query 与该 block 的 attention
    ...
```

vLLM 中的实现使用 CUDA kernel 优化了这一过程，对外暴露的接口与标准 transformer 类似。

## 3. vLLM 架构解析

### 3.1 vLLM 是什么？

vLLM 是一个针对 LLM 推理高吞吐优化的开源引擎，核心贡献就是 **PagedAttention**。它提供了：

- 高效的 KV Cache 管理（PagedAttention）。
- Continuous Batching（动态批处理）。
- OpenAI-compatible API server。
- 支持多种量化格式（AWQ、GPTQ、FP8、INT8 等）。
- 多 GPU 推理（Tensor Parallelism、Pipeline Parallelism）。

### 3.2 vLLM 核心组件

| 组件 | 作用 |
|------|------|
| **LLMEngine** | 核心调度引擎，管理请求队列、KV Cache、模型执行 |
| **Scheduler** | 决定哪些请求可以进入当前 batch |
| **BlockManager** | 管理 Physical Block 的分配与回收 |
| **Worker** | 实际执行模型推理的进程（支持多 GPU） |
| **Model Runner** | 加载模型并执行 forward / decode |

### 3.3 vLLM 的调度流程

```
1. 请求到达 → 加入 waiting queue
2. Scheduler 从 waiting queue 选择可运行的请求
3. 为每个请求分配/复用 Physical Block
4. 执行 Prefill / Decode
5. 将完成的请求返回，释放或保留 KV Cache（多轮对话）
```

### 3.4 Continuous Batching

vLLM 使用 **Continuous Batching**（也叫 iteration-level scheduling）：

- 传统 batching：一个 batch 内所有请求完成后再处理下一个 batch。
- Continuous Batching：每个 iteration 结束后，完成的请求被移出，新的请求可以立即加入。
- 这大大提高了 GPU 利用率，尤其是在请求长度差异大的场景。

## 4. KV Cache 进阶管理技术

### 4.1 KV Cache 量化

KV Cache 量化通过降低 K/V 的精度来减少显存占用。常见方案：

| 方案 | 精度 | 显存降低 | 精度影响 | 代表工作 |
|------|------|---------|---------|---------|
| **INT8 KV Cache** | 8-bit | ~2x | 较小 | 通用方案 |
| **FP8 KV Cache** | 8-bit | ~2x | 较小 | NVIDIA、vLLM FP8 |
| **KIVI** | 2-bit K + 4-bit V | ~4-8x | 中等 | KIVI (Liu et al., 2023) |
| **KVQuant** |  per-channel | ~2-4x | 较小 | KVQuant (Yao et al., 2023) |

vLLM 已支持 KV Cache 的 FP8/INT8 量化，配置简单。

### 4.2 Prefix Caching（前缀缓存）

**Prefix Caching** 是 PagedAttention 的自然延伸：

- 如果多个请求有相同的前缀（如 system prompt、RAG 检索结果），它们的 KV Cache 可以共享。
- vLLM 通过 RadixAttention 实现：将 prefix 的 KV Cache 缓存起来，新请求直接复用。
- 这极大减少了多轮对话和 RAG 场景的重复计算。

### 4.3 Chunked Prefill

**Chunked Prefill** 将长 prompt 的 prefill 阶段拆分成多个小块：

- 避免单个长 prefill 占用 GPU 过久，导致 decode 请求等待。
- 将 prefill 和 decode 混合在同一个 batch 中，提高整体吞吐。
- vLLM 在较新版本中已支持此特性。

### 4.4 MQA / GQA

- **MQA (Multi-Query Attention)**：所有 query 共享同一组 K/V，KV Cache 最少。
- **GQA (Grouped-Query Attention)**：多个 query 共享一组 K/V，平衡显存与质量。
- **MHA (Multi-Head Attention)**：每个 query 有独立的 K/V，KV Cache 最大。

现代模型（如 LLaMA 2/3、Qwen 2/3、Mistral）普遍使用 GQA 来降低 KV Cache。

## 6. 性能对比：transformers vs vLLM

### 6.1 对比维度

| 维度 | transformers | vLLM |
|------|-------------|------|
| KV Cache 管理 | 连续预分配，碎片化严重 | PagedAttention，按需分配 |
| Batching | 静态 batch | Continuous Batching |
| Prefix 共享 | 不支持 | 支持（Prefix Caching） |
| 服务化 | 需自行封装 | 内置 API Server |
| 吞吐 | 较低 | 显著更高 |
| 易用性 | 简单 | 稍复杂，但功能强大 |

### 6.2 吞吐对比实验设计

可以通过以下步骤进行对比：

1. 准备 100 个长度不同的 prompt。
2. 使用 transformers 顺序或简单 batch 推理，记录总时间。
3. 使用 vLLM 以相同并发度推理，记录总时间。
4. 对比两种方式的 Throughput（tok/s 或 req/s）。

典型结果：vLLM 的吞吐通常是 transformers 的 **2-10 倍**，尤其在请求长度差异大和并发高的场景。

## 7. 常见问题与排查

### 7.1 vLLM 安装失败

- 检查 CUDA 版本与 PyTorch 版本是否兼容。
- 尝试安装预编译 wheel：`pip install vllm`。
- 如果 GPU 较旧，可能需要 `--no-build-isolation` 从源码编译。

### 7.2 vLLM 出现 OOM

- 减小 `--max-num-seqs` 限制并发数。
- 启用 KV Cache 量化（`--kv-cache-dtype fp8`）。
- 减小 `--max-model-len` 限制最大序列长度。
- 启用 prefix caching 减少重复 KV Cache。

### 7.3 输出与 transformers 不一致

- vLLM 与 transformers 的采样实现可能存在细微差异。
- 检查 `temperature`、`top_p`、`repetition_penalty` 等参数是否一致。
- 设置相同的随机种子。

### 7.4 PagedAttention 是否总是更好？

PagedAttention 主要提升吞吐和显存效率，但：

- 小 batch、单请求场景优势不明显。
- 实现更复杂，调试难度更高。
- 对特定自定义模型支持可能不完善。

## 9. 本节小结

1. **KV Cache 是 LLM 推理的核心显存瓶颈**，传统连续预分配方式存在严重浪费和碎片化。
2. **PagedAttention** 借鉴操作系统虚拟内存思想，将 KV Cache 划分为 Block，实现按需分配、消除碎片、支持共享。
3. **vLLM** 是基于 PagedAttention 的高吞吐 LLM 推理引擎，提供 Continuous Batching 和 OpenAI-compatible API。
4. **KV Cache 量化、Prefix Caching、Chunked Prefill** 是进一步提升效率和降低延迟的关键技术。
5. **GQA/MQA** 通过减少 KV Head 数量降低 KV Cache，是现代 LLM 的重要设计。
6. 生产环境中，vLLM 通常比原生 transformers 有显著吞吐优势，尤其在长上下文和高并发场景。
