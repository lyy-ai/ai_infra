# 16.2 预训练数据处理

> 学习目标：掌握预训练数据处理的核心技术环节——文本提取、去重（MinHash/LSH）、质量过滤、去污、隐私处理，以及主流开源框架（datatrove / NeMo Curator / Data-Juicer / Dolma）。

## 1. 文本提取与解析

原始网页语料（Common Crawl 的 WARC 格式）到可用文本的处理链：

1. **HTML 解析与正文提取**：trafilatura/resiliparse 等工具从 HTML 提取正文（去导航、广告、页脚）。
2. **语言识别**：fastText 语言分类器，按目标语言过滤（保留率与识别精度的权衡）。
3. **格式规范化**：Unicode 归一化、去控制字符、处理乱码与断行。
4. **代码/数学等特殊格式保留**：代码块的缩进、数学公式需要在提取时特殊处理——这也是为什么主流管线对代码类域名（GitHub、StackExchange）单独处理。

## 2. 去重（Deduplication）—— 数据处理的"第一课"

去重是收益最大的单一环节：网页语料中重复/近重复内容占比可达 30-50%，不去重会导致模型记忆化、泛化下降、有效训练 token 被浪费。

**三个层级**：

1. **精确去重**：URL 或文档哈希完全相同 → 直接删除（最便宜）。
2. **模糊去重（MinHash + LSH）**：近重复检测的标准方案——
   - 文档 → n-gram 集合 → MinHash 签名（用 k 个哈希函数压成 k 维签名，签名相似度 ≈ 集合 Jaccard 相似度）；
   - LSH 分桶：把 k 维签名切成 b 个 band，同 band 相同的文档对进入候选（把 O(N²) 的两两比较降为近线性）；
   - 候选对做精确 Jaccard 验证，按阈值（如 0.8）判定重复。
3. **语义去重**：用嵌入向量找语义近重复（更贵，通常只用于高价值子集）。

配套脚本 `minhash_dedup_demo.py` 完整实现了 MinHash+LSH 流程，可直观看到签名相似度与 Jaccard 的关系。

## 3. 质量过滤（Quality Filtering）

两类方法互补使用：

**规则/启发式过滤**（便宜，第一道）：
- 长度异常（过短/过长）、字符统计（乱码率、重复行比例）、标点/大写比例、停用词覆盖（是否是自然语言）、域名黑白名单、样板文本（boilerplate）检测。

**模型/分类器过滤**（贵，第二道）：
- **fastText 质量分类器**：用"已知高质量语料（维基/书籍）vs 随机网页"训练二分类器，给每篇文档打质量分——FineWeb/DCLM/GPT-3 时代的标准做法。
- **Perplexity 过滤**：用小语言模型算困惑度，砍掉异常高（乱码）和异常低（模板重复）的文档。
- **LLM 打分**：用大模型直接评估质量（最贵，用于高价值子集或生成训练分类器的标签）。

关键认知：**过滤阈值是配比问题而非纯技术问题**——激进过滤提升平均质量但可能造成领域偏斜（如过滤掉口语化内容后模型不会聊天），需要按领域分别标定。

## 4. 去污（Decontamination）

**benchmark 污染**：训练语料中包含评测集题目 → 评测分数虚高、能力误判。处理：

- n-gram 重叠检测：文档与评测集做 n-gram（如 13-gram）匹配，命中即删或标记。
- 嵌入级相似：对改写的题目（非逐字重复）用嵌入相似度兜底。
- 工程难点：评测集本身保密时如何去污（加密哈希交换）、去污报告的透明度（FineWeb/DCLM 都公开了去污方法与命中统计）。

## 5. 隐私与安全（PII）

- PII（个人身份信息）检测与打码：邮箱、电话、身份证号的规则 + NER 模型识别，删除或替换。
- 合规要求（GDPR 等）：数据来源的可撤回机制（opt-out 列表的下游传播）。
- 代码语料的特殊问题：许可证扫描（GPL 传染性、license 头保留）。

## 6. 主流开源框架对比

| 框架 | 背景 | 特点 | 仓库 |
|------|------|------|------|
| **datatrove** | HuggingFace | FineWeb 的生产管线，轻量、模块化、支持本地/Slurm/Ray 执行 | github.com/huggingface/datatrove |
| **NeMo Curator** | NVIDIA | GPU 加速的数据处理（RAPIDS 生态），语义去重/分类模块强，与 Nemotron-CC 数据集配套 | github.com/NVIDIA/NeMo-Curator |
| **Data-Juicer** | 阿里巴巴 | 算子最丰富（百+种处理/分析算子），多模态数据支持好，配置驱动 | github.com/modelscope/data-juicer |
| **Dolma toolkit** | AI2 | Dolma 数据集的配套工具，tagging 体系完整 | github.com/allenai/dolma |
| **DCLM 工具链** | DCLM 团队 | DCLM 数据集的完整复现管线，实验设计严谨 | github.com/mlfoundations/dclm |

**选型建议**：学原理用 datatrove（代码干净、文档好）；GPU 资源充足且要语义级处理用 NeMo Curator；国内多模态场景用 Data-Juicer。

## 7. 工程要点：规模与成本

- 数百 TB 文本的处理是 Spark/Ray 集群的天职——按"每 TB 处理成本"做技术选型（GPU 过滤 vs CPU 过滤差一个量级价格）。
- 管线必须**增量可重跑**：新一批 Common Crawl 只跑新增部分；中间结果物化（Parquet 落盘）避免重复计算。
- 每个环节记录保留率与质量采样报告——数据处理没有"跑完就行"，只有"知道留下了什么"。

## 9. 面试视角

- **Q：MinHash 为什么能近似 Jaccard 相似度？** A：对随机哈希函数，两集合最小哈希值相等的概率恰等于其 Jaccard 相似度；k 个独立哈希的相等比例就是 Jaccard 的无偏估计。
- **Q：LSH 的 band 数怎么影响召回？** A：band 越多越宽松（召回高、候选对多、验证贵），越少越严格；按目标相似度阈值调参。
- **Q：怎么去 benchmark 污染？** A：n-gram 重叠检测为主（如 13-gram 命中即删），嵌入相似度兜底改写题；关键是去污方法要公开可审计。
